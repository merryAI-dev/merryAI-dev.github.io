안녕하세요, MYSC AXR팀의 보람입니다.

저장 응답이 왔습니다. 이제 끝내도 될까요? 세금계산서 처리에서 제가 먼저 짚고 싶은 장면은 **저장한 값을 다시 읽는 순간**입니다. 개발 이력에는 이전 문서에서 조회한 계좌 표시값을 그대로 보냈고, 서버가 그 문자열을 저장한 문제를 재조회 검증에서 발견했다는 기록이 남아 있습니다. 요청이 받아들여졌다는 것과 의도한 값이 저장됐다는 것은 다른 사건이었습니다.

잠깐 PDF를 받은 시점으로 돌아가 보겠습니다. 메일을 읽었는지, PDF가 얼마인지, 이미 지급한 건인지, 같은 증빙을 올린 적이 있는지, 이전 문서의 어느 값을 재사용할 수 있는지가 차례로 결정됩니다. AI가 이 과정을 진행하더라도 어떤 근거로 다음 단계에 갈지는 사람이 정한 조건과 코드가 함께 결정합니다.

[1편](/posts/amaranth-expense-skill/)이 Skill과 CLI의 역할을 나누고 질문을 다듬은 이야기라면, 이번에는 `taxinvoice.py`에서 증빙 한 건을 처리하는 검증 루프를 따라갑니다. 카드 양식 1211과 세금계산서 양식 1210은 저장 구조 일부를 공유하지만 같은 업무는 아닙니다.

**근거와 예시를 구분합니다.** 아래 ‘변경 기록의 요지’는 실제 커밋 설명과 diff를 의역한 것입니다. 대화 원문은 확인하지 않았으므로 보람이나 AI의 당시 대사를 만들어 넣지 않았습니다. 제 해석은 구현 분석으로 설명합니다. 흐름을 연결하는 ‘예시클라우드, 공급가액 100,000원·세액 10,000원’은 합성 사례이며 실제 한 건의 처리 기록이 아닙니다. 실제 거래처·금융정보·인증정보는 제외했습니다.

## PDF는 한 장인데, 채울 칸은 여럿

**합성 사례를 하나 정하겠습니다.** 담당자 A가 예시사업 A에서 사용한 서비스에 대해 ‘예시클라우드’의 전자세금계산서를 받았습니다. 공급가액은 100,000원, 세액은 10,000원, 합계는 110,000원이고 `[영수]`로 표시돼 있습니다. 담당자는 이 서비스가 카드로 이미 결제된 건이라고 설명합니다. 실제 자료의 이름이나 금액을 바꿔 옮긴 것이 아니라 흐름을 설명하기 위해 만든 사례입니다.

아마란스에 옮길 것은 합계 한 칸만이 아닙니다. 증빙에 적힌 거래처와 작성일자, 공급가액·세액·합계를 구분하고, 담당자의 업무 설명을 적요와 프로젝트에 연결해야 합니다. 이미 결제한 건인지에 따라 지급 정보와 비고도 달라집니다.

| 증빙·업무에서 확인한 사실 | 지출결의에 반영할 내용 | 자동으로 확정할 수 없는 것 |
|---|---|---|
| 공급자와 공급받는자 | 거래처 이름, 우리 회사의 증빙인지 비교 | 상호가 비슷한 별도 법인의 동일성 |
| 공급가액 100,000원·세액 10,000원 | 공급가액·세액·합계 각각의 금액 | 세법상 처리 적정성 |
| 세금계산서 작성일 | 증빙일자, 기본 회계일 | 다른 날짜로 처리할 사유의 적정성 |
| 예시사업 A에서 사용 | 적요·용도·프로젝트 제안과 확인 | 이번 지출의 실제 목적 |
| 이미 카드 결제했다는 설명 | 결제 후보·결제일·비고·결제 증빙 확인 | 같은 금액만으로 같은 거래임을 확정 |
| 임시보관 요청 | 검토한 값으로 초안 저장 후 재조회 | 상신·결재·실제 지급 완료 |

이 사례에서 세금계산서의 합계와 카드 금액이 같더라도 두 문서가 같은 역할을 하는 것은 아닙니다. 카드 거래는 결제 관계를 확인하는 자료이고, 세금계산서는 공급가액과 세액 등 증빙 항목의 근거입니다. 도구는 현재 조직의 절차에 맞춰 초안을 준비하며, 두 증빙의 회계상 관계를 독자적으로 판단하지 않습니다.

## 메일은 읽었는데, 결의서는 올렸나요?

메일함의 읽음 표시는 편리합니다. 처음의 Skill 절차에도 세금계산서 메일에서 안 읽은 메일과 안 올린 건을 알리라는 안내가 있었습니다. 두 상태를 분리하는 기준이 충분히 구체적이지 않았습니다. 이미 메일을 열었어도 결의서를 만들지 않은 경우에는 읽음 상태로 업무 완료를 판단할 수 없습니다.

**변경 기록의 요지 — `25681cf`:** 확인 기준을 메일 읽음 여부에서 기존 1210 문서 유무로 바꾼다. 발행 안내만 담긴 메일에서 금액을 확정하지 않고 PDF의 금액·승인번호와 대조한다. 작성일이 같다는 이유만으로 같은 건으로 단정하지 않는다.

수정의 핵심은 어디를 보고 판단할지 정한 데 있습니다. 메일은 찾아야 할 증빙의 단서, PDF는 증빙 값, 그룹웨어 문서는 이미 처리했는지를 확인할 근거가 됩니다. 각각 다른 질문에 답하는 자료입니다.

따라서 합성 예시에서 메일을 열어봤다는 사실만으로 110,000원짜리 증빙을 건너뛰지 않습니다. PDF를 읽고 기존 결의와 비교해야 합니다. 반대로 열람 링크만 있는 메일에서는 금액을 채우지 않습니다. 이 판단은 당시 다루던 안내 메일에 대한 것이며 모든 세금계산서 메일의 형식이 같다는 주장은 아닙니다.

Gmail 확인은 선택적인 커넥터를 사용하는 Skill 절차입니다. CLI에 메일함 감시 기능이 구현된 것은 아닙니다. 지출결의 연동은 MCP 서버 없이 CLI로 처리하지만, 메일 확인은 별도 연결에 의존합니다. 이번 검증에서 Gmail 처리 루프를 재실행하지 않았으므로 자동 알림의 운영 성과로 제시하지 않습니다.

## 100원이 안 맞으면, 일단 멈춘다

금액은 PDF에 적힌 칸에서 각각 읽습니다. `read_invoice`는 `pdftotext -layout`으로 텍스트를 얻고, `parse_invoice`가 지원하는 홈택스 표준 서식에서 작성일자·공급가액·세액·합계·승인번호·상호와 등록번호를 읽습니다. 전자계산서는 세액을 0으로 처리합니다. 합계만 보고 부가세를 역산하지 않는 이유는 원본이 이미 공급가액과 세액을 구분해 주기 때문입니다.

예를 들어 합성 PDF에 공급가액 100,000원, 세액 10,000원, 합계 110,000원이 적혀 있다면 이 세 값을 각각 읽고 덧셈이 맞는지 검사합니다. 합계가 110,100원이라면 부족한 100원을 임의의 칸에 넣지 않고 중단합니다.

승인번호 앞부분의 날짜와 작성일자가 일치하는지도 검사합니다. 이것은 현재 파서가 채택한 지원 조건입니다. 날짜가 다르다는 이유만으로 해당 증빙이 법적으로 잘못됐다고 판정하는 기능은 아닙니다. 지원하는 패턴 밖의 증빙은 자동 처리에서 멈추고 사람이 확인해야 합니다.

스캔본을 읽는 OCR은 없고, 음수 금액과 코드에서 식별하는 수정 사유도 거절합니다. 수정세금계산서 전반, 표준 밖 서식, 원천징수 대상 외부인건비까지 처리하는 범용 세무 엔진은 아닙니다. 문서의 종류를 넓히는 것보다 읽지 못한 값을 그럴듯하게 채우지 않는 쪽으로 범위를 정했습니다.

## 이미 낸 돈인가, 앞으로 낼 돈인가

같은 세금계산서라도 이미 결제했는지에 따라 다음 할 일이 달라집니다. 검토안은 PDF의 `[영수]`와 `[청구]` 표시를 보고 인식용 `recognition`과 지급요청용 `payment`를 제안합니다. 표시가 불분명하거나 여러 PDF가 섞여 하나로 정할 수 없으면 질문을 남깁니다. 사용자가 방식을 바꾸면 원본 표시와 다르다는 경고를 보관합니다.

| 확인 항목 | 인식용 초안 | 지급요청용 초안 |
|---|---|---|
| 업무 전제 | 이미 결제한 건의 회계 인식 | 거래처에 지급할 건의 결의 준비 |
| 결제일 | 카드 후보 또는 확인된 결제일 필요 | 카드 결제 후보를 요구하지 않음 |
| 수취 정보 | 승인된 이전 문서의 회사 계좌 근거 | 같은 거래처의 승인된 이전 지급 계좌 근거 |
| 출금계좌 안내 | 비우도록 안내 | 입력을 필수로 요구 |
| 실행의 끝 | 임시보관 | 임시보관 |

여기서 `payment`는 지급 실행 명령이 아닙니다. 지급할 건의 결의 초안을 만드는 모드입니다. 어떤 모드를 선택해도 도구가 상신하거나 계좌이체를 실행하지는 않습니다. 또한 이 구분과 계좌 배치는 MYSC에서 확인한 업무 흐름을 반영한 것으로, 다른 조직에 그대로 적용할 회계 처리 지침은 아닙니다.

‘인식용이면 출금계좌가 절대로 들어가지 않는다’고 설명하는 것도 정확하지 않습니다. Skill은 비우도록 안내하지만, 코드에서는 인식용에 출금계좌를 넣으면 경고를 남깁니다. 지급요청에서 출금계좌가 없는 경우의 저장 차단과는 강도가 다릅니다. 업무 안내와 강제 검증을 구분해야 실제 보호 범위를 알 수 있습니다.

## 11만 원짜리 카드 거래를 찾았다. 같은 건일까?

합성 PDF에 `[영수]`가 있고 합계가 110,000원이라면, 다음 질문은 이 금액을 이미 어떻게 결제했는가입니다. `card_matches`는 개인 프로필에 지정된 카드에서 작성일부터 31일 안의 미반영 거래 중 같은 금액을 찾습니다. 다음은 함수의 비교 기준을 줄인 **설명용 의사코드**입니다.

```python
end = min(invoice.issued + days(31), today)
candidates = [
    row for row in unreflected_card_rows(invoice.issued, end)
    if row.approved_amount == invoice.total
]
```

`build_plan`은 후보가 하나면 결제일을 제안하고, 없거나 여러 개면 미해결 항목을 만듭니다. AI는 후보를 설명하고, 사용자는 실제 결제 관계와 날짜를 확인합니다. 이체였다면 별도로 확인된 날짜와 방식을 넣습니다. 단, 단일 후보의 날짜를 자동 제안하는 것은 코드 동작이고 그 관계를 사람이 검토하도록 하는 것은 Skill의 절차입니다. 모든 후보에 별도의 강제 확인 플래그가 있는 것은 아닙니다.

후보를 찾았지만, 아직 결제 짝을 찾았다고 말할 단계는 아닙니다. 현재 함수는 카드 가맹점과 PDF 공급자의 동일성을 강하게 검사하지 않습니다. 같은 기간에 우연히 같은 금액의 거래가 하나 있어도 후보가 됩니다. 이미 반영된 카드 거래는 검색에서 빠질 수 있습니다. **이 결과는 동일 금액 후보이지 동일 거래의 증명은 아닙니다.**

Skill은 인식용 문서를 만든다는 이유로 카드 결의의 해당 거래를 자동 제외하지 않도록 합니다. 세금계산서와 카드 결의가 어떤 회계 관계에 놓이는지는 재경 판단에 남깁니다. AI가 합계를 보기 좋게 만들기 위해 거래를 삭제하는 선택을 하지 않도록 경계를 둔 것입니다.

## 이 세금계산서, 이미 처리한 것 아닌가요?

같은 증빙을 다시 올리지 않기 위해 두 종류의 정보를 사용합니다. 로컬 작업 기록은 승인번호를 기준으로 저장 시도를 구분하고, 기존 1210 문서 조회는 증빙일·합계·거래처를 비교합니다. ERP 행에 승인번호가 저장되지 않기 때문에 서버 문서 비교에서는 대체 조건이 필요합니다. 승인번호는 비고에도 남기도록 되어 있습니다.

조회 기간은 가장 이른 증빙 작성일에서 366일 전부터 현재까지입니다. 조회한 문서 중 같은 증빙일·합계에 공급자 상호도 맞는 후보가 있으면 차단하고, 반려 문서는 참고 경고로 남깁니다. 상호가 비어 있으면 날짜와 금액이 같은 문서가 넓게 후보로 잡힐 수 있습니다. 전사·전기간의 중복을 승인번호로 완벽하게 판별하는 것은 아닙니다.

회사 확인도 비슷합니다. 파서는 공급받는자의 등록번호를 추출하지만, 검토안에서 회사와 비교하는 것은 **상호 문자열**입니다. `same_party`는 법인 표기와 공백 등을 정리하고 일치 또는 포함 관계를 검사합니다. 사업자등록번호의 정확한 일치나 외부 기관 조회를 수행하는 검증과는 다릅니다. 비슷한 상호를 구분해야 하는 사례에는 추가 확인이 필요합니다.

여기서는 무엇을 확인했는지 구체적으로 말해야 합니다. 공급가액과 세액의 덧셈은 결정적으로 확인할 수 있지만, 이름의 포함 관계는 동일 법인임을 보증하지 못합니다. 두 검사를 같은 확신 수준으로 사용자에게 설명해서는 안 됩니다.

## 지난 문서에서 가져와도 되는 것들

같은 거래처의 승인된 1210 문서에서 적요·용도·프로젝트를 제안합니다. 인식용이고 카드 결제 후보가 있으면 해당 가맹점의 승인된 카드 결의 적요를 먼저 참고해 두 양식의 표현을 맞춥니다. 가장 많이 쓴 표현을 제안하되 동률이면 질문하고, 다른 표현이 있으면 참고 정보로 보여줍니다.

이 정책은 앞선 카드 글의 이력 충돌 처리와 같지 않습니다. 카드 경로는 서로 다른 선택을 질문으로 남기지만, 세금계산서의 카드 적요 제안은 최빈값과 동률 여부를 사용합니다. 공통 Skill 아래에 있다고 해서 두 모듈의 판단 기준까지 같다고 가정하면 안 됩니다.

처음 보는 거래처에서는 사용자 확인이 필요하다고 Skill이 지시합니다. 다만 구현에는 용도의 기본 코드와 프로필의 기본 프로젝트를 채우는 경로도 있습니다. 따라서 ‘이력이 없으면 모든 값이 반드시 빈칸이고 저장이 항상 막힌다’는 설명은 맞지 않습니다. 누락 항목을 막는 코드 검사와, 제안값을 사용자에게 확인받는 대화 절차가 함께 필요합니다.

반면 수취 계좌는 임의의 새 값을 입력받는 경로를 두지 않았습니다. 사용할 수 있는 승인 문서가 없으면 첫 건은 그룹웨어에서 직접 작성하도록 막습니다. 과거 승인 계좌가 현재도 유효한지는 별도로 검토해야 하며, 과거에 승인됐다는 사실만으로 이후 변경 가능성이 사라지는 것은 아닙니다.

## 날짜도 계좌도, 복사 전에 한 번 더

개발 이력의 `84c913a`는 증빙일자를 세금계산서 작성일자로 고정합니다. 코드에는 재경 반려 사유를 반영한 규칙이라는 설명이 있습니다. 결제일, 메일 수신일, 증빙 작성일은 각각 다른 사건을 가리킵니다. 잘못된 날짜를 입력한 뒤 안내 문구만 붙이는 대신 저장 직전 검증에도 조건을 넣었습니다.

```python
# validate의 실제 비교식에서 오류 메시지만 생략
if any(row["issDt"] != invoice["issued"]
       for row, invoice in zip(plan["rows"], plan["invoices"])):
    raise ExpenseError("증빙일자는 작성일자여야 합니다")
```

반면 회계일은 기본값이 작성일자일 뿐, 같은 해의 다른 날짜는 경고로 남습니다. 다른 해이면 차단합니다. 모든 날짜를 똑같이 고정하는 대신 각 필드의 의미와 검증 강도를 나눈 것입니다. 이 글은 해당 조직의 구현을 설명하며 일반적인 회계·세무 지침을 제시하지 않습니다.

계좌 문제는 더 직접적입니다. **변경 기록의 요지 — `c7fd293`:** 첫 실서버 저장에서 조회 응답의 마스킹·암호화 표시값을 그대로 보냈고, 서버가 그 문자열을 계좌로 저장했다. 재조회 검증이 이를 발견했다.

대화 원문이 없으므로 제가 AI에게 어떤 표현으로 수정 요청을 했는지는 적을 수 없습니다. 하지만 선택의 결과는 diff에서 확인할 수 있습니다. 조회한 계좌를 그대로 복사하는 대신, 승인된 문서의 숫자 계좌값만 선택하고 저장 직전에도 형식을 확인하도록 바뀌었습니다. 테스트 역시 ‘조회 표시값과 같다’에서 ‘숫자 계좌값과 같다’로 기대값이 바뀌었습니다.

```python
# 변경 전: 조회용 표현을 저장에 재사용
"baNb": bank.get("baNb") or ""

# 변경 후: 승인 문서의 저장용 값을 검사해 사용
"baNb": plain_account(bank.get("decryptBaNb"))
```

`plain_account`는 숫자 형식을 검사합니다. 이것만으로 계좌 소유자나 현재 유효성까지 검증하는 것은 아닙니다. 그래서 사용할 수 있는 승인 문서가 없는 첫 거래는 직접 작성하도록 하고, 저장 후에는 다시 조회한 계좌값을 계획한 값과 비교합니다. 실제 계좌값은 예시나 코드에 넣지 않았습니다.

이 장면은 AI가 버그를 내지 않았다는 성공담보다, AI와 개발할 때 **성공 판정의 기준을 어디에 놓아야 하는가**를 잘 보여줍니다. 요청을 정상적으로 보낸 코드는 있어도 필드의 의미가 틀릴 수 있습니다. 재조회가 없었다면 로컬 검토안만 보고 끝낼 가능성이 있었습니다. 수정의 초점은 모델에게 더 주의하라고 지시하는 것에 그치지 않고, 변환 규칙과 회귀 테스트를 바꾸는 데 있었습니다.

## 저장됐다고 끝난 게 아니었다

이제 임시보관 차례입니다. `prepare`는 검토안과 질문을 만들고, `check`는 저장 직전 조건을 다시 확인합니다. PDF를 다시 읽어 검토 후 변경되지 않았는지 확인하고, 첨부 해시, 로그인 계정, 중복 후보, 마감일, 현재 사용 가능한 용도를 검사합니다. Skill은 이 검사와 별도로 최종 내용을 보여주고 임시보관 요청을 받도록 합니다.

저장 후 `verify_tax`는 ERP의 합계·공급가액·세액·증빙일·지급요청일·용도·적요·프로젝트 등 주요 필드를 검토안과 비교합니다. 이어 전자결재 임시보관 상태, 본문의 비고 문장, 첨부 개수와 식별자, 다운로드한 PDF의 해시를 확인합니다. 본문의 모든 시각적 배치를 검증하는 것은 아니며, 비고 포함 검사와 ERP 값 대조를 구분해서 이해해야 합니다.

임시보관 뒤에는 검토안의 기대값과 서버의 실제 값을 비교합니다. 아래는 `verify_tax`의 여러 검사 중 핵심을 줄인 **설명용 의사코드**입니다.

```python
saved = client.document(journal.link_key)
require(saved.erp_state == "5")
compare_fields(saved.rows, plan.rows)
compare_account(saved, plan)
require(eap.document_state == "10")
require(expected_notes_present(eap.body))
require(downloaded_pdf_hash == original_pdf_hash)
# 위 조건들을 통과한 뒤에만 verified
```

상태 코드 두 개는 서로 다른 계층을 뜻합니다. ERP의 임시보관과 전자결재의 임시보관을 각각 확인해야 합니다. 첨부도 파일명이 같다는 확인 대신 실제 다운로드 바이트의 해시를 비교합니다. 다만 PDF 해시 일치는 첨부 동일성의 증거이며, 거래의 업무 목적이나 증빙의 진위를 확인하는 것은 아닙니다.

중간 실패는 단계별 작업 기록으로 남깁니다. 불명확한 업로드·연결키·ERP 쓰기는 자동 재전송하지 않습니다. 전자결재 저장 응답이 유실되면 연결된 문서를 조회해 복구를 시도합니다. 기존 기록이 있으면 같은 `draft` 호출이 재개 경로를 타며, 1편의 카드 모듈처럼 별도 `resume` 명령을 쓰는 방식과는 다릅니다.

재조회에서 값이 다르면 자동으로 문서를 고치지 않습니다. Skill의 절차는 차이를 알리고, 사용자가 그룹웨어에서 임시보관 문서를 삭제했다면 상태를 확인한 뒤 기록을 보관하고 다시 준비하는 것입니다. 이때도 **절차가 의도하는 조건과 코드가 실제 허용하는 조건을 구분해야 합니다.** 현재 `retire_command`는 삭제 상태 외의 상태가 반환되면 막지만, 조회 결과가 비어 있어도 보관을 허용합니다. ‘삭제 상태가 명시적으로 반환된 경우에만 가능하다’고 단정할 수 없습니다.

이 부분은 이번 글을 고치며 코드와 설명을 다시 대조해 발견한 한계입니다. 빈 응답과 명시적 삭제를 구분해 더 엄격히 처리하는 것은 향후 개선 항목으로 남깁니다. 현재 구현에 이미 존재하는 안전장치처럼 도식에 넣지 않았습니다. 이번 작업에서는 재무 연동 코드를 수정하거나 운영 문서를 삭제하지 않았습니다.

## 테스트가 통과해도 남는 질문들

이번 확인에서는 네트워크를 차단하고 합성 입력과 가짜 클라이언트를 사용하는 기본 테스트를 실행했습니다. 세금계산서·계산서 파싱, 금액 불일치와 음수 차단, 중복·회사명·연도·용도 검사, 본문 생성과 HTML 이스케이프, 양식 변경 차단이 통과했습니다. 저장 순서와 재실행 시 추가 쓰기 없음, 불명확한 단계의 재전송 차단, 전자결재 응답 유실 복구도 가짜 서버 응답으로 확인했습니다.

파서 테스트 통과는 지원 서식의 텍스트 해석을 검증한 결과입니다. 모든 발행처 PDF나 실제 금융기관 처리 결과를 검증한 것은 아닙니다. 회사명 비교와 카드 후보 매칭의 한계 역시 테스트 통과만으로 없어지지 않습니다.

기존 로컬 세금계산서 작업 기록에는 `verified` 상태와 문서 식별자, 첨부 검증 결과가 남아 있었습니다. 이를 과거 임시보관 검증의 증거로 확인했고, 실제 거래 내용은 공개 자료에 옮기지 않았습니다. 현재 서버 상태를 재조회하거나 신규 저장을 실행한 것은 아닙니다. 최종 상신과 결재·지급이 이 도구로 검증됐다는 주장은 하지 않습니다.

세금계산서 처리에서 반복되는 일은 PDF를 읽는 한 번의 작업보다, 읽은 값이 어떤 업무 관계에 놓이는지 확인하는 과정에 가까웠습니다. 금액 검산은 코드가 맡고, 결제 관계는 후보와 근거를 보여주며, 사용자 판단을 거친 초안은 저장 후 다시 읽습니다. 이 경계를 유지하는 것이 현재 구현의 핵심입니다.

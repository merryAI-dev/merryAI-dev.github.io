세금계산서가 도착했다고 해서 새로 돈을 지급해야 하는 것은 아닙니다. 이미 카드로 결제한 서비스의 증빙일 수도 있고, 아직 지급하지 않은 청구 건일 수도 있습니다. 같은 PDF에서 금액을 정확히 읽었더라도 이 관계를 구분하지 못하면 다른 지출결의 초안이 만들어집니다.

[앞선 글](/posts/amaranth-expense-skill/)에서는 기존 CLI를 Claude Code Skill로 연결한 카드 지출결의 구조를 소개했습니다. 이번에는 별도 모듈인 `taxinvoice.py`를 중심으로 증빙을 읽고 기존 문서와 대조하는 과정을 살펴봅니다. 카드 양식은 1211, 세금계산서·계산서에 사용하는 양식은 1210입니다. 저장 단계의 구조는 공유하지만, 두 양식에서 확인해야 할 업무 의미는 다릅니다.

이 글의 근거는 2026년 10월 17일 확인한 소스·테스트·변경 이력과 기존 로컬 작업 기록입니다. 예시 회사와 금액·날짜는 모두 합성 값입니다. 원본 세금계산서, 실제 거래처 정보, 계좌, 승인번호와 비공개 결제 자료는 공개하지 않았습니다. 검증된 실행 범위는 임시보관까지이며 상신·결재·지급 완료 사례를 뜻하지 않습니다.

## 메일, 증빙, 결의서는 서로 다른 상태를 알려줍니다

Skill에는 지출결의를 시작할 때 세금계산서 메일을 확인하는 절차가 있습니다. 이때 ‘안 읽은 메일’만 확인해서는 미처리 증빙을 찾을 수 없습니다. 이미 메일을 열었어도 결의서를 만들지 않았을 수 있기 때문입니다. 처리 여부를 판단하려면 기존 1210 문서와 대조해야 합니다.

역할도 구분했습니다. 메일은 발행 안내를 찾는 출발점이고, 금액과 승인번호의 대조 근거는 PDF입니다. Skill에서 다루는 열람 링크 안내 메일만으로 금액을 확정하지 않도록 되어 있습니다. 이것이 모든 세금계산서 메일에 금액이 없다는 일반적인 주장은 아닙니다.

또한 Gmail 조회는 연결된 커넥터를 Claude가 사용하는 절차입니다. Python CLI에 메일함을 감시하는 기능이 들어 있는 것은 아닙니다. **지출결의 연동 자체는 MCP 서버 없이 CLI로 구현했고, 선택적인 메일 확인은 별도 커넥터에 의존합니다.** 이번에는 Gmail 실행 기록을 독립적으로 재검증하지 않았으므로 자동 알림 서비스가 운영 검증됐다고 설명하지 않습니다.

## 금액을 추정하지 않고 PDF의 항목을 읽습니다

`read_invoice`는 `pdftotext -layout`으로 텍스트를 얻고, `parse_invoice`가 지원하는 홈택스 표준 서식에서 작성일자·공급가액·세액·합계·승인번호·상호와 등록번호를 읽습니다. 전자계산서는 세액을 0으로 처리합니다. 합계만 보고 부가세를 역산하지 않는 이유는 원본이 이미 공급가액과 세액을 구분해 주기 때문입니다.

예를 들어 합성 PDF에 공급가액 100,000원, 세액 10,000원, 합계 110,000원이 적혀 있다면 이 세 값을 각각 읽고 덧셈이 맞는지 검사합니다. 합계가 110,100원이라면 부족한 100원을 임의의 칸에 넣지 않고 중단합니다.

승인번호 앞부분의 날짜와 작성일자가 일치하는지도 검사합니다. 이것은 현재 파서가 채택한 지원 조건입니다. 날짜가 다르다는 이유만으로 해당 증빙이 법적으로 잘못됐다고 판정하는 기능은 아닙니다. 지원하는 패턴 밖의 증빙은 자동 처리에서 멈추고 사람이 확인해야 합니다.

스캔본을 읽는 OCR은 없고, 음수 금액과 코드에서 식별하는 수정 사유도 거절합니다. 수정세금계산서 전반, 표준 밖 서식, 원천징수 대상 외부인건비까지 처리하는 범용 세무 엔진은 아닙니다. 문서의 종류를 넓히는 것보다 읽지 못한 값을 그럴듯하게 채우지 않는 쪽으로 범위를 정했습니다.

## 영수와 청구에 따라 필요한 정보가 달라집니다

검토안은 PDF의 `[영수]`와 `[청구]` 표시를 보고 인식용 `recognition`과 지급요청용 `payment`를 제안합니다. 표시가 불분명하거나 여러 PDF가 섞여 하나로 정할 수 없으면 질문을 남깁니다. 사용자가 방식을 바꾸면 원본 표시와 다르다는 경고를 보관합니다.

| 확인 항목 | 인식용 초안 | 지급요청용 초안 |
|---|---|---|
| 업무 전제 | 이미 결제한 건의 회계 인식 | 거래처에 지급할 건의 결의 준비 |
| 결제일 | 카드 후보 또는 확인된 결제일 필요 | 카드 결제 후보를 요구하지 않음 |
| 수취 정보 | 승인된 이전 문서의 회사 계좌 근거 | 같은 거래처의 승인된 이전 지급 계좌 근거 |
| 출금계좌 안내 | 비우도록 안내 | 입력을 필수로 요구 |
| 실행의 끝 | 임시보관 | 임시보관 |

여기서 `payment`는 지급 실행 명령이 아닙니다. 지급할 건의 결의 초안을 만드는 모드입니다. 어떤 모드를 선택해도 도구가 상신하거나 계좌이체를 실행하지는 않습니다. 또한 이 구분과 계좌 배치는 MYSC에서 확인한 업무 흐름을 반영한 것으로, 다른 조직에 그대로 적용할 회계 처리 지침은 아닙니다.

‘인식용이면 출금계좌가 절대로 들어가지 않는다’고 설명하는 것도 정확하지 않습니다. Skill은 비우도록 안내하지만, 코드에서는 인식용에 출금계좌를 넣으면 경고를 남깁니다. 지급요청에서 출금계좌가 없는 경우의 저장 차단과는 강도가 다릅니다. 업무 안내와 강제 검증을 구분해야 실제 보호 범위를 알 수 있습니다.

## 카드 결제는 같은 금액의 후보부터 찾습니다

이미 결제한 세금계산서라면 해당 결제와의 관계를 확인해야 합니다. 현재 구현은 개인 프로필에 지정된 카드에서 **작성일부터 31일 안의 미반영 거래 중 합계가 같은 것**을 찾습니다. 후보가 하나면 그 날짜를 결제일로 제안하고, 없거나 여러 개면 결제일을 묻습니다. 이체로 결제했다면 그 사실과 날짜를 따로 지정할 수 있습니다.

이 방식에는 명확한 한계가 있습니다. 후보 검색 함수는 카드 가맹점과 PDF 공급자의 동일성을 강하게 검증하지 않습니다. 기간과 금액이 같은 다른 거래가 하나만 남아도 후보가 될 수 있습니다. 이미 카드 결의에 반영된 거래는 검색 범위에서 빠질 수도 있습니다. 따라서 ‘동일 결제 검증 완료’보다 ‘동일 금액의 결제 후보를 제안’한다고 표현하는 편이 맞습니다.

Skill은 저장 직전에 공급자·날짜·금액·비고·첨부를 한 번에 보여주고 확인받도록 합니다. 이 단계에서 사용자가 실제 결제 관계를 살펴야 합니다. 카드 결제와 관계가 있다는 이유로 해당 거래를 카드 결의에서 자동 제외하지도 않습니다. 두 양식의 회계상 처리 관계는 재경 검토에 남깁니다.

## 기존 결의 중복과 회사 확인도 범위를 밝혀야 합니다

같은 증빙을 다시 올리지 않기 위해 두 종류의 정보를 사용합니다. 로컬 작업 기록은 승인번호를 기준으로 저장 시도를 구분하고, 기존 1210 문서 조회는 증빙일·합계·거래처를 비교합니다. ERP 행에 승인번호가 저장되지 않기 때문에 서버 문서 비교에서는 대체 조건이 필요합니다. 승인번호는 비고에도 남기도록 되어 있습니다.

조회 기간은 가장 이른 증빙 작성일에서 366일 전부터 현재까지입니다. 조회한 문서 중 같은 증빙일·합계에 공급자 상호도 맞는 후보가 있으면 차단하고, 반려 문서는 참고 경고로 남깁니다. 상호가 비어 있으면 날짜와 금액이 같은 문서가 넓게 후보로 잡힐 수 있습니다. 전사·전기간의 중복을 승인번호로 완벽하게 판별하는 것은 아닙니다.

회사 확인도 비슷합니다. 파서는 공급받는자의 등록번호를 추출하지만, 검토안에서 회사와 비교하는 것은 **상호 문자열**입니다. `same_party`는 법인 표기와 공백 등을 정리하고 일치 또는 포함 관계를 검사합니다. 사업자등록번호의 정확한 일치나 외부 기관 조회를 수행하는 검증과는 다릅니다. 비슷한 상호를 구분해야 하는 사례에는 추가 확인이 필요합니다.

이 한계를 숨기지 않는 이유는 검증이라는 단어가 너무 넓기 때문입니다. 공급가액과 세액의 덧셈은 결정적으로 확인할 수 있지만, 이름의 포함 관계는 동일 법인임을 보증하지 못합니다. 두 검사를 같은 확신 수준으로 사용자에게 설명해서는 안 됩니다.

## 과거 문서에서 재사용할 값과 다시 물을 값을 나눴습니다

같은 거래처의 승인된 1210 문서에서 적요·용도·프로젝트를 제안합니다. 인식용이고 카드 결제 후보가 있으면 해당 가맹점의 승인된 카드 결의 적요를 먼저 참고해 두 양식의 표현을 맞춥니다. 가장 많이 쓴 표현을 제안하되 동률이면 질문하고, 다른 표현이 있으면 참고 정보로 보여줍니다.

이 정책은 앞선 카드 글의 이력 충돌 처리와 같지 않습니다. 카드 경로는 서로 다른 선택을 질문으로 남기지만, 세금계산서의 카드 적요 제안은 최빈값과 동률 여부를 사용합니다. 공통 Skill 아래에 있다고 해서 두 모듈의 판단 기준까지 같다고 가정하면 안 됩니다.

처음 보는 거래처에서는 사용자 확인이 필요하다고 Skill이 지시합니다. 다만 구현에는 용도의 기본 코드와 프로필의 기본 프로젝트를 채우는 경로도 있습니다. 따라서 ‘이력이 없으면 모든 값이 반드시 빈칸이고 저장이 항상 막힌다’는 설명은 맞지 않습니다. 누락 항목을 막는 코드 검사와, 제안값을 사용자에게 확인받는 대화 절차가 함께 필요합니다.

반면 수취 계좌는 임의의 새 값을 입력받는 경로를 두지 않았습니다. 사용할 수 있는 승인 문서가 없으면 첫 건은 그룹웨어에서 직접 작성하도록 막습니다. 과거 승인 계좌가 현재도 유효한지는 별도로 검토해야 하며, 과거에 승인됐다는 사실만으로 이후 변경 가능성이 사라지는 것은 아닙니다.

## 실제 수정 이력에서 나온 두 가지 검증

개발 이력에는 증빙일자와 수취 계좌 처리에 대한 수정이 남아 있습니다. 둘 다 화면에 값이 보인다는 사실만으로 올바른 입력이라고 볼 수 없었던 지점입니다.

첫째, 증빙일자는 PDF의 작성일자로 고정합니다. 결제일이나 메일 수신일로 바꾸지 못하도록 저장 전 `validate`에서도 대조합니다. 회계일은 기본적으로 작성일자를 사용하지만 다른 날짜를 지정할 수 있으며, 같은 해의 다른 날이면 경고, 다른 해이면 차단합니다. 날짜의 이름이 비슷해도 각 필드가 뜻하는 사건은 다릅니다.

둘째, 조회 화면용 계좌 표시값과 실제 저장에 필요한 값을 구분했습니다. 변경 이력에는 마스킹된 표시값을 전송하지 않고 승인 문서의 숫자 계좌값을 사용하도록 고친 내용이 있습니다. 현재 코드는 입력값이 숫자 형식인지 검사하고, 저장 후에도 다시 읽은 계좌값이 검토안의 값과 같은지 비교합니다. 이 글에는 그 필드의 실제 값이나 화면을 싣지 않았습니다.

이 수정에서 얻을 수 있는 교훈은 과거 문서를 그대로 복사하면 안전하다는 것이 아닙니다. 조회 API가 반환한 값 중에는 표시용 표현이 있고 저장용 값이 있습니다. 재사용할 필드의 의미를 확인하고, 실제 저장 결과까지 대조해야 합니다.

## 저장 후 재조회까지가 하나의 처리 루프입니다

*그림 1. 확정 계산, 후보 제안, 사용자 판단을 구분한 처리 흐름입니다. [Mermaid 원본](/assets/images/diagrams/jichool/02-tax-loop.mmd)*

`prepare`는 검토안과 질문을 만들고, `check`는 저장 직전 조건을 다시 확인합니다. PDF를 다시 읽어 검토 후 변경되지 않았는지 확인하고, 첨부 해시, 로그인 계정, 중복 후보, 마감일, 현재 사용 가능한 용도를 검사합니다. Skill은 이 검사와 별도로 최종 내용을 보여주고 임시보관 요청을 받도록 합니다.

저장 후 `verify_tax`는 ERP의 합계·공급가액·세액·증빙일·지급요청일·용도·적요·프로젝트 등 주요 필드를 검토안과 비교합니다. 이어 전자결재 임시보관 상태, 본문의 비고 문장, 첨부 개수와 식별자, 다운로드한 PDF의 해시를 확인합니다. 본문의 모든 시각적 배치를 검증하는 것은 아니며, 비고 포함 검사와 ERP 값 대조를 구분해서 이해해야 합니다.

중간 실패는 단계별 작업 기록으로 남깁니다. 결과가 불명확한 업로드·연결키·ERP 쓰기는 자동 재전송하지 않습니다. 전자결재 저장 응답이 유실된 경우에는 연결된 문서를 조회해 이미 저장됐는지 확인합니다. 기존 기록이 있으면 같은 `draft` 호출에서 재개 경로를 타며, 카드 모듈의 별도 `resume` 명령과 사용 방식이 다릅니다.

재조회에서 값이 다르면 성공으로 마무리하지 않습니다. Skill은 무엇이 다른지 알리고, 사용자가 그룹웨어에서 임시보관 문서를 삭제한 경우에만 서버 삭제 상태를 확인해 기록을 보관 처리한 뒤 다시 준비하도록 안내합니다. 불확실한 문서를 자동으로 덮어쓰는 복구는 하지 않습니다.

## 테스트와 작업 기록이 말해 주는 범위

이번 확인에서는 네트워크를 차단하고 합성 입력과 가짜 클라이언트를 사용하는 기본 테스트를 실행했습니다. 세금계산서·계산서 파싱, 금액 불일치와 음수 차단, 중복·회사명·연도·용도 검사, 본문 생성과 HTML 이스케이프, 양식 변경 차단이 통과했습니다. 저장 순서와 재실행 시 추가 쓰기 없음, 불명확한 단계의 재전송 차단, 전자결재 응답 유실 복구도 가짜 서버 응답으로 확인했습니다.

파서 테스트 통과는 지원 서식의 텍스트 해석을 검증한 결과입니다. 모든 발행처 PDF나 실제 금융기관 처리 결과를 검증한 것은 아닙니다. 회사명 비교와 카드 후보 매칭의 한계 역시 테스트 통과만으로 없어지지 않습니다.

기존 로컬 세금계산서 작업 기록에는 `verified` 상태와 문서 식별자, 첨부 검증 결과가 남아 있었습니다. 이를 과거 임시보관 검증의 증거로 확인했고, 실제 거래 내용은 공개 자료에 옮기지 않았습니다. 현재 서버 상태를 재조회하거나 신규 저장을 실행한 것은 아닙니다. 최종 상신과 결재·지급이 이 도구로 검증됐다는 주장은 하지 않습니다.

세금계산서 처리에서 반복되는 일은 PDF를 읽는 한 번의 작업보다, 읽은 값이 어떤 업무 관계에 놓이는지 확인하는 과정에 가까웠습니다. 금액 검산은 코드가 맡고, 결제 관계는 후보와 근거를 보여주며, 사용자 판단을 거친 초안은 저장 후 다시 읽습니다. 이 경계를 유지하는 것이 현재 구현의 핵심입니다.

<p>안녕하세요. MYSCube를 만들고 있는 MYSC AXR팀입니다.</p>
<p><strong>MYSCube는 MYSC가 자체 개발한 내부 ERP입니다.</strong> 프로젝트, 예산, 지출, 정산, 현금흐름처럼 조직 운영에 필요한 데이터를 하나의 흐름으로 연결하고 있습니다.</p>
<p>지난 글에서는 구글 시트의 셀을 그대로 데이터베이스에 복사하지 않고, 그 안에 담긴 업무의 의미를 시스템의 언어로 옮긴 과정을 소개했습니다. 시트의 위치는 바뀔 수 있지만 “어느 프로젝트의 몇 월 몇 주차 입금인가”라는 의미는 남아야 했기 때문입니다.</p>
<p>그다음 문제는 더 까다로웠습니다.</p>
<blockquote>
<p>시트에서 숫자를 잘 읽어 왔다면, 그 숫자는 믿어도 되는가?</p>
</blockquote>
<p>처음에는 시트의 오늘 값을 불러와 내부 ERP에 저장하면 될 것처럼 보였습니다. 그러나 셀에 표시된 숫자는 계산의 결과일 뿐, 그 계산이 업무 규칙에 맞았다는 보증은 아니었습니다. 수식이 지워지고 숫자만 남을 수도 있고, 합계 셀이 비어 있을 수도 있습니다. 앞 주의 잔액이 잘못되면 다음 주부터 오류가 연쇄적으로 이어질 수도 있습니다.</p>
<p>그래서 이번에는 값을 <em>가져오는 일</em>과 값이 <em>맞는지 판단하는 일</em>을 분리했습니다. 구글 시트에 가까운 BFF는 셀의 위치와 상태를 업무 데이터로 번역하고, JVM 서버는 같은 입력으로 입금·출금·잔액을 다시 계산합니다. 이 글은 두 서버의 역할을 나누고, 시트의 숫자를 내부 ERP에 반영하기 전에 독립적으로 검증하게 된 과정에 관한 이야기입니다.</p>

<h2>비어 있는 합계 셀에서 시작된 질문</h2>

<p>입금 항목을 모두 더하면 결과는 0원이었습니다. 하지만 시트의 합계 셀은 비어 있었습니다.</p>

<p><code>BL22</code>의 빈칸은 작은 차이였지만, 시스템이 숫자만 저장해서는 안 된다는 사실을 보여주었습니다. 값뿐 아니라 그 값이 어떤 상태에서 만들어졌는지까지 남겨야 했습니다.</p>

<h2>가져오는 서버와 판단하는 서버를 나누다</h2>
<p>시트 계산을 다시 확인하기로 한 뒤에는 “어디에서 계산할 것인가”를 정해야 했습니다.</p>
<p>브라우저에서 다시 계산하는 방식은 빠르게 만들 수 있지만, 화면마다 같은 규칙이 반복됩니다. 화면을 거치지 않는 저장 요청에는 규칙을 강제할 수도 없습니다.</p>
<p>BFF에서 모든 계산을 끝내는 방법도 있었습니다. BFF는 <strong>Backend for Frontend</strong>의 약자로, 화면과 외부 서비스를 이어 주는 중간 서버입니다. 구글 시트와 가장 가까운 곳에 있어 셀을 읽고 합계를 내기에는 편리합니다.</p>
<p>하지만 BFF가 시트 구조 해석과 재무 계산의 최종 판단을 모두 맡으면 책임이 섞입니다. 시트의 열이 바뀌는 문제와 잔액 규칙이 바뀌는 문제가 같은 코드에서 충돌하고, 다른 저장 경로가 생기면 공식 계산 규칙이 둘로 갈라질 수 있습니다.</p>
<p>그래서 역할을 다음과 같이 나눴습니다.</p>
<ul>
<li><strong>BFF는 번역합니다.</strong> 구글 시트의 셀 주소, 주차, 예측값과 실적값, 빈칸과 0원을 내부 서버가 이해할 수 있는 형태로 정리합니다.</li>
<li><strong>JVM 서버는 판단합니다.</strong> 입금 합계, 출금 합계, 이전 기간에서 이어지는 잔액을 다시 계산하고 시트의 표시값과 비교합니다.</li>
<li><strong>화면은 설명합니다.</strong> 계산이 다르면 어느 셀의 현재값과 기대값이 다른지 사람이 이해할 수 있게 보여줍니다.</li>
</ul>
<p>JVM은 <strong>Java Virtual Machine</strong>의 약자로, 자바 프로그램을 실행하는 환경입니다. MYSCube에서는 JVM 위에서 동작하는 Spring Boot 서버가 재무 계산과 저장 규칙을 맡습니다. Spring Boot는 자바로 서버를 만드는 개발 도구입니다.</p>
<p><img src="/assets/images/diagrams/building-ledger-02/bff-jvm-role-separation.png" alt="구글 시트 값을 BFF가 구조화하고 JVM이 독립 계산한 뒤 Firestore에 반영하거나 사람에게 차이를 보여주는 구조" /></p>
<p><em>그림 1. BFF는 시트의 위치와 상태를 번역하고, JVM은 계산이 맞는지 독립적으로 판단합니다.</em></p>
<p>이 구분에서 가장 중요했던 것은 <mark>BFF가 숫자의 옳고 그름을 최종 결정하지 않는다는 것</mark>이었습니다. BFF는 시트를 잘 읽는 데 집중하고, JVM은 어느 화면이나 저장 경로에서도 같은 계산 규칙이 적용되도록 책임집니다.</p>

<h2>BFF는 셀 주소를 업무의 언어로 바꾼다</h2>
<p>구글 시트에서는 <code>BL22</code>처럼 위치가 곧 의미입니다. 하지만 내부 ERP가 셀 주소를 그대로 저장하면 열 하나가 이동할 때마다 시스템의 의미도 흔들립니다.</p>
<p>BFF는 물리적인 셀 위치를 다음과 같은 업무 정보로 바꿉니다.</p>
<pre><code>{
  "기간": "2026년 12월 5주차",
  "구분": "예측값",
  "항목": "입금 합계",
  "셀 상태": "비어 있음",
  "금액": 0,
  "원본 셀": "BL22"
}
</code></pre>
<p>이때 원본 셀 주소도 버리지 않습니다. 내부에서는 “2026년 12월 5주차의 예측 입금 합계”로 다루되, 문제가 생겼을 때 사용자가 시트의 어느 자리를 확인해야 하는지 다시 알려주기 위해서입니다.</p>
<p>BFF는 연동하기로 한 고정 범위를 읽고, 연도와 주차, 입금과 출금 항목, 빈칸과 오류 상태를 구분합니다. 사용자가 검토한 뒤 시트가 바뀌지 않았는지도 확인합니다. 그러나 합계와 잔액이 업무 규칙에 맞는지에 대한 최종 판단은 다음 단계인 JVM에 넘깁니다.</p>

<h2>JVM은 시트의 수식을 복제하지 않는다</h2>
<p>JVM 검증기를 만든다고 해서 엑셀이나 구글 시트의 모든 수식을 다시 구현한 것은 아닙니다. 범위가 지나치게 크기도 하지만, 우리의 문제를 해결하는 데 필요하지 않았습니다.</p>
<p>대신 내부 현금흐름에서 반드시 맞아야 하는 고정 계산만 코드로 옮겼습니다.</p>
<ul>
<li>예측값과 실적값의 입금 합계</li>
<li>예측값과 실적값의 출금 합계</li>
<li>직전 기간 잔액을 이어받는 누적 잔액</li>
<li>이전 연도의 입출금에서 계산한 시작 잔액</li>
<li>연간 입금 합계·출금 합계·잔액</li>
</ul>
<p>한 주의 계산은 단순합니다. 입금 항목 7개와 출금 항목 9개를 각각 더하고, 직전 주의 잔액에 입금을 더한 뒤 출금을 뺍니다.</p>
<pre><code>이번 주 잔액 = 직전 주 잔액 + 입금 합계 - 출금 합계
</code></pre>
<p>어려운 부분은 산식이 아니라 “직전 주 잔액을 어디에서 가져올 것인가”였습니다.</p>
<p>시트에 표시된 직전 잔액을 그대로 다음 계산의 출발점으로 쓰면, 앞 주의 오류가 뒤로 계속 전파됩니다. 이후 숫자는 서로 이어져 있어 겉으로는 맞아 보일 수도 있습니다.</p>
<p>그래서 JVM은 시트에 표시된 잔액을 이어 쓰지 않습니다. JVM이 직접 계산한 이전 기간의 잔액을 다음 기간의 시작값으로 사용합니다. 시트의 숫자는 비교 대상이지, 다음 계산을 믿게 만드는 근거가 아닙니다.</p>
<p><img src="/assets/images/diagrams/building-ledger-02/jvm-independent-calculation.png" alt="JVM이 입금 7개와 출금 9개를 더하고 자체 계산 잔액을 다음 기간으로 넘겨 시트 표시값과 비교하는 흐름" /></p>
<p><em>그림 2. JVM은 자신이 계산한 잔액을 다음 기간으로 넘겨, 차이가 처음 생긴 지점을 찾습니다.</em></p>
<p>연도가 바뀔 때도 같은 원칙을 적용했습니다. 이전 연도의 원천 입출금을 JVM이 다시 합산하고, 그 결과를 새해 첫 주의 시작 잔액으로 사용합니다. 연간 잔액 셀에 보이는 숫자는 계산의 출발점이 아니라 검증할 대상입니다.</p>
<blockquote>
<p>구글 시트를 다시 만드는 것이 아니라, 우리 업무에서 반드시 지켜야 하는 계산만 시스템의 규칙으로 고정한다.</p>
</blockquote>

<h2>저장하기 전에 한 번 더 계산한다</h2>
<p>검증 결과가 저장 뒤에 경고로만 남는다면 이미 늦을 수 있습니다. 그래서 JVM의 계산은 내부 ERP에 반영하기 전에 실행됩니다.</p>
<ol>
<li>사용자가 구글 시트의 값을 불러옵니다.</li>
<li>BFF가 셀의 위치와 상태를 업무 데이터로 정리합니다.</li>
<li>사용자가 반영을 누르면 BFF가 같은 값 묶음을 JVM에 보냅니다.</li>
<li>JVM이 입금·출금·잔액을 다시 계산해 시트 표시값과 비교합니다.</li>
<li>값이 다르면 저장을 잠시 멈추고 셀 주소·현재값·기대값을 돌려줍니다.</li>
</ol>
<p><img src="/assets/images/diagrams/building-ledger-02/formula-preflight-review.png" alt="시트 값을 BFF가 검토용으로 고정하고 JVM이 반영 전에 계산한 뒤 차이가 있으면 사람이 확인하는 흐름" /></p>
<p><em>그림 3. 계산이 다르면 자동으로 고치지 않고, 사람이 원본과 기대값을 함께 확인합니다.</em></p>
<p><code>BL22</code>에서 차이가 발견되면 사용자는 다음과 같은 설명을 보게 됩니다.</p>
<blockquote>
<p><strong>2026년 12월 5주차 · 예측값 · 입금 합계</strong><br />
<strong>BL22 셀</strong>은 해당 기간의 입금 항목을 모두 더한 값입니다.<br />
시트에는 <strong>0원</strong>이 표시되어야 합니다.<br />
현재 시트에는 이 값이 비어 있습니다.</p>
</blockquote>
<p>시스템은 이 빈칸을 몰래 0원으로 바꾸지 않습니다. 사용자는 시트를 수정한 뒤 다시 불러오거나, 차이를 이해한 상태에서 현재 원천 항목을 반영할 수 있습니다. 계산은 시스템이 하지만, 예외를 해석하고 승인하는 책임까지 시스템이 대신하지는 않습니다.</p>

<h2>검토하는 동안 값이 바뀐다면</h2>
<p>사용자가 차이를 확인하는 사이에도 시트나 내부 ERP의 값은 바뀔 수 있습니다. 따라서 확인 버튼을 눌렀다는 사실만으로 저장을 허용해서는 안 됩니다.</p>
<p>MYSCube는 사용자가 검토한 시트와 내부 ERP 값의 판본을 함께 확인합니다. 검토 뒤 어느 한쪽이라도 달라졌다면 최신 값을 다시 불러오게 합니다. 같은 반영 요청이 네트워크 문제로 두 번 도착해도 재무 변경은 한 번만 처리합니다.</p>
<p>같은 요청을 여러 번 보내도 결과가 한 번 처리한 것과 같아야 하는 성질을 기술적으로는 <strong>멱등성(idempotency)</strong>이라고 부릅니다. 사용자가 기다리다 버튼을 다시 누르더라도 같은 기록이 두 번 만들어지지 않게 하는 장치입니다.</p>
<p>저장이 끝난 뒤에도 성공 응답만 믿지 않습니다. 실제 저장소인 Firestore를 다시 읽어 요청한 프로젝트와 항목 수, 새 판본이 맞는지 확인합니다. Firestore는 구글이 제공하는 문서형 데이터베이스입니다.</p>

<h2>역할을 나눴다고 끝난 것은 아니었다</h2>
<p>BFF와 JVM의 책임을 나누면 계산 규칙은 선명해집니다. 대신 두 서버 사이의 통신이 새로운 경계가 됩니다.</p>
<p>점검 과정에서는 브라우저가 기다리는 시간보다 서버의 재시도 시간이 더 길거나, JVM의 구체적인 오류가 BFF를 지나며 하나의 일반 문구로 바뀌는 문제를 발견했습니다. 쓰기에 필요한 정보가 자바스크립트 객체를 옮기는 과정에서 빠지는 경로도 있었습니다.</p>
<p>이를 계기로 서버를 나누는 것만큼 두 서버가 주고받는 약속을 관리하는 일이 중요하다는 것을 다시 확인했습니다. 변경 요청은 함부로 재시도하지 않고, 오류의 종류와 원인을 끝까지 보존했습니다. 누가 어떤 변경을 실행할 수 있는지도 JVM의 권한 규칙을 기준으로 맞췄습니다.</p>
<p>JVM을 둔 이유는 자바가 덧셈을 더 잘해서가 아닙니다. <mark>재무 계산과 저장 권한을 한곳에서 지키고, 그 규칙을 실제 저장 결과까지 포함해 반복해서 검증할 수 있기 때문</mark>입니다.</p>

<h2>우리가 확인한 것과 아직 남은 것</h2>
<p>정상적인 숫자 하나를 더해 보는 것만으로는 계산 검증을 끝낼 수 없었습니다. 입금 7개와 출금 9개의 합계, 이전 연도에서 이어지는 첫 잔액, 빈칸과 명시적인 0원, 음수 정정 금액, 잘못된 소수 금액, 중복된 셀과 누락된 항목을 각각 확인했습니다. 시트 잔액이 틀려도 JVM의 계산 잔액으로 다음 기간이 이어지는지도 검증했습니다.</p>
<p>물론 현재 구조에도 한계는 있습니다. 모든 구글 시트 수식을 해석하는 범용 계산기가 아니라, 현금흐름 탭의 고정된 합계와 잔액 규칙만 검증합니다. BFF에는 기존 화면을 위한 비교 계산이 일부 남아 있어, JVM 결과와 충분히 대조한 뒤 정리해야 합니다. 계산 결과의 판본을 월결산의 최종 차단 조건과 연결하는 작업도 남아 있습니다.</p>
<p>그럼에도 이 단계에서 얻은 변화는 분명했습니다. 시스템이 시트의 숫자를 조용히 복사하는 대신, “이 값은 우리가 다시 계산한 결과와 다르다”고 말할 수 있게 되었습니다. 그리고 어느 셀을 왜 확인해야 하는지 사람에게 설명할 수 있게 되었습니다.</p>

<h2>정리</h2>
<p>구글 시트 연동의 다음 단계는 더 많은 셀을 읽는 일이 아니었습니다. 읽어 온 숫자를 어떤 근거로 믿을지 정하는 일이었습니다.</p>
<p>MYSCube는 구글 시트와 내부 ERP 사이의 역할을 다음처럼 나눴습니다.</p>
<ul>
<li>구글 시트는 사용자가 익숙하게 입력하고 확인하는 화면입니다.</li>
<li>BFF는 셀의 위치와 상태를 업무의 언어로 번역합니다.</li>
<li>JVM은 입금·출금·잔액을 독립적으로 계산하고 저장 가능 여부를 판단합니다.</li>
<li>프론트엔드는 계산하지 않고 사람이 판단할 수 있는 근거를 보여줍니다.</li>
</ul>
<p>이 구조의 목적은 사람의 판단을 없애는 것이 아니었습니다. 반복할 수 있는 계산은 시스템이 책임지고, 예외를 해석하고 승인하는 일은 사람이 근거를 보고 결정하도록 만드는 것이었습니다.</p>
<p>그런데 계산이 맞는 값을 저장한 뒤에도 또 다른 문제가 남았습니다. 주정산을 마쳤다고 표시한 뒤 원천 데이터가 수정되면, 이미 확인한 숫자는 어떻게 다뤄야 할까요? “확인 완료”와 “최종 확정”은 같은 상태일까요?</p>
<p>다음 글에서는 주정산을 마친 뒤 숫자가 다시 바뀐 상황을 출발점으로, 주간 확인과 월결산의 경계를 어떻게 나누었는지 소개하겠습니다.</p>

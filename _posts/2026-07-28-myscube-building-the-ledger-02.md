<p>안녕하세요. MYSCube를 만들고 있는 MYSC AXR팀입니다.</p>
<p><strong>MYSCube는 MYSC가 자체 개발한 내부 ERP입니다.</strong> 프로젝트, 예산, 지출, 정산, 현금흐름처럼 조직 운영에 필요한 데이터를 하나의 흐름으로 연결하고 있습니다.</p>
<p>지난 글에서는 구글 시트의 셀을 그대로 데이터베이스에 복사하지 않고, 프로젝트·주차·현금흐름 항목이라는 업무 의미로 바꾼 과정을 소개했습니다. 이번에는 그 과정에서 왜 하나가 아닌 <strong>두 개의 백엔드</strong>가 필요했는지 이야기해 보겠습니다.</p>
<p>백엔드는 사용자가 보는 화면 뒤에서 데이터를 읽고 계산하고 저장하는 서버입니다. MYSCube의 구글 시트 연동에는 서로 다른 책임을 가진 두 백엔드가 있습니다.</p>
<ul>
<li><strong>Express BFF</strong>는 구글 시트와 화면 사이를 잇습니다. BFF는 <code>Backend for Frontend</code>의 약자로, 화면에 필요한 데이터를 모아 알맞은 형태로 전달하는 중간 서버입니다. <code>BL22</code> 같은 셀 주소를 “2026년 12월 5주차의 예측 입금 합계”라는 업무 정보로 바꾸고, 빈칸·0원·오류처럼 셀의 상태도 함께 정리합니다.</li>
<li><strong>Spring Boot 기반 JVM 서버</strong>는 계산과 저장의 기준을 지킵니다. JVM은 <code>Java Virtual Machine</code>의 약자로, 자바 프로그램을 실행하는 환경입니다. 이 서버는 BFF가 전달한 입금과 출금 항목으로 합계와 잔액을 다시 계산하고, 시트의 숫자를 내부 ERP에 반영해도 되는지 판단합니다.</li>
</ul>
<p>두 서버를 둔 이유는 시트를 <em>잘 읽는 책임</em>과 재무 숫자가 <em>맞다고 판단하는 책임</em>을 분리하기 위해서였습니다. 외부 시트의 열이나 셀 위치가 바뀌는 일은 BFF가 다루고, 입금·출금·잔액의 계산 규칙은 JVM 서버 한곳에서 지키도록 했습니다.</p>
<p>시트에서 값을 잘 읽어 왔다면 그 숫자를 내부 ERP에 저장해도 될까요?</p>
<p>처음에는 그렇게 생각했습니다. 하지만 시트에 표시된 숫자는 계산 결과일 뿐, 그 계산이 업무 규칙에 맞았다는 보증은 아니었습니다. 수식이 지워지고 숫자만 남을 수도 있고, 합계 셀이 비어 있을 수도 있습니다. 앞 주의 잔액이 잘못되면 다음 주부터는 오류가 연쇄적으로 이어집니다.</p>
<p>2026년 12월 5주차 입금 합계가 들어가는 <code>BL22</code> 셀이 실제 사례였습니다. 입금 항목을 모두 더하면 0원이 나와야 했지만 시트에는 값이 비어 있었습니다.</p>
<blockquote>
<p>시트 값을 읽는 것과 시트 계산을 믿는 것은 다른 문제다.</p>
</blockquote>
<p>그래서 MYSCube는 구글 시트의 값을 단순히 불러오는 데서 멈추지 않았습니다. BFF가 정리한 같은 입력을 JVM 서버가 다시 계산하고, 두 결과가 다르면 어느 셀에서 무엇이 어긋났는지 사람에게 보여주도록 만들었습니다.</p>

<h2>계산 검증을 어디에서 할 것인가</h2>
<p>시트 계산을 다시 확인하기로 한 뒤에는 어느 계층이 그 책임을 가져야 하는지 정해야 했습니다. 세 가지 선택지를 비교했습니다.</p>
<h3>1. 브라우저에서 다시 계산한다</h3>
<p>화면에서 입금과 출금을 더하면 구현은 빠릅니다. 하지만 화면마다 같은 계산을 반복하게 되고, 화면을 거치지 않는 저장 요청에는 같은 규칙을 강제할 수 없습니다. 사용자가 오래된 화면을 열어 둔 상태라면 서버의 규칙과 다른 계산을 할 수도 있습니다.</p>
<h3>2. BFF에서 계산하고 판단한다</h3>
<p>BFF는 화면이 쓰기 편한 형태로 여러 서비스의 응답을 조합하는 서버입니다. 구글 시트와 가장 가까운 곳에 있으므로 셀 위치를 읽고 합계를 계산하기에도 편합니다.</p>
<p>하지만 BFF가 시트 구조 해석과 재무 규칙의 최종 판단을 모두 맡으면 책임이 섞입니다. 시트 열이 바뀌는 문제와 잔액 계산 규칙이 바뀌는 문제가 같은 코드에서 충돌합니다. 또 다른 저장 경로가 BFF의 계산을 우회하면 공식 규칙이 둘로 갈라질 수 있습니다.</p>
<h3>3. BFF는 구조를 정리하고 JVM이 계산을 검증한다</h3>
<p>저희가 선택한 방식입니다.</p>
<ul>
<li>BFF는 구글 시트를 한 번 읽고, 셀 위치·주차·항목·상태를 내부 서버가 이해할 수 있는 형태로 정리합니다.</li>
<li>JVM 위의 Spring Boot 서버는 입금·출금·잔액을 독립적으로 계산합니다.</li>
<li>구글의 문서형 데이터베이스인 Firestore 반영과 변경 이력, 같은 요청을 두 번 보내도 한 번만 반영하는 규칙은 JVM이 책임집니다.</li>
<li>프론트엔드는 계산하지 않고 결과와 원본 셀 위치를 보여줍니다.</li>
</ul>
<p><img src="/assets/images/diagrams/building-ledger-02/bff-jvm-role-separation.png" alt="구글 시트 값을 BFF가 구조화하고 JVM이 독립 계산한 뒤 Firestore에 반영하거나 사람에게 차이를 보여주는 구조" /></p>
<p><em>그림 1. BFF는 시트의 위치와 상태를 정리하고, JVM은 계산의 최종 판단을 맡습니다.</em></p>

<h2>BFF는 계산기가 아니라 번역기다</h2>
<p>구글 시트는 셀 주소로 말합니다. <code>BL22</code>, <code>BL32</code>, <code>BL33</code>처럼 위치가 곧 의미입니다. 내부 ERP는 그렇게 저장하면 안 됩니다. 같은 의미의 셀이 다른 위치로 이동할 수 있기 때문입니다.</p>
<p>BFF는 셀을 다음과 같은 업무 정보로 바꿉니다.</p>
<pre><code>{
  "yearMonth": "2026-12",
  "weekNo": 5,
  "mode": "projection",
  "lineId": "TEAM_SUPPORT_IN",
  "state": "ZERO",
  "amount": 0,
  "sourceCell": "BL20"
}
</code></pre>
<p>이 과정에서 BFF가 맡는 일은 다음과 같습니다.</p>
<ul>
<li>연동하기로 한 고정 범위를 한 번 읽습니다.</li>
<li>예측값과 실적값, 연도와 주차, 입금과 출금 항목을 찾습니다.</li>
<li>빈칸·0원·금액·잘못된 값·시트 오류를 구분합니다.</li>
<li>사용자가 검토한 시점의 값과 현재 시트 판본이 같은지 확인합니다.</li>
<li>JVM이 돌려준 오류를 화면에서 이해할 수 있는 응답으로 바꿉니다.</li>
</ul>
<p>여기서 중요한 경계는 <mark>BFF가 숫자의 옳고 그름을 최종 결정하지 않는다는 것</mark>입니다. BFF 안에도 화면 미리보기와 이전 동작을 위한 비교 코드가 일부 남아 있지만, 저장을 허용할지 판단하는 계산은 JVM이 같은 입력으로 다시 수행합니다.</p>

<h2>JVM은 시트 수식을 실행하지 않는다</h2>
<p>JVM 검증기를 만든다고 해서 엑셀이나 구글 시트의 모든 수식을 구현한 것은 아닙니다. 그것은 범위가 지나치게 크고, 이 문제를 해결하는 데 필요하지도 않았습니다.</p>
<p>현재 검증 범위는 내부 현금흐름 탭의 고정된 계산 규칙입니다.</p>
<ul>
<li>예측값과 실적값 각각의 입금 합계</li>
<li>예측값과 실적값 각각의 출금 합계</li>
<li>직전 기간 잔액을 이어받는 누적 잔액</li>
<li>이전 연도의 입출금에서 계산한 시작 잔액</li>
<li>연간 입금 합계·출금 합계·잔액</li>
</ul>
<p>실적값의 원천에는 조건에 맞는 값만 골라 더하는 <code>SUMIFS</code> 수식도 있습니다. 대상 행 수는 매번 달라질 수 있습니다. JVM은 이 수식을 다시 구현하지 않습니다. 구글 시트가 계산한 각 실적 항목의 결과를 입력 근거로 받고, 그 아래의 고정된 합계와 잔액이 맞는지를 독립적으로 검증합니다.</p>
<blockquote>
<p>엑셀을 다시 만드는 것이 아니라, 우리 업무에서 반드시 지켜야 하는 계산만 코드로 고정한다.</p>
</blockquote>

<h2>시트 잔액을 다음 계산의 출발점으로 쓰지 않은 이유</h2>
<p>한 주의 계산은 단순합니다.</p>
<pre><code>입금 합계 = 입금 항목 7개의 합
출금 합계 = 출금 항목 9개의 합
이번 주 잔액 = 직전 주 잔액 + 입금 합계 - 출금 합계
</code></pre>
<p>문제는 “직전 주 잔액”을 어디에서 가져오느냐입니다. 시트에 표시된 직전 잔액을 그대로 다음 주 계산에 사용하면 앞 주의 오류가 뒤로 전파됩니다. 이후 주차는 모두 계산이 맞는 것처럼 보일 수도 있습니다.</p>
<p>JVM은 시트에 표시된 잔액을 다음 계산의 입력으로 쓰지 않습니다. 이전 기간에 JVM이 계산한 잔액을 다음 기간의 시작값으로 사용합니다. 덕분에 어느 기간에서 처음 차이가 발생했는지 찾을 수 있습니다.</p>
<p><img src="/assets/images/diagrams/building-ledger-02/jvm-independent-calculation.png" alt="JVM이 입금 7개와 출금 9개를 더하고 자체 계산 잔액을 다음 기간으로 넘겨 시트 표시값과 비교하는 흐름" /></p>
<p><em>그림 2. JVM은 시트 잔액을 이어 쓰지 않고 자체 계산 결과를 다음 기간으로 넘깁니다.</em></p>
<p>2026년 첫 주를 계산할 때도 같은 원칙을 적용했습니다. 2024년과 2025년의 원천 입출금 항목을 JVM이 다시 합산하고, 그 결과를 2026년 첫 주의 시작 잔액으로 사용합니다. 연간 잔액 셀에 표시된 숫자는 비교 대상일 뿐 계산의 출발점이 아닙니다.</p>
<p>금액은 모두 원 단위 정수로 계산합니다. 소수 금액이나 숫자로 해석할 수 없는 값은 반올림해 넘어가지 않고 잘못된 입력으로 거절합니다. 취소와 정정에 필요한 음수 금액은 허용합니다.</p>

<h2>저장 전에 JVM에 먼저 물어본다</h2>
<p>계산 검증은 저장이 끝난 뒤 경고를 남기는 기능이 아닙니다. 실제 반영 전에 실행되는 사전 검사입니다.</p>
<ol>
<li>사용자가 구글 시트 값을 불러옵니다.</li>
<li>BFF가 검토할 셀 값과 원본 판본, 현재 ERP 값의 판본을 함께 보관합니다.</li>
<li>사용자가 반영을 누르면 BFF가 같은 값 묶음을 JVM의 계산 검사 경로로 보냅니다.</li>
<li>JVM이 입금·출금·잔액을 다시 계산하고 시트 표시값과 비교합니다.</li>
<li>값이 다르면 반영을 잠시 멈추고 셀 주소·현재값·기대값을 반환합니다.</li>
</ol>
<p><img src="/assets/images/diagrams/building-ledger-02/formula-preflight-review.png" alt="시트 값을 BFF가 검토용으로 고정하고 JVM이 반영 전에 계산한 뒤 차이가 있으면 사람이 확인하는 흐름" /></p>
<p><em>그림 3. 계산이 다르면 자동 수정하지 않고 사람이 시트와 기대값을 함께 확인합니다.</em></p>
<p><code>BL22</code>의 경우 사용자는 다음 내용을 보게 됩니다.</p>
<blockquote>
<p><strong>2026년 12월 5주차 · 예측값(Projection) · 입금 합계</strong><br />
<strong>BL22 셀</strong>은 해당 기간의 입금 항목을 모두 더한 값입니다.<br />
시트에는 <strong>0원</strong>이 표시되어야 합니다.<br />
현재 시트에는 이 값이 비어 있습니다.</p>
</blockquote>
<p>시스템이 시트 값을 몰래 0으로 고치지는 않습니다. 사용자는 시트를 수정한 뒤 다시 불러오거나, 차이를 이해한 상태에서 <code>그래도 현재 시트값 반영</code>을 선택할 수 있습니다.</p>
<p>두 번째 선택은 “시트 계산이 맞다”는 선언이 아닙니다. 사람이 입력한 원천 항목을 현재 상태로 가져오겠다는 명시적인 판단입니다. 계산 차이는 검증 결과로 남고, 월결산처럼 값을 최종 확정하는 단계에서는 다시 확인해야 합니다.</p>

<h2>확인 버튼 하나로 끝내지 않은 이유</h2>
<p>검토 창에서 사용자가 확인을 눌렀더라도 그 사이 시트나 ERP 값이 바뀔 수 있습니다. 그래서 확인 여부만 보내지 않고, 사용자가 검토했던 값의 판본도 함께 확인합니다.</p>
<ul>
<li>검토한 시트 판본이 달라졌으면 다시 불러오도록 합니다.</li>
<li>검토 뒤 ERP의 현금흐름 값이 바뀌었으면 다시 비교하도록 합니다.</li>
<li>같은 반영 요청이 두 번 도착해도 재무 변경은 한 번만 처리합니다.</li>
<li>반영 뒤에는 JVM이 돌려준 프로젝트·항목 수·새 판본이 요청과 맞는지 BFF가 다시 확인합니다.</li>
</ul>
<p>같은 요청을 한 번만 처리하는 성질을 기술적으로는 <strong>멱등성(idempotency)</strong>이라고 부릅니다. 사용자가 기다리다 새로고침하거나 네트워크가 끊겨 다시 눌러도 원장이 두 번 만들어지지 않게 하는 장치입니다.</p>

<h2>주정산을 잠금으로 만들지 않은 이유</h2>
<p>초기에는 주정산이 끝난 주차를 수정하지 못하도록 잠그는 구조도 만들었습니다. 주간 업무를 완료했다면 값도 고정해야 한다고 생각했기 때문입니다.</p>
<p>하지만 실제 운영에서는 주정산과 월결산의 의미가 달랐습니다.</p>
<ul>
<li><strong>주정산</strong>은 해당 주에 값을 확인했는지, 목요일까지 처리했는지를 기록하는 운영 신호입니다.</li>
<li><strong>월결산</strong>은 그 달의 값을 최종 확정하고 이후 변경에 별도 절차를 요구하는 회계 경계입니다.</li>
</ul>
<p>주정산을 강한 잠금으로 사용하면 월말 전에 발견한 누락도 바로 고칠 수 없습니다. 반대로 아무 기록도 남기지 않으면 어느 값을 기준으로 주간 확인을 마쳤는지 알 수 없습니다.</p>
<p>현재 구조에서는 주정산 시점의 값과 처리자·처리 시각을 고정해 기록하되, 월결산 전 수정 자체를 막지는 않습니다. 실제 쓰기를 막는 유일한 기준은 월결산입니다. 코드에도 이 결정을 다음과 같이 남겼습니다.</p>
<pre><code>// 주정산은 운영 상태일 뿐이다.
// 쓰기를 막는 기준은 월결산 하나로 둔다.
</code></pre>
<p>이 변화는 단순한 이름 변경이 아니었습니다. “완료”와 “확정”을 분리한 것입니다. 주정산 뒤 값이 달라지면 사람에게 차이를 알리고 이력을 남길 수 있지만, 최종 고정 권한은 월결산에만 둡니다.</p>

<h2>JVM을 둔다고 문제가 자동으로 해결되지는 않았다</h2>
<p>역할을 나누면 책임은 명확해지지만, BFF와 JVM 사이의 통신 경로가 하나 더 생깁니다. 최근 점검에서는 이 경계 자체에서도 문제를 발견했습니다.</p>
<ul>
<li>브라우저가 기다리는 시간보다 BFF의 재시도 시간이 길어 사용자는 결과를 받지 못하는 경로가 있었습니다.</li>
<li>JVM의 구체적인 오류가 BFF를 지나며 하나의 영어 오류 문구로 바뀌었습니다.</li>
<li>쓰기 요청에 필요한 편집 정보가 자바스크립트 객체를 옮기는 과정에서 조용히 빠지는 경로가 있었습니다.</li>
<li>BFF와 JVM이 역할별 권한을 서로 다르게 정의한 적도 있었습니다.</li>
</ul>
<p>그래서 BFF와 JVM을 나눈 뒤에는 통신 계약도 함께 정리했습니다. 변경 요청은 함부로 재시도하지 않고, 서버 오류 코드는 개발 기록까지 보존합니다. 누가 어떤 명령을 실행할 수 있는지는 JVM의 권한표를 기준으로 삼고 자동 검사에서 서로 다른 정의가 생기면 실패하도록 했습니다.</p>
<p>JVM을 유지한 이유는 Java가 숫자를 더 잘 계산해서가 아닙니다. 재무 규칙과 저장 권한을 한곳에서 지키고, 실제 Firestore 변경을 포함한 테스트로 그 경계를 확인할 수 있었기 때문입니다.</p>

<h2>테스트한 것</h2>
<p>계산 검증은 정상 숫자 하나만 맞는다고 끝나지 않습니다. 다음 경우를 각각 확인했습니다.</p>
<ul>
<li>입금 7개와 출금 9개의 합계가 맞는지</li>
<li>이전 연도 잔액이 다음 연도 첫 주에 이어지는지</li>
<li>시트 잔액이 틀려도 JVM 계산 잔액으로 다음 기간을 이어 가는지</li>
<li>빈칸과 명시적인 0원이 계산 결과는 같아도 서로 다른 상태로 남는지</li>
<li>음수 정정 금액은 허용하고 소수 금액은 거절하는지</li>
<li>같은 셀이 두 번 들어오거나 필수 항목이 빠지면 거절하는지</li>
<li>2024년 첫 연간 잔액과 이후 연도의 이월 잔액을 다르게 설명하는지</li>
<li>사용자에게 실제 셀 주소와 현재값·기대값이 표시되는지</li>
</ul>
<p>가장 최근 화면 검사는 세 가지 설명을 확인합니다. 비어 있는 주간 합계, 최초 연도의 잔액, 이전 연도에서 이어지는 잔액입니다. 마지막 변경은 Stage 자동 배포까지 성공한 상태에서 확인했습니다.</p>

<h2>현재 구조의 한계</h2>
<p>첫째, 모든 구글 시트 수식을 해석하는 범용 계산기는 아닙니다. 현재는 고정된 현금흐름 탭의 주차별·연간 입금 합계, 출금 합계, 잔액과 이전 연도 이월을 검증합니다.</p>
<p>둘째, BFF에는 화면 미리보기와 기존 경로를 위한 중복 계산 코드가 일부 남아 있습니다. 최종 판단은 JVM이 하지만, 역할을 더 선명하게 만들려면 결과가 같은지 충분히 확인한 뒤 BFF의 중복 계산을 걷어내야 합니다.</p>
<p>셋째, 계산 차이를 월결산의 최종 차단 조건과 연결하는 작업은 아직 남아 있습니다. 현재는 반영 전 차이를 발견하고 명시적인 사람 확인을 받는 단계까지 구현했습니다. 다음 단계에서는 검증되지 않은 계산 결과가 월결산으로 확정되지 않도록 같은 계산 판본을 다시 확인해야 합니다.</p>
<p>마지막으로 JVM의 일부 Firestore 조회에는 과거 관계형 데이터베이스 시절의 접근 방식이 남아 있습니다. 역할 분리와 계산 정확성은 확보했지만, 월결산 조회 성능은 기간 조건과 인덱스를 실제로 사용하도록 별도로 개선해야 합니다.</p>

<h2>정리</h2>
<p>구글 시트 연동의 다음 단계는 값을 더 많이 읽는 일이 아니었습니다. 읽어 온 숫자를 어떤 근거로 믿을지 정하는 일이었습니다.</p>
<p>MYSCube는 역할을 다음처럼 나눴습니다.</p>
<ul>
<li>구글 시트는 사용자가 익숙하게 입력하고 확인하는 화면입니다.</li>
<li>BFF는 셀 위치와 상태를 업무 정보로 바꾸고, 검토한 값이 바뀌지 않았는지 확인합니다.</li>
<li>JVM은 입금·출금·잔액을 독립적으로 계산하고 저장 권한과 변경 이력을 책임집니다.</li>
<li>프론트엔드는 계산하지 않고 사람이 판단할 수 있는 설명을 보여줍니다.</li>
</ul>
<p>이 구조에서 가장 중요한 결과는 오류를 자동으로 고치는 기능이 아닙니다. 시스템이 “시트와 계산이 다르다”고 말하고, 어느 셀을 왜 확인해야 하는지 설명할 수 있게 된 것입니다.</p>
<p>계산의 옳고 그름을 JVM이 판단하게 되자 다음 질문은 그 결과를 어떤 명령과 상태로 저장할 것인가였습니다. 주정산을 단순한 생성·조회·수정·삭제로 다루면 중복 요청과 동시 수정, 그리고 “확인 완료”와 “최종 확정”의 차이를 표현하기 어렵습니다.</p>

<p>안녕하세요. MYSCube를 만들고 있는 MYSC AXR팀입니다.</p>
<p><strong>MYSCube는 MYSC가 자체 개발한 내부 ERP입니다.</strong> 프로젝트, 예산, 지출, 정산, 현금흐름처럼 조직 운영에 필요한 데이터를 하나의 흐름으로 연결하고 있어요.</p>
<p>MYSC는 그동안 사업별 현금흐름을 구글 시트로 관리해 왔습니다. 하나의 시트 안에서 월별·주차별 예측값과 실적값을 나누고, 입금과 출금 항목을 기록한 뒤 합계와 잔액을 계산했어요.</p>
<p>시트의 가로축에는 월별 주차가, 세로축에는 입금과 출금 항목이 놓여 있었습니다. 같은 구조가 예측값과 실적값으로 나뉘고, 각 구간의 끝에서는 입금 합계·출금 합계·잔액을 계산했어요. 한 화면에서 사업의 현금흐름을 살펴보기에는 편리했지만, 데이터의 의미가 셀의 위치와 수식에 묶여 있는 구조였습니다.</p>
<p>현장에서 구글 시트는 익숙하고 유연한 도구였습니다. 항목을 추가하기도 쉽고, 상황에 따라 수식을 고치거나 숫자를 직접 보정할 수도 있었죠. 문제는 이 유연함까지 시스템으로 옮겨야 할 때 시작됐습니다.</p>
<p>처음에는 시트의 오늘 값을 읽어 내부 ERP에 저장하면 된다고 생각했어요. 하지만 셀에 보이는 숫자는 계산의 결과일 뿐, 그 계산이 업무 규칙에 맞았다는 보증은 아니었습니다. 수식이 지워지고 숫자만 남을 수도 있고, 합계가 0원이어야 할 자리가 비어 있을 수도 있었어요. 앞 주의 잔액이 틀리면 다음 주의 숫자도 연이어 달라질 수 있었고요.</p>
<blockquote>
<p>시트의 값을 읽는 것과 그 숫자를 믿는 것은 다른 문제였습니다.</p>
</blockquote>
<p>그래서 MYSCube는 백엔드를 두 개로 나눴습니다. 하나는 구글 시트를 잘 읽고, 다른 하나는 읽어 온 숫자가 맞는지 다시 계산합니다. 이번 글에서는 왜 이런 구조를 선택했고, 두 백엔드가 각각 어떤 일을 맡았는지 소개할게요.</p>

<h2>왜 백엔드가 두 개나 필요했을까요?</h2>
<p>백엔드는 사용자가 보는 화면 뒤에서 데이터를 읽고 계산하고 저장하는 서버입니다. MYSCube의 구글 시트 연동에는 서로 다른 책임을 가진 두 백엔드가 있어요.</p>
<h3>시트를 읽는 Express BFF</h3>
<p>첫 번째는 <strong>Express BFF</strong>입니다. BFF는 <code>Backend for Frontend</code>의 약자로, 화면에 필요한 데이터를 모아 알맞은 형태로 전달하는 중간 서버예요.</p>
<p>구글 시트는 행과 열의 위치로 정보를 표현합니다. 사람은 표의 제목과 주변 문맥을 보며 의미를 이해하지만, 시스템은 그렇지 못해요. BFF는 시트의 특정 위치에 있는 숫자를 “2026년 12월 5주차의 예측 입금 합계”처럼 업무에서 사용하는 정보로 바꿉니다. 빈칸인지, 명시적인 0원인지, 수식 오류인지도 함께 구분하고요.</p>
<h3>숫자를 다시 계산하는 JVM 서버</h3>
<p>두 번째는 <strong>Spring Boot 기반 JVM 서버</strong>입니다. JVM은 <code>Java Virtual Machine</code>의 약자로, 자바 프로그램을 실행하는 환경이에요. Spring Boot는 이 환경에서 서버를 만드는 데 사용하는 개발 도구입니다.</p>
<p>JVM 서버는 BFF가 전달한 입금과 출금 항목으로 합계와 잔액을 다시 계산합니다. 시트에 표시된 합계를 그대로 믿지 않고, 같은 원천 값을 우리 업무 규칙에 따라 독립적으로 계산하는 거예요. 계산 결과가 맞는지, 내부 ERP에 반영해도 되는지, 누가 어떤 값을 저장했는지도 이 서버가 책임집니다.</p>
<p><img src="/assets/images/diagrams/building-ledger-02/bff-jvm-role-separation.png" alt="구글 시트를 BFF가 업무 데이터로 바꾸고 JVM 서버가 계산을 검증한 뒤 내부 ERP에 반영하거나 사람에게 차이를 보여주는 구조" /></p>
<p><em>그림 1. BFF는 시트의 언어를 업무의 언어로 바꾸고, JVM 서버는 숫자가 맞는지 판단합니다.</em></p>
<p>서버를 나눈 이유는 기술을 더 복잡하게 만들기 위해서가 아니었습니다. <mark>시트를 잘 읽는 책임과 재무 숫자가 맞다고 판단하는 책임을 분리하기 위해서</mark>였어요.</p>
<p>시트의 열이나 배치가 바뀌면 BFF만 수정하면 됩니다. 입금·출금·잔액의 계산 규칙이 바뀌면 JVM 서버에서 관리하고요. 화면이나 다른 저장 경로가 추가되더라도 재무 계산의 기준은 한곳에 남습니다.</p>

<h2>빈칸과 0원은 정말 같은 값일까요?</h2>
<p>계산을 검증하던 중 실제로 이런 경우를 만났습니다.</p>
<p>2026년 12월 5주차의 예측 입금 항목을 모두 더하면 결과는 0원이었습니다. 그런데 입금 합계가 표시되어야 할 자리는 비어 있었어요.</p>
<table>
<thead>
<tr>
<th>확인한 내용</th>
<th>결과</th>
</tr>
</thead>
<tbody><tr>
<td>입금 항목을 다시 더한 값</td>
<td>0원</td>
</tr>
<tr>
<td>구글 시트의 입금 합계</td>
<td>비어 있음</td>
</tr>
</tbody></table>
<p>계산만 놓고 보면 빈칸과 0원을 똑같이 처리할 수도 있습니다. 하지만 업무에서는 의미가 달라요.</p>
<ul>
<li><strong>빈칸</strong>은 아직 입력하거나 확인하지 않았다는 뜻일 수 있습니다.</li>
<li><strong>0원</strong>은 확인한 결과 금액이 없다는 명시적인 판단입니다.</li>
</ul>
<p>두 상태를 모두 0으로 저장하면 나중에는 “확인하지 않은 값”과 “확인했고 0원인 값”을 구분할 수 없습니다. 그래서 BFF는 금액만 가져오지 않고 빈칸, 0원, 금액, 잘못된 입력, 시트 오류라는 상태도 함께 전달합니다.</p>
<p>JVM 서버는 이 정보를 바탕으로 계산합니다. 빈칸과 0원은 합계에서는 모두 0으로 다루되, 검토할 때는 서로 다른 상태로 남겨요. 계산의 편의 때문에 업무의 의미를 지우지 않기 위해서입니다.</p>

<h2>구글 시트 전체를 다시 만들지는 않았어요</h2>
<p>JVM 서버가 계산을 검증한다고 하면 구글 시트의 모든 수식을 자바로 다시 만든 모습을 떠올릴 수 있습니다. 하지만 저희가 만든 것은 범용 스프레드시트 계산기가 아니에요.</p>
<p>MYSC의 현금흐름 관리에서 반드시 맞아야 하는 계산만 코드로 옮겼습니다.</p>
<ul>
<li>입금 항목 7개의 합계</li>
<li>출금 항목 9개의 합계</li>
<li>직전 기간의 잔액을 이어받는 누적 잔액</li>
<li>이전 연도에서 다음 연도로 넘어오는 시작 잔액</li>
<li>연간 입금·출금·잔액 합계</li>
</ul>
<p>한 주의 잔액을 구하는 식 자체는 단순합니다.</p>
<pre><code>이번 주 잔액 = 직전 주 잔액 + 입금 합계 - 출금 합계
</code></pre>
<p>어려운 부분은 ‘직전 주 잔액’을 어디에서 가져오느냐였습니다.</p>
<p>시트에 표시된 직전 잔액을 그대로 다음 계산에 사용하면, 앞 주에서 생긴 오류가 뒤로 계속 이어집니다. 이후 숫자끼리는 서로 맞아 보여 처음 어디서 잘못됐는지 찾기도 어려워져요.</p>
<p>그래서 JVM 서버는 시트에 표시된 잔액을 다음 계산의 출발점으로 사용하지 않습니다. 자신이 직접 계산한 이전 기간의 잔액을 다음 기간으로 넘겨요. 시트의 잔액은 믿고 이어 쓰는 값이 아니라, 서버 계산과 비교할 대상이 됩니다.</p>
<p><img src="/assets/images/diagrams/building-ledger-02/jvm-independent-calculation.png" alt="JVM 서버가 입금과 출금을 다시 더하고 자체 계산한 잔액을 다음 기간으로 넘겨 시트 표시값과 비교하는 흐름" /></p>
<p><em>그림 2. JVM 서버는 자신이 계산한 잔액을 다음 기간으로 넘겨, 차이가 처음 생긴 시점을 찾습니다.</em></p>
<p>연도가 바뀔 때도 같은 원칙을 적용했습니다. 이전 연도의 원천 입출금을 다시 합산하고, 그 결과를 새해 첫 주의 시작 잔액으로 사용해요.</p>
<blockquote>
<p>구글 시트를 다시 만드는 것이 아니라, 우리 업무에서 반드시 지켜야 하는 계산만 시스템의 규칙으로 옮겼습니다.</p>
</blockquote>

<h2>저장하기 전에 사람에게 먼저 알려줘요</h2>
<p>계산이 다르다는 사실을 내부 ERP에 저장한 뒤 발견하면 이미 늦을 수 있습니다. 그래서 JVM 서버의 계산 검증은 저장하기 전에 실행돼요.</p>
<ol>
<li>사용자가 구글 시트의 값을 불러옵니다.</li>
<li>BFF가 시트 값을 기간·항목·상태가 있는 업무 데이터로 바꿉니다.</li>
<li>사용자가 반영을 누르면 BFF가 같은 데이터를 JVM 서버에 보냅니다.</li>
<li>JVM 서버가 입금·출금·잔액을 다시 계산합니다.</li>
<li>결과가 다르면 저장을 잠시 멈추고 어느 기간의 어떤 항목이 다른지 알려줍니다.</li>
</ol>
<p><img src="/assets/images/diagrams/building-ledger-02/formula-preflight-review.png" alt="시트 값을 BFF가 정리하고 JVM 서버가 반영 전에 계산한 뒤 차이가 있으면 사람이 확인하는 흐름" /></p>
<p><em>그림 3. 계산이 다르면 자동으로 고치지 않고, 사람이 현재값과 기대값을 함께 확인합니다.</em></p>
<p>앞서 본 입금 합계라면 사용자는 다음과 같은 설명을 보게 됩니다.</p>
<blockquote>
<p><strong>2026년 12월 5주차 · 예측값 · 입금 합계</strong><br />
입금 합계는 해당 기간의 입금 항목을 모두 더한 값입니다.<br />
시트에는 <strong>0원</strong>이 표시되어야 합니다.<br />
현재 시트에는 이 값이 비어 있습니다.</p>
</blockquote>
<p>시스템이 빈칸을 몰래 0원으로 바꾸지는 않습니다. 사용자는 시트를 수정한 뒤 다시 불러오거나, 차이를 이해한 상태에서 현재 값을 반영할 수 있어요.</p>
<p>계산은 시스템이 책임지지만 예외를 해석하고 승인하는 판단까지 대신하지는 않습니다. 사람이 판단해야 한다면, 적어도 무엇을 보고 판단해야 하는지는 시스템이 설명하도록 만들었습니다.</p>

<h2>검토하는 사이 숫자가 바뀐다면요?</h2>
<p>사용자가 차이를 확인하는 동안에도 시트나 내부 ERP의 값은 바뀔 수 있습니다. 확인 버튼을 눌렀다는 사실만으로 저장을 허용할 수 없는 이유예요.</p>
<p>MYSCube는 사용자가 검토한 시트와 내부 ERP 값의 판본을 함께 기억합니다. 검토 뒤 어느 한쪽이라도 달라졌다면 최신 값을 다시 불러오게 해요. 기다리던 사용자가 버튼을 두 번 눌러도 같은 재무 기록은 한 번만 반영합니다.</p>
<p>같은 요청이 여러 번 도착해도 결과를 한 번만 반영하는 성질을 개발에서는 <strong>멱등성(idempotency)</strong>이라고 부릅니다. 어려운 이름이지만 목적은 단순해요. 네트워크가 끊기거나 사용자가 버튼을 다시 눌러도 같은 돈이 두 번 기록되지 않게 하는 것입니다.</p>
<p>저장이 끝난 뒤에도 서버의 ‘성공’ 응답만 믿지 않았습니다. 실제 저장소인 Firestore를 다시 읽어 요청한 프로젝트와 항목 수, 새 판본이 맞는지 확인했어요. Firestore는 구글이 제공하는 문서형 데이터베이스입니다.</p>

<h2>두 백엔드를 두고 얻은 것</h2>
<p>이 구조에서 가장 중요한 결과는 오류를 자동으로 고치는 기능이 아니었습니다. 시스템이 “시트와 다시 계산한 결과가 다르다”고 말하고, 사용자가 무엇을 확인해야 하는지 설명할 수 있게 된 것이었어요.</p>
<p>역할도 더 분명해졌습니다.</p>
<ul>
<li>구글 시트는 사용자가 익숙하게 입력하고 확인하는 화면으로 남았습니다.</li>
<li>BFF는 시트의 행과 열을 기간·항목·상태라는 업무 정보로 바꿉니다.</li>
<li>JVM 서버는 입금·출금·잔액을 다시 계산하고 저장 규칙을 지킵니다.</li>
<li>프론트엔드는 계산하지 않고 사람이 판단할 근거를 보여줍니다.</li>
</ul>
<p>물론 아직 남은 일도 있습니다. 현재 검증기는 모든 구글 시트 수식을 이해하는 도구가 아니라 MYSC 현금흐름의 고정된 계산만 다룹니다. BFF에 남아 있는 일부 비교 계산도 JVM 결과와 충분히 대조한 뒤 정리해야 해요. 계산 결과의 판본을 월결산의 최종 확정 조건과 연결하는 작업도 남아 있습니다.</p>
<p>하지만 이번 단계에서 한 가지 기준은 분명해졌습니다.</p>
<blockquote>
<p>외부 도구의 값을 가져오는 서버와, 그 값을 공식 기록으로 인정할지 판단하는 서버는 같은 책임이 아닙니다.</p>
</blockquote>
<p>반복할 수 있는 계산은 시스템이 맡고, 예외에 대한 최종 판단은 사람이 근거를 보고 내립니다. 두 개의 백엔드는 이 경계를 지키기 위한 선택이었습니다.</p>

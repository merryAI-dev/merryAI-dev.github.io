안녕하세요, MYSC AXR팀의 보람입니다.

> “MYSC 플랫폼도 API로 연결할 수 있나요?”

최근 사내에서 이런 질문을 받았습니다. MYSC는 개발자가 중심인 조직이 아닙니다. 사업을 운영하고, 스타트업을 만나고, 투자와 액셀러레이팅을 하는 구성원들이 자체 개발한 플랫폼을 사용하고 있습니다.

그런 조직에서 먼저 API 연결을 물어왔다는 사실이 반가웠습니다. 플랫폼에 필요한 기능을 요청하는 데서 한 걸음 더 나아가, 다른 도구와 연결해 자신의 업무 흐름을 바꿔보려는 수요가 생긴 것이니까요.

어떤 연결을 원하는지 이야기를 더 들어보니 요청이 구체적으로 보이기 시작했습니다. ChatGPT나 Claude에서 사업의 정산 현황을 물어보고, 등록된 기업을 검색하고, 엑셀에 정리한 기업들을 한 번에 등록하고 싶었습니다. 필요할 때는 조건에 맞는 목록을 파일로 내려받고 싶었고요.

사용자가 원하는 경험은 익숙한 AI 도구에서 MYSC의 정보를 찾고 업무를 처리하는 것이었습니다. 기존 API를 그 경험으로 이어주는 인터페이스로 MCP를 선택했습니다.

이번 글에서는 API와 MCP의 역할부터 살펴보고, 화면을 직접 조작하는 에이전트 대신 MCP를 선택한 이유와 구현 과정을 소개합니다. 그리고 **업무에서 필요한 정보를 플랫폼에 담고, MCP로 활용하고, 그 피드백으로 플랫폼을 개선하는 플라이휠**이 MYSC에서 어떻게 돌기 시작했는지 이야기하려고 합니다.

## API와 MCP는 어떤 역할을 맡을까요

API는 프로그램이 다른 프로그램의 기능을 호출하는 인터페이스입니다. MYSCube의 API에는 사업 목록 조회나 정산 현황 조회가 있고, EMA Station의 서버 함수에는 기업 조회와 등록 기능이 있습니다.

이 기능을 호출하려면 호출하는 쪽이 주소, 인증 방식, 입력값, 응답 형식을 알아야 합니다. 개발자는 그 정보를 바탕으로 연동 코드를 작성합니다. AI 에이전트에도 이런 호출 방법을 직접 연결할 수 있습니다.

MCP(Model Context Protocol)는 AI 애플리케이션과 외부 시스템이 도구 등을 주고받는 공통 규약입니다. 서버는 도구의 이름, 설명, 입력 스키마를 제공하고, 클라이언트는 도구 목록을 확인한 뒤 필요한 도구를 호출합니다. [MCP 공식 아키텍처 문서](https://modelcontextprotocol.io/docs/learn/architecture)

MYSC에서는 MCP가 기존 API를 호출하도록 구성했습니다. 사업을 찾는 도구는 사업 목록 API를 사용하고, 기업을 등록하는 도구는 EMA의 등록 함수를 사용합니다.

| 구분 | 기존 API | MCP로 제공하는 도구 |
|---|---|---|
| 기능을 알리는 방법 | API 문서와 연동 코드 | 도구 목록, 설명, 입력 스키마 |
| 호출 예시 | 사업 조회 주소에 정해진 파라미터 전달 | `project_search`에 사업명 전달 |
| AI 앱에 연결하는 방식 | 앱별로 호출 코드를 연결 | MCP를 지원하는 앱의 공통 규약 사용 |
| 업무 규칙과 권한 | 기존 서버가 검증 | MCP를 거쳐도 기존 서버가 검증 |

MCP의 이점은 반복해서 제공할 도구의 사용법을 공통 인터페이스로 설명할 수 있다는 점입니다. 새로운 AI 앱마다 전체 업무 로직을 다시 연결하는 부담을 줄일 수 있습니다. 다만 각 앱의 인증 지원과 도구 사용 방식은 연결 시 확인해야 합니다.

한 개의 AI 서비스에서 정해진 API만 호출한다면 직접 연동도 충분히 좋은 선택입니다. MYSC는 구성원들이 사용하는 여러 AI 도구에 자체 플랫폼을 연결하려 했고, 그 요구에 MCP가 잘 맞았습니다.

## 에이전트가 화면을 직접 조작하면 어떨까요

AI 에이전트가 브라우저를 열어 사람처럼 플랫폼을 사용하는 방법도 있습니다. 화면이나 DOM을 확인하고, 메뉴를 선택하고, 검색창에 입력하고, 결과를 읽는 방식입니다. API를 제공하지 않는 외부 서비스나 화면 자체를 검증하는 작업에 유용합니다.

그런데 MYSC는 플랫폼의 코드와 API를 직접 관리하고 있습니다. 반복되는 조회와 등록을 위해 화면 탐색 과정을 매번 거치게 할 필요가 있는지 생각해봤습니다.

예를 들어 “등록된 기업 현황을 알려줘”라는 요청을 비교해볼 수 있습니다. 아래 그림은 실행 단계를 설명하기 위한 예시이며 실제 측정 결과는 아닙니다.

![화면 조작에서는 메뉴 이동과 화면 확인을 거치고 MCP에서는 현황 도구로 기존 서버 함수를 호출하는 경로 비교](/assets/images/diagrams/platform-mcp-flywheel/01-gui-and-mcp.png)
*그림 1. 반복되는 업무는 화면 탐색 단계를 줄이고, 서버가 계산한 결과를 직접 받을 수 있습니다.*

화면 조작에서는 각 단계의 결과를 보고 다음 행동을 정해야 합니다. 화면 기반 방식은 스크린샷을, DOM 기반 방식은 페이지 구조나 접근성 정보를 처리합니다. 이 관찰과 판단의 반복이 모델 입력량과 대기 시간에 영향을 줄 수 있습니다. 스크린샷 기반 컴퓨터 사용의 동작 원리는 [Anthropic의 컴퓨터 사용 소개](https://www.anthropic.com/research/developing-computer-use)에서도 확인할 수 있습니다.

MCP에서는 도구를 선택한 뒤 서버가 조회·집계한 결과를 받을 수 있습니다. 화면에서 표를 읽고 합계를 재구성하는 일을 서버의 명시적인 조회로 옮길 수 있는 것이죠. 다만 MCP도 도구 설명과 응답을 모델에 전달하며, 한 작업에 여러 도구 호출이 필요할 수 있습니다.

이 선택의 경제성은 다음 비용을 함께 봐야 합니다.

| 비용 항목 | 화면을 조작하는 방식 | MYSC의 MCP 방식 |
|---|---|---|
| 초기 구현 | 기존 화면을 활용해 시작 가능 | 도구, 인증, 서버 연결 구현 필요 |
| 반복 실행 | 화면 관찰·이동·결과 해석이 누적 | 도구 선택과 구조화된 응답 처리 |
| 변경 대응 | 메뉴·레이아웃·DOM 변경의 영향 | API 계약과 도구 스키마 변경의 영향 |
| 실패 복구 | 어느 화면에서 멈췄는지 확인 | 호출·오류·배치 처리 상태로 확인 |
| 운영 | 브라우저 실행 환경과 세션 관리 | MCP 서비스, 인증, API 운영 |

**한 번의 시연보다 같은 업무를 여러 번 수행할 때의 총비용**이 판단 기준이었습니다. MCP 구축에는 초기 비용이 들지만, 안정적인 API가 있고 반복 업무가 많다면 탐색·재시도·화면 변경 대응 비용을 줄일 여지가 있습니다.

이번 작업에서 두 방식의 토큰 비용이나 시간을 동일 조건으로 측정하지는 않았습니다. 따라서 특정 비율의 절감을 주장할 수는 없습니다. MYSC가 선택한 근거는 자체 API를 재사용해 실행 경로를 짧고 명확하게 만들 수 있다는 구조적 이점이었습니다. 이후에는 성공한 업무 한 건당 모델 비용, 완료 시간, 재시도 횟수와 유지보수 시간을 함께 측정하려고 합니다.

## 기존 플랫폼을 AI 도구의 기반으로 사용하기

MYSCube는 사업과 정산 데이터를 관리합니다. EMA Station은 스타트업과 프로그램 운영 정보를 관리하고, 기업 등록번호인 FRN을 발급해 등록 이력을 쌓습니다.

MYSCube에는 8월에 구현한 OAuth 기반 정산 현황 조회 MCP가 있었습니다. 이번 작업에서는 사업 검색부터 입출금 조회까지 이어갈 수 있도록 그 초기 구현을 확장했습니다.

| MYSCube 도구 | 하는 일 |
|---|---|
| `project_search` · `project_get` | 사업을 찾고 기본 정보 조회 |
| `cashflow_status` | 월별 주정산·월결산 현황 조회 |
| `accounting_read` | 원장에 반영된 계획·실적 입출금 조회 |
| `sheet_check` | 사업비 시트 양식과 불러오기 오류 확인 |
| `api_catalog` · `api_read` | 등록된 추가 조회 API 탐색과 실행 |

도구를 만들 때는 AI가 결과의 의미를 알 수 있도록 설명했습니다. 예를 들어 `accounting_read`는 원장에 반영된 값을 읽습니다. Google Sheets의 실시간 값을 읽는 도구로 해석해서는 안 되므로 그 차이를 설명에 넣었습니다.

조회 API마다 도구를 하나씩 늘리는 대신 일부 기능은 카탈로그로 묶었습니다. AI는 카탈로그에서 필요한 API를 찾고, 해당 입력 스키마에 맞춰 조회합니다. 실행할 수 있는 항목은 등록된 목록으로 제한하고 파라미터도 검증합니다.

EMA에서는 현황, 검색, 상세 조회에 더해 엑셀 내보내기, 업로드 링크, 일괄 등록 미리보기와 실행을 도구로 제공했습니다. 등록 양식을 내려받는 도구도 추가했습니다. 실제 현황 도구 구현의 핵심을 축약하면 다음과 같습니다.

```javascript
tool(server, 'ema_registry_status', {
  title: '등록 현황',
  description: '스타트업 등록 현황 요약. 삭제된 기업은 제외합니다.',
  input: {
    recentCount: z.number().int().min(0).optional()
      .describe('최근 수정 기업을 몇 건 볼지'),
  },
}, ({ recentCount }) => ema.call(
  'getRegistryStatusSummary',
  recentCount === undefined ? {} : { recentCount },
));
```

도구는 호출 방법을 설명하고, 전체 현황 집계는 EMA 서버 함수가 담당합니다. 모델은 그 결과를 사용자의 질문에 맞춰 설명합니다.

## 로그인과 권한을 기존 서버에 연결하기

AI를 통해 요청해도 로그인한 구성원의 권한을 사용하도록 구성했습니다. MCP 서버가 별도의 관리자 계정으로 모든 데이터를 읽도록 만들지는 않았습니다.

MYSCube의 MCP 서버는 구성원의 Firebase ID 토큰으로 BFF를 호출합니다. BFF는 기존 요청과 같은 경로에서 구성원의 상태, 역할, 사업 접근 범위를 확인합니다. EMA도 사용자 토큰으로 서버 함수를 호출하고, 함수가 권한을 검사합니다.

![AI 앱에서 MCP 서버를 거쳐 사용자 Firebase 토큰으로 기존 BFF와 EMA 서버 함수를 호출하는 구조](/assets/images/diagrams/platform-mcp-flywheel/02-user-authority.png)
*그림 2. MCP는 호출을 연결하고, 데이터 접근과 업무 규칙은 기존 플랫폼이 판단합니다.*

두 플랫폼의 로그인 방식은 달랐습니다. MYSCube는 회사 Google 계정을, EMA는 구성원별 이메일·비밀번호 계정을 사용합니다. Firebase 프로젝트도 다르기 때문에 같은 로그인 흐름을 그대로 적용할 수 없었습니다.

EMA에는 기존 웹사이트에 MCP 연결 확인 화면을 추가했습니다. 사용자는 EMA 사이트에서 로그인하고 연결을 허용합니다. 비밀번호는 그 사이트에서 입력하고, MCP 서비스는 로그인 후 전달된 Firebase 토큰으로 접근 권한을 확인합니다.

EMA의 조회는 관리자·컨설턴트·직원에게, 일괄 등록과 내보내기는 관리자에게 제공합니다. 관리자용 도구를 목록에서 구분하고 실제 함수에서도 권한을 다시 검사합니다.

도구 설명이나 읽기 전용 표시는 사용 지침입니다. 실행 권한을 보장하는 것은 서버의 검사이므로 두 역할을 구분했습니다.

## 엑셀 등록을 반복 가능한 실행으로 만들기

엑셀 일괄 등록은 여러 기업에 FRN을 발급하거나 기존 기업에 등록 근거를 추가하는 작업입니다. 조회와 달리 실제 데이터가 바뀌므로 미리보기와 실행을 나눴습니다.

미리보기에서는 신규 기업, 기존 기업과의 일치, 파일 안의 중복, 삭제·이관 기업과의 일치, 오류 행을 분류합니다. 기업 데이터는 쓰지 않고, 결과를 사용자에게 보여준 뒤 확인받아 실행하도록 도구 사용 지침을 넣었습니다.

실행 시에는 서버가 데이터를 다시 검증하고 현재 상태로 중복을 판단합니다. 미리보기와 실행 사이에 다른 사용자가 같은 기업을 등록했을 수 있기 때문입니다. 사람의 확인은 AI의 사용 흐름에서 요구하고, 서버는 권한과 데이터 조건을 검증하도록 구성했습니다.

단건 등록과 일괄 등록은 공통 함수 `registerRegistrySourceRecordForActor`를 사용합니다. 같은 업무의 쓰기 규칙이 별도 경로에서 달라지는 것을 줄이기 위해서입니다.

```javascript
const result = await registerRegistrySourceRecordForActor({
  uid,
  profile,
  authEmail,
  data: item.record,
  awardCredit: false,
  additive: true,
  importLedger: {
    ref: db.collection('registryImportLedger').doc(importKey),
    batchId,
    index: item.index,
  },
});
```

위 코드는 핵심 옵션을 남긴 축약본입니다. `additive: true`인 일괄 등록은 기존 값의 빈 칸만 채우며, 기여 크레딧은 기본으로 부여하지 않습니다. 처리 식별값과 결과는 트랜잭션 안에서 원장에 기록해 같은 행을 다시 요청해도 중복 처리하지 않도록 했습니다.

MCP에서는 25행씩 나눠 처리하고 진행 상태를 저장합니다. 처리 시간이 길어지거나 중간에 실패하면 같은 배치로 이어서 실행할 수 있습니다. AI가 매번 복구 절차를 새로 추론하기보다 서버와 배치 기록이 재처리를 책임지도록 했습니다.

엑셀 내보내기는 Worker에서 파일을 생성해 만료 시간이 있는 다운로드 링크를 반환합니다. 기본 검색·상세 응답에서는 연락처와 사업자번호 전체를 제한하고, 내보내기 권한이 있는 사용자는 파일로 전체 정보를 받습니다. 이때 파일 링크는 소지자가 접근할 수 있는 임시 링크이므로 전달 범위도 고려해야 합니다.

## MCP를 독립적으로 배포하기

처음에는 MYSCube BFF 안에서 원격 MCP를 제공했습니다. 하지만 MCP 변경이 앱 배포에 묶이고, 앱 배포는 다른 JVM 정산 전환을 기다리면서 도구 개선을 사용자에게 전달하기 어려워졌습니다.

이 경험을 계기로 MCP를 독립 Cloudflare Worker로 분리했습니다. MYSCube와 EMA는 각각 별도 서비스와 세션 저장소를 사용하며, 기존 BFF와 서버 함수를 호출합니다. MCP 배포는 `main`의 CI 성공에 연결해 앱·JVM 릴리스 주기와 분리했습니다.

다만 새 도구가 새 백엔드 API를 필요로 한다면 해당 API 배포도 필요합니다. 독립 서비스로 옮겼다고 모든 기능의 배포 의존성이 사라지는 것은 아닙니다.

배포 후에는 OAuth 연결 요청의 만료와 도구 목록 수신도 확인해야 했습니다. 서버가 실행 중인 상태, 사용자 연결이 끝난 상태, AI 앱에서 도구를 호출할 수 있는 상태는 각각 다릅니다. 만료된 동의 요청에는 오류 화면 대신 연결을 다시 시작하는 안내를 추가했습니다.

## MYSC의 개발과 활용 플라이휠

이번 작업을 통해 **필요한 정보를 자체 플랫폼에 담는 단계에서, 그 정보를 AI 도구로 활용하고 다시 개발에 반영하는 단계까지 한 사이클이 이어졌습니다.**

플라이휠은 한 단계의 결과가 다음 단계의 기반이 되고, 그 결과가 다시 처음 단계의 개선으로 돌아오는 순환을 뜻합니다. MYSC에서는 다음 흐름으로 설명할 수 있습니다.

![업무에서 나온 정보와 요청이 자체 플랫폼과 API 개발, MCP 도구 제공, AI 활용과 검증, 사용 피드백을 거쳐 다음 개선으로 돌아오는 플라이휠](/assets/images/diagrams/platform-mcp-flywheel/03-development-flywheel.png)
*그림 3. 플랫폼에 쌓인 데이터와 업무 규칙이 MCP의 기반이 되고, 사용 피드백이 다음 플랫폼 개선으로 돌아옵니다.*

사업과 기업 정보를 자체 플랫폼에 모으면서 데이터 구조와 업무 규칙이 생겼습니다. 그 규칙을 구현한 API와 서버 함수는 MCP 도구의 기반이 됐습니다. 구성원은 익숙한 AI 도구에서 플랫폼 기능을 시도하고, 그 과정에서 기존 화면만 사용할 때는 드러나지 않았던 요구를 제시했습니다.

실제로 이 피드백이 서버 개선으로 돌아온 사례가 있습니다.

EMA 웹 화면에서는 기업명·대표자·섹터를 중심으로 FRN을 발급할 수 있었지만, 처음 만든 일괄 등록 흐름은 발굴 경로와 국가 코드, 법인명까지 요구했습니다. AI는 그 설명을 따라 복잡한 엑셀 양식을 제시했습니다.

사용자는 같은 등록인데 왜 더 많은 항목이 필요한지 물었습니다. 이 피드백을 받아 일괄 등록의 입력 기준과 기본값을 웹 화면에 맞췄습니다. 법인명이 비면 기업명을 사용하고, 기본 발굴 경로도 화면과 같게 적용했습니다. 모르는 섹터는 조용히 다른 값으로 바꾸지 않고 오류로 알려주도록 했습니다.

**AI에서 나온 사용 피드백이 플랫폼의 입력 계약을 개선하고, 개선된 계약이 다시 AI의 도구 사용을 바꾸는 흐름**입니다.

MYSCube에서는 “전체 사업을 확인하고 싶다”는 요청이 검색의 20건 제한을 드러냈습니다. 특정 사업을 찾기 위한 검색과 전수조사는 요구가 다릅니다. 이 문제는 마지막 페이지까지 읽는 전체 조회와 조회 범위를 표시하는 응답 설계로 이어졌습니다.

집필 시점에 EMA의 최소 입력 기준 개선은 서버에 병합됐고, 도구 안내·양식 다운로드 개선도 MCP에 병합돼 Worker 배포를 마쳤습니다. MYSCube의 전체 조회 개선은 후속 PR에서 진행 중입니다. 피드백이 개발로 돌아오는 순환은 시작됐으며, 각 변경의 실제 사용 검증을 이어가고 있습니다.

이 순환의 기반은 MCP 이전에 축적한 플랫폼 자산입니다. 사업 ID, 기업 식별 기준, 사용자 권한, 정산 원장, 등록 규칙이 있어야 AI가 호출할 기능도 명확하게 만들 수 있습니다. 자체 개발한 플랫폼에서는 사용 중 발견한 문제를 API와 업무 규칙까지 거슬러 올라가 고칠 수 있다는 점도 중요했습니다.

다만 이 플라이휠이 사용량과 생산성을 얼마나 높였는지는 앞으로 측정해야 합니다. 현재 확인한 것은 활용 수요가 도구 개발로 이어지고, 도구 사용 중 나온 피드백이 플랫폼 개선으로 돌아온 구체적인 흐름입니다.

## 다음 사이클에서 확인할 것

MYSC는 MCP 연결 성공과 업무 완료를 구분해 검증하려고 합니다. 조회에서는 접근 가능한 범위와 전체 건수가 맞는지, 등록에서는 미리보기·실행·재시도가 같은 결과를 유지하는지 확인해야 합니다.

비용도 업무 완료를 기준으로 비교할 계획입니다. 같은 권한과 입력 데이터로 화면 조작과 MCP를 실행하고, 성공한 업무 한 건당 모델 비용·완료 시간·재시도 횟수를 기록하면 경제성을 더 정확히 판단할 수 있습니다. API와 MCP의 유지보수 비용도 함께 봐야 하고요.

MCP 도구가 추가되는 것만으로 플라이휠이 지속되지는 않습니다. 사용자가 겪은 문제를 재현하고, 코드와 테스트를 고치고, 배포 후 같은 업무에서 개선됐는지 확인하는 과정이 계속 연결되어야 합니다.

## 마치며

사내에서 먼저 API 연결을 물어왔던 장면이 오래 남습니다. 비개발자 조직의 구성원이 자체 플랫폼의 정보를 다른 도구에서도 활용하고 싶어 했다는 점이 반가웠습니다.

MYSC는 그 요청을 구체화하며 기존 API를 MCP 도구로 연결했습니다. 반복 업무는 명시적인 호출과 구조화된 결과로 제공하고, 권한과 데이터 변경 규칙은 기존 서버에서 검증하도록 했습니다.

그리고 도구를 사용해보는 과정에서 나온 질문이 다시 플랫폼 개발로 돌아왔습니다. 조회 범위를 고치고, 등록 입력값을 맞추고, 재처리와 연결 오류를 다루는 일이 다음 개선이 됐습니다.

MYSC의 자체 플랫폼 개발은 이제 데이터를 저장할 화면을 만드는 일에서 더 나아가고 있습니다. **업무에 필요한 정보를 만들고, 연결하고, 활용하고, 그 경험으로 다시 개선하는 사이클**을 이어가고 있습니다. MCP는 그 사이클에서 구성원의 AI 도구와 MYSC의 플랫폼을 잇는 역할을 맡았습니다.

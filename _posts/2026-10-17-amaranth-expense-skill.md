안녕하세요, MYSC AXR팀의 보람입니다.

지출결의를 AI와 함께 처리하는 과정에서 흥미로웠던 것은 AI가 얼마나 많은 칸을 채울 수 있는가보다, **어떤 질문을 없애고 어떤 질문을 끝까지 남겨야 하는가**였습니다. 정해진 날짜를 매번 묻는 것은 번거롭지만, 과거 택시비의 적요를 이번 거래에 그대로 붙이는 것은 위험합니다. 둘 다 빈칸을 채우는 일처럼 보여도 필요한 판단은 다릅니다.

이번 글에서는 `jichool`의 기능 목록보다 그 경계를 고쳐 나간 과정을 따라가 보려고 합니다. 기존 CLI에 Skill을 붙인 이유, 고정 날짜를 질문하던 흐름을 고친 일, 규칙 문서를 추가한 뒤 다시 일부 적용을 멈춘 일이 실제 변경 이력에 남아 있습니다. AI가 진행할 절차와 사람이 결정할 사항이 어떻게 코드와 문서로 나뉘었는지가 이 글의 중심입니다.

**기록을 읽는 방법을 먼저 밝힙니다.** 이 글은 2026년 10월 17일 확인한 소스·Git 변경 이력·테스트와 기존 작업 기록을 바탕으로 합니다. 일부 커밋에는 Claude 공동 작성 표기가 있지만, 그것만으로 각 판단을 누가 먼저 제안했는지 알 수는 없습니다. 당시 대화 원문을 확인하지 않았으므로 대사를 재현하지 않았습니다. 아래의 ‘변경 기록의 요지’는 커밋 설명과 diff의 의역이며, ‘구현 분석’은 그 결과를 읽은 저의 해석입니다. 거래·대화 예시는 합성임을 별도로 표시합니다.

도구의 실행 범위는 전자결재 **임시보관까지**입니다. 이번 글의 검증 과정에서 재무 시스템에 새로 쓰거나 상신·지급하지 않았고, 원본 증빙·개인정보·계좌·인증정보도 공개하지 않았습니다.

## 아마란스에서 우리가 만들려는 것은 어떤 문서인가

이 도구가 만드는 것은 **본인·현재 부서의 법인카드 사용 내역을 정리한 지출결의서**입니다. 카드 사용 사실과 금액은 카드 원본·영수증·명세서에서 가져옵니다. 그 위에 왜 썼는지 적요를 쓰고, 어떤 비용으로 분류할지 용도를 선택하고, 어느 프로젝트에 귀속할지 정합니다. 이 글에서 ‘사업의 비용으로 귀속한다’는 말은 구현에 있는 프로젝트 선택을 설명하는 표현이며, 별도의 사업 배분 기능이 있다는 뜻은 아닙니다.

과거 같은 가맹점의 적요가 야근 택시비였다면 AI가 그 표현을 제안할 수는 있습니다. 하지만 사용자가 외부 미팅이었다고 확인한 이번 건은 다른 목적입니다. 적요뿐 아니라 용도와 프로젝트까지 다시 봐야 합니다. AI가 질문을 잘 묶어야 하는 이유는 한 답변이 여러 업무 항목에 영향을 주기 때문입니다. 이 장면은 구현된 질문 흐름을 설명하는 합성 사례이며 실제 대화 인용이 아닙니다.

아마란스에서 사용하는 용도 선택은 비용 분류와 연결되지만, 도구가 독립적으로 회계 판단을 확정하지는 않습니다. 지급요청일 역시 실제 지급 완료일이 아닙니다. 이 흐름의 끝은 임시보관이며, 사용자가 문서를 검토하고 직접 상신하는 후속 절차가 남습니다. 결재선의 자동 추천·확정은 이번에 검증한 기능에 포함하지 않았습니다.

## 첫 번째 결정: 연동을 다시 만들지 않고 진행자를 붙였습니다

[앞선 MCP 글](/posts/mysc-platform-mcp-flywheel/)은 자체 플랫폼의 API를 여러 AI 도구에 연결하는 이야기였습니다. 이번에는 이미 그룹웨어를 조회하고 임시보관할 수 있는 Python CLI가 있었습니다. 남아 있던 문제는 사용자가 명령 순서를 외우고, 각 응답에서 확인할 항목을 찾아 다음 명령에 넣어야 한다는 점이었습니다.

**변경 기록의 요지 — `33b499a`:** 기존 CLI를 Claude Code Skill로 감싸서 모델이 질문 해소 루프를 대화로 진행하게 한다. 새로운 API 표면은 추가하지 않는다. 이 변경에서 추가된 것은 주로 `SKILL.md`였고, 연동 엔진을 교체한 것이 아니었습니다.

이때의 선택을 저는 인터페이스의 문제로 봅니다. 카드 조회를 위한 연결은 이미 있었으므로, 필요한 것은 다른 연결 서버보다 결과를 설명하고 미해결 질문을 이어받는 진행자였습니다. 여러 클라이언트를 지원하기 위한 MCP의 필요성과, 한 작업 환경에서 기존 명령을 대화로 실행하는 요구는 구분할 수 있습니다. 다만 ‘MCP와 CLI를 비교 실험한 뒤 더 빨라서 선택했다’는 기록은 없습니다. 여기서 설명하는 이유는 변경 목적과 최종 구조에 대한 분석입니다.

`expense.py`는 거래·이력을 조회하고 검토안과 저장 기록을 관리합니다. `statement.py`는 지원하는 명세서 PDF를 읽습니다. `SKILL.md`는 이 명령을 호출할 순서, 질문할 기준, 사용자에게 보여줄 내용을 정합니다. CLI가 외부 AI API를 호출하지 않고 JSON을 반환하면, Claude Code가 그 결과를 읽고 대화를 이어갑니다.

이 분리는 실패 원인을 찾는 데도 도움이 됩니다. 금액 합계가 틀렸다면 파서와 검증 코드를 봅니다. 이미 정해진 날짜를 또 묻는다면 명령 순서와 Skill을 봅니다. 업무 목적을 모르는데 답을 만들어 냈다면 모델에게 준 확인 규칙과 사용자 검토 경계를 봅니다. 모두 ‘AI가 잘못했다’로 묶어 버리면 고칠 위치를 놓칩니다.

| 책임 | 담당 | 실패할 때 돌아갈 곳 |
|---|---|---|
| 요청 해석·질문 묶기 | AI, Skill의 진행 지침 | 질문 문구와 호출 순서 |
| 값·근거·미해결 상태 보존 | CLI의 검토안 | 데이터 계약과 검증 코드 |
| 이번 목적·예외·저장 의사 확인 | 사용자 | 추가 질문 또는 보류 |
| 실제 저장 상태 | 아마란스 | 저장 응답 뒤 재조회 |

검토 결과를 모델이 읽는 만큼 ‘CLI가 모델을 부르지 않는다’가 ‘업무 정보가 AI 환경에서 처리되지 않는다’는 뜻은 아닙니다. 인증정보와 원본 거래를 어떻게 전달하고 보관할지는 별도 경계로 남습니다.

## 승인 이력은 정답이 아니라 제안의 근거입니다

카드 검토안을 만들 때는 사용 기간 시작일에서 183일 전까지의 승인 이력을 조회합니다. 후보를 고르는 코드에서는 승인 완료 여부, 본인 사원 코드, 같은 회사와 카드인지 확인합니다. 기본 검색은 사업자등록번호와 가맹점명까지 맞는 이력을 찾습니다.

이렇게 범위를 좁히는 이유는 다른 사람의 분류를 이번 사용자의 기본값으로 섞지 않기 위해서입니다. 같은 식당을 이용했어도 누군가는 외부 미팅, 다른 사람은 팀 회식으로 처리했을 수 있습니다.

카드의 `prepare` 경로에서는 과거 적요·용도·프로젝트가 서로 다르거나 승인 근거가 부족하면 `history` 질문을 남깁니다. 하나의 선택지만 있고 승인 문서가 두 건 이상인 경우에는 그 값을 제안할 수 있습니다. 하지만 과거 적요에 야근·출장·회의·접대·회식처럼 이번 목적 확인이 필요한 표현이 있으면 별도의 `purpose_review`가 생깁니다.

예를 들어 합성 거래인 ‘예시모빌리티 18,000원’에 이전 야근 택시비 이력이 있어도, 이번 이동이 야근 귀가였다고 확정할 수는 없습니다. 카드 승인 시각은 택시 출발 시각을 증명하지도 않습니다. 그래서 대화는 “이전에는 야근 택시비로 처리했는데, 이번에도 같은 목적이었나요?”라는 질문으로 이어집니다.

여기에는 검색의 빈틈도 있습니다. 해외 가맹점처럼 사업자등록번호가 없는 거래는 기본 완전일치 검색에서 빠질 수 있습니다. Skill에는 이력 0건을 곧바로 ‘기록 없음’으로 해석하지 않고 가맹점명이나 적요 토큰으로 `context --query`를 다시 조회하는 절차가 있습니다. 이때도 본인·회사·카드 조건은 유지됩니다. 이는 검색 누락을 보완하는 절차이며, 다른 거래를 같은 거래라고 확정하는 장치는 아닙니다.

## 두 번째 결정: 빈칸이라고 모두 사용자에게 묻지는 않습니다

변경 이력에서 가장 구체적으로 보이는 장면은 날짜 질문입니다. 검토안에는 행마다 지급요청일 확인이 필요하다고 표시됐습니다. 하지만 이 업무의 회계처리일과 지급요청일은 이미 정해진 규칙이 있었습니다. 모델이 새 사실을 물어야 할 상황이 아니라, 규칙을 적용하는 명령이 빠진 상황이었습니다.

**변경 기록의 요지 — `f8698fe`:** 월별 진행 절차에 `dates` 호출이 없어 행별 날짜 안내가 사용자에게 물을 질문으로 읽혔다. 초안 직후 날짜를 적용하고 결과를 알리도록 Skill을 수정한다.

이 수정은 질문 문구를 더 친절하게 바꾸는 데서 끝나지 않았습니다. `prepare → inspect` 사이에 다음 호출이 들어갔습니다. 아래 경로는 합성 예시입니다.

```sh
python3 expense.py dates draft-a.json \
  --accounting-date month-end --pay-date today \
  --out draft-b.json
```

사용월 말일과 작성 시점의 한국 날짜를 적용하고, 새 검토안으로 다음 단계를 진행합니다. 사용자는 같은 날짜를 여러 행에서 다시 결정하지 않습니다. 여러 달의 거래처럼 이 규칙을 적용할 수 없는 경우에는 질문이 남습니다.

반대로 택시 출발 시각은 남겨야 하는 질문입니다. 카드 전표에 있는 결제 시각만으로는 출발 시각을 알 수 없고, 과거 야근 택시비 이력도 이번 목적을 증명하지 못합니다. 같은 커밋은 이 구분도 Skill에 명시했습니다. **줄인 것은 반복 입력 질문이고, 남긴 것은 데이터에 없는 사실에 대한 질문**입니다.

저는 이 장면에서 AI와 사람이 주고받는 단위를 ‘대답 한 번’보다 ‘어떤 종류의 불확실성인가’로 보는 편이 유용하다고 생각합니다. AI가 확인 필요 항목을 보여주면, 사람은 그 항목이 새 판단인지 기존 규칙 적용인지 구분합니다. 그 결과를 다음 실행에도 반영하려면 대화로만 끝내지 않고 Skill의 순서나 검증 코드에 남겨야 합니다. 이는 변경 결과를 읽은 구현 분석이며 당시 발언의 재현은 아닙니다.

## 세 번째 결정: 규칙 문서에도 미확정 상태가 필요했습니다

날짜 흐름을 고친 변경에서는 계정별 적요 형식과 증빙·프로젝트 규칙 문서도 추가했습니다. 과거 승인 이력이 현재 규칙과 충돌하면 규칙을 먼저 보도록 한 것입니다. 그런데 바로 다음 변경은 규칙을 더 강하게 적용하는 방향이 아니었습니다.

**변경 기록의 요지 — `962cd2d`:** 옮겨 적은 규칙 중 재경 검토가 끝나지 않은 항목이 있다. 돈의 처리 방식에 영향을 주는 미확정 항목은 문서의 권위만으로 적용하지 말고 사용자에게 묻는다. 확인된 답은 이번 행에 적용하고, 문서와 다르면 문서 수정이 필요하다고 알린다.

규칙을 정리하면 AI에게 확실한 지식을 준 것처럼 느끼기 쉽습니다. 하지만 문서화는 사실 확인과 다른 작업입니다. 이 후속 수정은 ‘과거 이력보다 문서 우선’이라는 원칙에도 예외 상태가 필요하다는 것을 보여줍니다. 제가 주목하는 결정은 내용을 더 많이 자동화한 것이 아니라, **문서에 들어갔다는 이유만으로 확정값이 되는 것을 막은 것**입니다.

이번 답변을 영구 규칙으로 승격하는 것도 분리했습니다. `edit`는 현재 검토안의 확인값을 반영하고, `rule`은 사용자가 앞으로도 적용하겠다고 명시적으로 결정할 때 개인 프로필에 기록합니다. 매번 목적이 바뀔 수 있는 식당·택시 거래에 한 번의 답변이 다음 달까지 전파되는 것을 피하려는 경계입니다.

## 대화가 끝났다는 사실을 어떻게 코드에 전달할까

질문을 자연어로만 보관하면 다음 명령은 무엇이 해결됐는지 알 수 없습니다. `inspect_plan`은 합계와 함께 `questions` 배열을 반환하고, 각 질문에 `kind`, `row`, 필요하면 `field`와 선택지를 넣습니다. 아래는 실제 필드 구조를 사용한 **합성 응답의 일부**입니다.

```json
{
  "count": 1,
  "total": 18000,
  "questions": [{
    "kind": "purpose_review",
    "row": 1,
    "field": "rmkDc",
    "current": "야근 택시비",
    "message": "이번 사용 목적 확인 필요"
  }]
}
```

`purpose_review`는 현재 적요가 비어 있다는 뜻이 아닙니다. 값은 있지만 이번 사용 목적에도 맞는지 확인되지 않았다는 뜻입니다. AI는 이 근거를 설명하고 사용자 답을 받은 뒤 `edit`로 반영합니다. 같은 값을 다시 지정하더라도 검토 완료로 기록되는 이유가 여기에 있습니다.

아래는 `inspect_plan`의 핵심 조건을 줄인 **설명용 의사코드**입니다. 실제 코드는 이미 저장된 행, 제외된 행, 명시적인 영구 규칙 등을 별도로 처리합니다.

```python
if field_not_confirmed and not explicit_personal_rule:
    if conflicting_options or approved_document_count < 2:
        questions.append(history_question)

if purpose_sensitive_description and not purpose_confirmed:
    questions.append(purpose_review)
```

이 계약으로 코드가 확인할 수 있는 것은 값과 확인 표시의 일관성입니다. 에이전트가 충분히 질문했는지, 답변이 사실인지까지 증명하지는 못합니다. 사용자 확인을 받으라는 Skill 지침과 미확인 상태를 차단하는 CLI를 함께 두되, 둘을 같은 보장으로 설명하지 않는 이유입니다.

## 합계와 행별 대응관계를 함께 봅니다

명세서 PDF를 읽는 `statement.py`는 문서를 자유롭게 해석하는 모델이 아닙니다. `pdftotext -bbox`로 글자 위치를 얻고, 지원하는 현대카드 인쇄 표의 열 제목과 위치를 이용해 이용일·가맹점·청구금액·통화를 추출합니다. 추출한 행의 건수와 금액 합계는 PDF에 적힌 총합계와 별도로 대조합니다.

그다음 명세서 행과 그룹웨어 카드 원본을 연결합니다. 날짜·가맹점·금액이 맞아도 후보가 여러 개라면 임의로 하나를 고르지 않습니다. 해외 거래는 날짜·가맹점이 연결되더라도 원화 청구액이 승인금액과 다를 수 있어 별도로 다룹니다.

예를 들어 합성 예시에서 카드 원본은 40,000원이고 PDF 청구액은 40,500원이라면, 합계를 맞추려고 원본을 지우는 대신 수정 금액과 차이, 근거 PDF의 해시·쪽·사유를 기록합니다. 원본 승인금액과 영수증 식별자는 보존합니다. 금액을 바꾼 검토안을 저장할 때에는 해당 근거 PDF 첨부도 요구합니다.

총액이 같다는 사실만으로 모든 거래가 맞는 것은 아닙니다. 두 행을 잘못 연결해도 합계는 우연히 같을 수 있습니다. 그래서 명세서 총액 확인과 개별 거래 연결 확인을 모두 거칩니다.

지원 범위는 제한적입니다. 모든 현대카드 PDF를 읽는 것은 아니며, 열 구조가 다른 이용내역 출력물이나 스캔본, 할부·사용월을 벗어난 거래는 지원 경로에서 거절될 수 있습니다. PDF 없이 카드 내역만으로 만드는 `preview` 경로도 있지만 이때는 명세서 건수·합계가 없으므로 누락 검증을 했다고 말할 수 없습니다.

## 임시보관 응답 다음에 확인할 것이 남아 있습니다

검토가 끝나면 검토용 HTML을 사람이 확인하고 `check`로 현재 서버 조건을 다시 조회합니다. 프로젝트·용도, 원본 잔액, 마감일, 카드 권한과 다른 곳에 이미 반영된 거래인지 등을 검사합니다. 검토안을 만든 시점과 저장 시점 사이에 조건이 달라질 수 있기 때문입니다.

저장 경로는 PDF 업로드, 연결키 발급, ERP 데이터 저장, 전자결재 임시보관으로 나뉩니다. 하나의 성공 응답만으로 이 모든 상태가 일치한다고 볼 수 없습니다. 그래서 `verify_saved`는 저장된 ERP의 행별 값과 임시보관 상태를 다시 읽고, 전자결재 문서가 `doc_sts=10`인지 확인합니다. 본문의 영수증 연결과 첨부 PDF도 검사하며, 다운로드한 파일의 SHA-256을 원본과 비교합니다.

이 검증이 보장하는 것도 구분해야 합니다. 같은 PDF가 저장됐다는 것은 첨부 파일의 동일성을 확인한 것이지, 그 PDF에 적힌 거래가 실제 업무였다는 증명이 아닙니다. 후자는 사용자와 재경 검토의 영역에 남습니다.

## 재개는 이전 명령의 반복이 아니라 상태의 해석입니다

네트워크 응답이 끊기면 사용자는 실패했다고 느끼지만, 서버에는 이미 저장됐을 수 있습니다. 이때 같은 요청을 다시 보내는 것은 단순한 복구가 아니라 중복 문서를 만드는 원인이 됩니다.

도구는 쓰기 전에 ‘시도 중’을 기록하고, 응답을 확인한 뒤 ‘완료’ 단계로 옮깁니다. `continue_draft`의 분기에서 중요한 것은 마지막 실행 명령보다 기록된 상태입니다.

```python
# expense.py의 상태 분기를 줄인 의사코드
if document_id or state in {"eap_attempted", "eap_saved", "verified"}:
    recover_draft()   # 연결 문서 조회 → 실제 값 검증
elif state in {"prepared", "pdf_uploaded", "link_saved", "erp_saved"}:
    continue_from_confirmed_stage()
else:
    stop_without_resending()
```

실제 구현은 이 분기 전에 연결키로 이미 생성된 문서가 있는지도 확인합니다. `pdf_upload_attempted`, `link_attempted`, `erp_attempted`에서 응답이 끊겼다면 완료를 확인하지 못했으므로 자동 재전송하지 않습니다. 전자결재 단계는 연결 문서를 찾을 수 있으면 응답 유실 뒤에도 재조회로 완료 여부를 판별합니다.

![확인된 저장 단계는 이어가고, 불명확한 쓰기는 중단하며, 이미 연결된 문서는 재조회하는 카드 재개 흐름](/assets/images/diagrams/jichool/03-card-resume.svg)
*그림 2. `resume`도 새 문서를 만드는 명령으로 단순화할 수 없습니다. 서버가 달라진 상태를 돌려주면 검증에서 중단합니다. [Mermaid 원본](/assets/images/diagrams/jichool/03-card-resume.mmd)*

여기서 포기한 것은 어떤 장애에서도 자동으로 끝내는 경험입니다. 대신 이미 저장됐을지 모르는 요청을 다시 보내지 않는 쪽을 택했습니다. 이는 상태 머신에서 확인되는 구현 선택입니다. 모든 네트워크 장애를 운영에서 재현했다는 뜻은 아니며, 로컬 기록을 다른 컴퓨터에서 잃어버린 상황까지 전역 중복을 방지하지도 않습니다.

이미 사용자가 상신하거나 상태를 바꾼 문서를 옛 임시보관 상태로 복원하지 않습니다. 임시보관 검증은 ERP와 전자결재에서 각각 기대한 상태를 확인해야 끝납니다. 사용자에게 ‘완료’라고 말할 시점은 AI가 마지막 명령을 보낸 때가 아니라, 저장 결과가 검토안과 일치한다고 확인된 때입니다.

## 어디까지 확인했는가

이번 글을 준비하면서 실제 로컬 소스와 테스트를 읽고, 네트워크 연결을 차단한 상태에서 기본 테스트를 실행했습니다. 카드 테스트에서는 사용자별 승인 이력 분리, 목적 재확인, 미확인 저장 차단, 이력 충돌과 종료 프로젝트 등의 검사가 통과했습니다. 세금계산서 모듈의 가짜 클라이언트 테스트에서는 저장 순서와 재실행 시 추가 쓰기 없음, 응답 유실 복구도 확인했습니다.

카드의 실제 PDF·저장 기록을 인수로 받는 추가 재현 테스트는 별도 경로입니다. 이번 기본 테스트 실행을 그 추가 경로까지 모두 통과한 결과로 집계하지 않았습니다. PDF 추출 구현은 소스에서 확인했고, 과거 실서버 검증 설명은 README에서 확인했습니다.

또한 기존 로컬 카드 작업 기록에서 `verified` 상태, 문서 식별자, 첨부 검증 기록의 존재를 확인했습니다. 이 기록은 과거 임시보관 검증을 뒷받침하지만, 지금 서버에 같은 상태로 남아 있다는 실시간 확인은 아닙니다. 화면 설명을 위해 기존 결재완료 문서를 읽기 전용으로 조회했으며, 임시보관 저장이나 재개 동작을 실서버에서 새로 실행하지 않았습니다. 다른 직원 계정 전반이나 모델별 판단 정확도, 처리 시간 절감률도 측정하지 않았습니다.

인증정보와 원본 거래를 다루는 경계도 남아 있습니다. 세션·검토안은 로컬 제한 권한 파일로 관리하지만, 검토안 원본에는 카드번호 등 민감한 값이 포함될 수 있습니다. 파일 권한을 제한하는 것과 자료를 공개해도 된다는 것은 다른 이야기입니다. 그래서 원본 JSON은 공개하지 않고, 구조와 합성 예시로 동작을 설명합니다. 실제 UI 참고 화면은 민감한 값을 완전히 제거한 검토본만 사용했습니다.

지출결의를 AI에게 맡기는 과정에서 결정해야 했던 것은 자동으로 채울 수 있는 칸의 수보다, 무엇을 근거로 제안하고 언제 멈출지였습니다. 조회·대조·질문·임시보관·재조회를 분리해 두니, 사용자에게 필요한 질문을 설명하고 저장 완료의 기준도 구체적으로 정의할 수 있었습니다.

지출결의를 작성할 때 시간이 드는 부분은 금액을 옮겨 적는 일만이 아닙니다. 같은 가맹점이라도 이번에는 어떤 업무에 썼는지, 어느 프로젝트에 넣어야 하는지, 지난번에는 어떻게 승인받았는지를 확인해야 합니다. 화면에 입력할 값이 모두 보이더라도 그 값의 의미까지 정해진 것은 아닙니다.

MYSC의 아마란스 지출결의 도우미 `jichool`은 이 구분에서 출발합니다. 프로그램이 조회하고 계산할 수 있는 것은 코드로 처리하고, 이번 지출의 실제 목적처럼 사용자에게 확인해야 하는 것은 대화로 남깁니다. 결과는 전자결재의 **임시보관**까지입니다. 상신·결재·지급은 이 도구가 수행하지 않습니다.

이 글은 2026년 10월 17일 확인한 로컬 구현과 테스트, 기존 작업 기록을 바탕으로 작성했습니다. 아래 거래와 대화 예시는 모두 설명을 위한 합성 예시입니다. 실제 거래처, 거래 금액, 계좌, 문서 식별자와 원본 증빙은 싣지 않았습니다. 글을 검증하기 위해 재무 시스템에 새 문서를 쓰거나 기존 문서를 변경하지도 않았습니다.

## 기존 CLI에 업무 진행 순서를 더했습니다

[앞선 글](/posts/mysc-platform-mcp-flywheel/)에서는 자체 플랫폼의 API를 여러 AI 도구에 연결하기 위해 MCP를 사용한 과정을 소개했습니다. 이번 구현에서는 지출결의 연동을 위한 MCP 서버를 추가하지 않았습니다. 이미 그룹웨어를 조회하고 임시보관할 수 있는 Python CLI가 있었고, Claude Code가 그 명령을 실행하도록 Skill을 구성했습니다.

구성은 작습니다. `expense.py`가 카드 거래와 승인 이력을 조회하고 검토안·저장 기록을 관리합니다. `statement.py`는 지원하는 카드 명세서 PDF를 읽습니다. `SKILL.md`는 이 명령을 어떤 순서로 호출하고, 결과 중 무엇을 사용자에게 물으며, 어디에서 멈춰야 하는지를 설명합니다.

CLI는 JSON 결과를 돌려주며 자체적으로 외부 AI API를 호출하지 않습니다. 대화 해석은 Claude Code 쪽에서 수행합니다. 따라서 CLI가 외부 모델을 호출하지 않는다는 사실을 업무 정보가 AI 환경에서 전혀 처리되지 않는다는 뜻으로 확대해서는 안 됩니다. 검토 결과를 모델이 읽는 구간과 로컬 프로그램이 검증하는 구간은 별개입니다.

| 구성 | 맡은 일 | 맡기지 않은 판단 |
|---|---|---|
| Skill | 명령 실행 순서, 질문 묶기, 사용자 답변 반영 | 근거 없는 업무 목적 확정 |
| CLI | 원본 조회, 금액·코드 검사, 검토안과 저장 상태 관리 | 자유로운 회계 해석 |
| 사용자 | 이번 목적과 예외 확인, 최종 문서 검토 | 프로그램 내부 명령 암기 |

이 선택의 이유는 기존 연동을 다시 만드는 대신, 이미 있는 명령과 확인 절차를 대화에 연결할 수 있었기 때문입니다. Skill은 새로운 전송 규약이 아니라 업무를 진행하는 설명서 역할을 합니다. 다만 자연어 설명만으로 모든 제약이 강제되지는 않습니다. 저장 가능 여부와 재전송 차단처럼 반드시 지켜야 할 조건은 코드에서도 검사합니다.

## 승인 이력은 정답이 아니라 제안의 근거입니다

카드 검토안을 만들 때는 사용 기간 시작일에서 183일 전까지의 승인 이력을 조회합니다. 후보를 고르는 코드에서는 승인 완료 여부, 본인 사원 코드, 같은 회사와 카드인지 확인합니다. 기본 검색은 사업자등록번호와 가맹점명까지 맞는 이력을 찾습니다.

이렇게 범위를 좁히는 이유는 다른 사람의 분류를 이번 사용자의 기본값으로 섞지 않기 위해서입니다. 같은 식당을 이용했어도 누군가는 외부 미팅, 다른 사람은 팀 회식으로 처리했을 수 있습니다.

카드의 `prepare` 경로에서는 과거 적요·용도·프로젝트가 서로 다르거나 승인 근거가 부족하면 `history` 질문을 남깁니다. 하나의 선택지만 있고 승인 문서가 두 건 이상인 경우에는 그 값을 제안할 수 있습니다. 하지만 과거 적요에 야근·출장·회의·접대·회식처럼 이번 목적 확인이 필요한 표현이 있으면 별도의 `purpose_review`가 생깁니다.

예를 들어 합성 거래인 ‘예시모빌리티 18,000원’에 이전 야근 택시비 이력이 있어도, 이번 이동이 야근 귀가였다고 확정할 수는 없습니다. 카드 승인 시각은 택시 출발 시각을 증명하지도 않습니다. 그래서 대화는 “이전에는 야근 택시비로 처리했는데, 이번에도 같은 목적이었나요?”라는 질문으로 이어집니다.

여기에는 검색의 빈틈도 있습니다. 해외 가맹점처럼 사업자등록번호가 없는 거래는 기본 완전일치 검색에서 빠질 수 있습니다. Skill에는 이력 0건을 곧바로 ‘기록 없음’으로 해석하지 않고 가맹점명이나 적요 토큰으로 `context --query`를 다시 조회하는 절차가 있습니다. 이때도 본인·회사·카드 조건은 유지됩니다. 이는 검색 누락을 보완하는 절차이며, 다른 거래를 같은 거래라고 확정하는 장치는 아닙니다.

## 모르는 항목만 질문하려면 질문도 데이터여야 합니다

필수 항목이 빠졌다는 이유만으로 매번 모든 항목을 사용자에게 물으면 대화가 입력 양식을 읽어주는 수준에 머뭅니다. 반대로 과거 값을 모두 복사하면 이번 지출의 의미가 사라집니다. 구현에서는 검토안에 값과 함께 제안 근거, 확인 여부, 미해결 질문을 보관합니다.

`inspect`가 반환하는 질문은 필수 항목 누락, 이력 충돌, 목적 재확인, 명세서 연결 실패, 금액 불일치 등으로 구분됩니다. Skill은 관련 질문을 묶어서 설명하고, 확인된 답을 `edit`나 `match`로 반영합니다. 답을 받지 못한 항목은 빈칸 또는 미해결 상태로 남습니다.

반대로 카드의 회계처리일과 지급요청일처럼 현재 업무 규칙으로 정해진 값은 매 행마다 질문하지 않습니다. 사용월 말일과 작성 시점의 한국 날짜를 적용한 뒤 사용자에게 알립니다. 여러 달의 거래처럼 규칙을 그대로 적용할 수 없는 경우에는 확인이 필요합니다.

이번 답변을 다음 달의 영구 규칙으로 자동 승격하지 않는 것도 중요합니다. 이번 검토안의 `edit`와 개인 프로필의 `rule`은 별도 명령입니다. “이번에는 프로젝트 A”라는 답변과 “앞으로도 이 가맹점은 프로젝트 A”라는 결정은 다른 데이터이기 때문입니다. 영구 규칙은 사용자가 명시적으로 결정할 때 등록하도록 Skill이 지시합니다.

**다만 코드가 확인하는 것은 확인 표시와 값의 일관성입니다.** 에이전트가 실제로 충분한 질문을 했는지, 사용자가 말한 업무 목적이 사실인지까지 증명하지는 못합니다. 명시적인 개인 규칙이 있으면 일부 재질문도 생략됩니다. 따라서 ‘모르는 항목만 묻는다’는 것은 설계한 진행 방식이며, 모델의 판단 정확도를 측정한 결과가 아닙니다.

## 합계와 행별 대응관계를 함께 봅니다

명세서 PDF를 읽는 `statement.py`는 문서를 자유롭게 해석하는 모델이 아닙니다. `pdftotext -bbox`로 글자 위치를 얻고, 지원하는 현대카드 인쇄 표의 열 제목과 위치를 이용해 이용일·가맹점·청구금액·통화를 추출합니다. 추출한 행의 건수와 금액 합계는 PDF에 적힌 총합계와 별도로 대조합니다.

그다음 명세서 행과 그룹웨어 카드 원본을 연결합니다. 날짜·가맹점·금액이 맞아도 후보가 여러 개라면 임의로 하나를 고르지 않습니다. 해외 거래는 날짜·가맹점이 연결되더라도 원화 청구액이 승인금액과 다를 수 있어 별도로 다룹니다.

예를 들어 합성 예시에서 카드 원본은 40,000원이고 PDF 청구액은 40,500원이라면, 합계를 맞추려고 원본을 지우는 대신 수정 금액과 차이, 근거 PDF의 해시·쪽·사유를 기록합니다. 원본 승인금액과 영수증 식별자는 보존합니다. 금액을 바꾼 검토안을 저장할 때에는 해당 근거 PDF 첨부도 요구합니다.

총액이 같다는 사실만으로 모든 거래가 맞는 것은 아닙니다. 두 행을 잘못 연결해도 합계는 우연히 같을 수 있습니다. 그래서 명세서 총액 확인과 개별 거래 연결 확인을 모두 거칩니다.

지원 범위는 제한적입니다. 모든 현대카드 PDF를 읽는 것은 아니며, 열 구조가 다른 이용내역 출력물이나 스캔본, 할부·사용월을 벗어난 거래는 지원 경로에서 거절될 수 있습니다. PDF 없이 카드 내역만으로 만드는 `preview` 경로도 있지만 이때는 명세서 건수·합계가 없으므로 누락 검증을 했다고 말할 수 없습니다.

## 임시보관 응답 다음에 확인할 것이 남아 있습니다

![요청을 해석한 뒤 검토와 질문을 반복하고, 임시보관 결과를 재조회해 완료 여부를 확인하는 흐름](/assets/images/diagrams/jichool/01-expense-flow.svg)
*그림 1. 각 단계의 역할을 요약한 도식입니다. 임시보관도 서버 쓰기이며, 상신·결재·지급으로 이어지는 자동 단계는 없습니다. [Mermaid 원본](/assets/images/diagrams/jichool/01-expense-flow.mmd)*

검토가 끝나면 검토용 HTML을 사람이 확인하고 `check`로 현재 서버 조건을 다시 조회합니다. 프로젝트·용도, 원본 잔액, 마감일, 카드 권한과 다른 곳에 이미 반영된 거래인지 등을 검사합니다. 검토안을 만든 시점과 저장 시점 사이에 조건이 달라질 수 있기 때문입니다.

저장 경로는 PDF 업로드, 연결키 발급, ERP 데이터 저장, 전자결재 임시보관으로 나뉩니다. 하나의 성공 응답만으로 이 모든 상태가 일치한다고 볼 수 없습니다. 그래서 `verify_saved`는 저장된 ERP의 행별 값과 임시보관 상태를 다시 읽고, 전자결재 문서가 `doc_sts=10`인지 확인합니다. 본문의 영수증 연결과 첨부 PDF도 검사하며, 다운로드한 파일의 SHA-256을 원본과 비교합니다.

이 검증이 보장하는 것도 구분해야 합니다. 같은 PDF가 저장됐다는 것은 첨부 파일의 동일성을 확인한 것이지, 그 PDF에 적힌 거래가 실제 업무였다는 증명이 아닙니다. 후자는 사용자와 재경 검토의 영역에 남습니다.

## 중단된 쓰기를 무조건 다시 보내지 않습니다

네트워크 응답이 끊기면 사용자는 실패했다고 느끼지만, 서버에는 이미 저장됐을 수 있습니다. 이때 같은 요청을 다시 보내는 것은 단순한 복구가 아니라 중복 문서를 만드는 원인이 됩니다.

도구는 단계마다 로컬 작업 기록을 남깁니다. 업로드나 연결키 발급, ERP 저장을 시도한 뒤 응답이 확인되지 않은 상태는 각각 `pdf_upload_attempted`, `link_attempted`, `erp_attempted`로 구분합니다. 이런 상태에서는 자동 재전송을 멈춥니다. 전자결재 저장 응답을 잃었더라도 연결된 문서를 조회할 수 있으면 실제 저장 여부를 확인하는 경로가 있습니다.

따라서 재개는 처음부터 다시 실행한다는 뜻이 아닙니다. 확인된 단계는 이어가고, 불명확한 쓰기는 확인할 때까지 보류합니다. 이미 사용자가 상신하거나 상태를 바꾼 문서를 옛 임시보관 상태로 되돌리지도 않습니다. 로컬 기록과 서버 확인에 의존하므로 여러 컴퓨터를 오가는 상황까지 전역적으로 중복을 막는 설계라고 설명할 수는 없습니다.

## 어디까지 확인했는가

이번 글을 준비하면서 실제 로컬 소스와 테스트를 읽고, 네트워크 연결을 차단한 상태에서 기본 테스트를 실행했습니다. 카드 테스트에서는 사용자별 승인 이력 분리, 목적 재확인, 미확인 저장 차단, 이력 충돌과 종료 프로젝트 등의 검사가 통과했습니다. 세금계산서 모듈의 가짜 클라이언트 테스트에서는 저장 순서와 재실행 시 추가 쓰기 없음, 응답 유실 복구도 확인했습니다.

카드의 실제 PDF·저장 기록을 인수로 받는 추가 재현 테스트는 별도 경로입니다. 이번 기본 테스트 실행을 그 추가 경로까지 모두 통과한 결과로 집계하지 않았습니다. PDF 추출 구현은 소스에서 확인했고, 과거 실서버 검증 설명은 README에서 확인했습니다.

또한 기존 로컬 카드 작업 기록에서 `verified` 상태, 문서 식별자, 첨부 검증 기록의 존재를 확인했습니다. 이 기록은 과거 임시보관 검증을 뒷받침하지만, 지금 서버에 같은 상태로 남아 있다는 실시간 확인은 아닙니다. 이번 발행 과정에서는 재무 시스템을 새로 호출해 검증하지 않았습니다. 다른 직원 계정 전반이나 모델별 판단 정확도, 처리 시간 절감률도 측정하지 않았습니다.

인증정보와 원본 거래를 다루는 경계도 남아 있습니다. 세션·검토안은 로컬 제한 권한 파일로 관리하지만, 검토안 원본에는 카드번호 등 민감한 값이 포함될 수 있습니다. 파일 권한을 제한하는 것과 자료를 공개해도 된다는 것은 다른 이야기입니다. 그래서 이 글에는 원본 JSON이나 화면 캡처 대신 구조와 합성 예시만 담았습니다.

지출결의를 AI에게 맡기는 과정에서 결정해야 했던 것은 자동으로 채울 수 있는 칸의 수보다, 무엇을 근거로 제안하고 언제 멈출지였습니다. 조회·대조·질문·임시보관·재조회를 분리해 두니, 사용자에게 필요한 질문을 설명하고 저장 완료의 기준도 구체적으로 정의할 수 있었습니다.

회의록을 검색하다 보면 관련 문장은 찾았는데 정작 궁금한 점은 풀리지 않을 때가 있습니다. 그 자리에서 나온 의견인지, 실제로 진행하기로 한 결정인지 알기 어려운 경우입니다.

“검토해보자”와 “검토가 끝나면 도입하기로 했다”는 비슷해 보여도 뜻이 다릅니다. 다음 회의에서 결정이 바뀌기도 하고, Slack에서는 결정한 이유가 본문보다 댓글에 더 자세히 남기도 합니다. 이런 기록을 바탕으로 답하려면 단어가 비슷한 문장을 찾는 것만으로는 부족했습니다.

MYSCdoc에서는 회의록과 Slack에서 사람·조직·결정 사항을 추출해 서로 연결하고, 그 정보를 찾아 답하는 AI를 실험했습니다. Gemini로 동작하던 기능을 기준으로 삼아 EXAONE 1.2B에도 추출, 검색, 답변을 학습시켰습니다.

AI와 함께 코드를 작성하고 실험을 반복하자 점수는 올라갔습니다. 그런데 실제 답변을 읽어보면 놓친 문제가 있었습니다. 답할 수 있는 질문을 거절하거나, 엉뚱한 문서의 숫자를 가져와 답했습니다. **점수가 오른 이유를 설명하는 일과, 이 모델을 서비스에 써도 되는지 판단하는 일은 달랐습니다.**

이 글에서는 2026년 7월 27–31일에 진행한 V1부터 V10까지의 실험을 따라갑니다. 각 버전에서 무엇을 기대했고, 어떤 결과 때문에 방향을 바꿨는지 살펴보겠습니다. 본문의 V1–V10은 답변과 중요도 판단을 학습한 실험 이름입니다. 추출기와 등급 판정기에도 별도 버전이 있으며, 실험마다 평가 데이터가 달라 모든 점수를 한 줄로 비교할 수는 없습니다.

실험 기록을 다시 확인하면서 나중에 잘못된 것으로 밝혀진 결과도 반영했습니다. 누가 먼저 제안했는지 남아 있지 않은 부분은 대화로 꾸미지 않고, 실제로 바꾼 내용과 판단 근거를 중심으로 정리했습니다.

## 어떤 모델에 어떤 일을 맡겼을까

같은 LLM이라도 맡은 일은 달랐습니다. 원문에서 정보를 뽑는 모델, 학습 데이터를 만드는 모델, 질문에 답하는 모델, 그 답을 채점하는 모델을 구분했습니다. 학습 데이터를 만들어 주는 쪽을 교사 모델, 그 데이터로 학습하는 쪽을 학생 모델이라고 부르겠습니다.

| 역할 | 모델·방법 | 맡긴 일 |
|---|---|---|
| 비교 기준 | Gemini 2.5 Flash | 회의록·Slack의 구조화된 추출 |
| 학생 모델 | EXAONE 4.0-1.2B | 추출, 검색 질의 재작성, 근거 기반 답변 |
| 학습 데이터 생성·보조 평가 | EXAONE 32B | 학습용 답변 생성, 확정도·응답 유형 판정 |
| 중요도 학습 데이터 생성 | Gemini | 같은 문맥에서 두 사실의 중요도 비교 |
| 학습 방법 | LoRA r16, 검색 과제의 GRPO | 과제별 소형 모델 학습 |

초기 추출 비교에서는 Gemini 2.5 Flash의 thinking budget과 temperature를 모두 0으로 설정했습니다. 두 모델에 문서를 나누는 방식과 프롬프트를 동일하게 적용하고, 정해진 JSON 형식으로 출력하도록 했습니다. 한쪽에만 출력 형식을 강제하면 모델 자체의 차이를 비교하기 어렵습니다. 실제로 이런 조건 차이가 있었던 비교 결과는 제외했습니다.

학습과 평가에는 H100 80GB 두 장을 사용했습니다. LoRA는 모델 전체 대신 일부 추가 파라미터를 학습하는 방법으로, 이 실험에서는 rank를 16으로 설정했습니다. 초기 소규모 1.2B 학습은 약 6–12분 걸렸습니다. 이후 학습 데이터가 25,000건으로 늘고 여러 작업이 GPU를 함께 사용한 V6에서는 훨씬 오래 걸렸습니다.

같은 입력 조각 524개를 처리하는 데 걸린 시간은 서버 GPU의 EXAONE 87초, Gemini API 220초였습니다. 서버 GPU에서 측정한 결과이므로 노트북에서도 같은 속도가 나온다고 볼 수는 없습니다. Apple M5에서는 MLX Q8 형식으로 모델을 변환하는 데 성공했지만, 당시 메모리가 부족해 속도를 제대로 측정하지 못했습니다. 이 연구에서 API 호출료가 없다는 말도 GPU·운영 비용까지 0원이라는 뜻은 아닙니다. 모델 도입에는 EXAONE 배포본의 비상업 라이선스 조건도 별도로 고려해야 했습니다. [모델 구성과 실행 시간 기록][compute]

## 누가 무엇을 결정했는지만 저장하면 부족했습니다

먼저 무엇을 저장해야 할지부터 정해야 했습니다. 다음은 구조를 설명하기 위해 만든 예시입니다.

> A팀은 보안 검토가 끝나면 B 서비스를 도입하기로 했다. 비용 때문에 C 서비스는 제외했다.

`A팀 → 도입한다 → B 서비스`만 저장하면 조건과 제외 이유가 사라집니다. 이미 도입했다는 뜻인지도 불분명합니다. 그래서 결정 하나를 별도의 노드로 만들고, 누가 내린 결정인지, 대상과 값은 무엇인지, 어떤 이유와 조건이 있었는지, 어떤 대안을 제외했는지 연결했습니다. 이렇게 사람·조직·서비스처럼 식별할 대상을 엔티티로, 대상 사이의 연결을 관계로 표현한 것이 지식그래프입니다.

![결정 사건 모델링과 가중치 역산 폐기의 의사결정 트리](/assets/images/diagrams/myscdoc-decisions/01-entity.svg)
*그림 1. 결정에 조건과 이유를 붙여 저장했습니다. 같은 주제의 두 기록이 같은 결정을 가리키는지는 여전히 판단해야 합니다. [Mermaid 원본](/assets/images/diagrams/myscdoc-decisions/01-entity.mmd)*

관계 자체를 하나의 대상으로 만들고 여러 참여자·속성을 붙인다는 점에서 W3C의 **n-ary relation** 패턴과 비교할 수 있습니다. 다만 이 패턴을 참고했다는 것과 OWL 기반 추론 체계를 구현했다는 것은 다릅니다. MYSCdoc은 주어·관계·목적어로 이뤄진 기록인 트리플을 PostgreSQL에 저장합니다. [W3C n-ary relations](https://www.w3.org/TR/swbp-n-aryRelations/)

구현에서 사용한 `결정:주제`라는 이름은 읽기 쉽습니다. 하지만 이름이 같다고 같은 결정은 아닙니다. 서로 다른 날 같은 주제를 논의했다면 기존 결정을 확인한 것인지, 새로 바꾼 것인지 구분해야 합니다. 같은 사람이나 조직의 여러 이름을 정리하는 문제와, 두 기록이 같은 사건을 가리키는지 판단하는 문제를 따로 다뤄야 했습니다.

이 지점에서 **LLMEA**의 엔티티 정렬 연구가 비교 대상이 됩니다. LLMEA는 서로 다른 지식그래프의 엔티티가 같은 대상을 가리키는지 판단하는 문제를 다룹니다. 우리에게는 별칭과 중복 엔티티를 연결하는 질문에 가깝습니다. 다만 같은 대상을 찾았다고 해서 발언이 얼마나 확정적인지, 왜 그런 결정을 내렸는지까지 알 수 있는 것은 아닙니다. [LLMEA 논문](https://arxiv.org/html/2401.16960v1)

관련 연구를 실제 설계 질문에 대응시키면 다음과 같습니다.

| 연구·패턴 | 우리에게 연결되는 질문 | 대신 해결해주지 않는 것 |
|---|---|---|
| W3C n-ary relations | 조건·이유·참여자를 하나의 결정에 어떻게 붙일까 | 사건 ID와 변경 이력 정책 |
| LLMEA | 서로 다른 표기의 엔티티가 같은 대상인가 | 발언이 결정인지, 누구의 결정인지 |
| AutoSchemaKG | 엔티티·사건·개념과 스키마를 어떻게 조직할까 | 발언 주체와 관계를 정확히 연결하는 일 |
| RAFT | 근거와 방해 문서가 함께 있을 때 무엇을 읽을까 | 정답 근거가 전혀 없을 때의 거절 보장 |

## 작은 모델의 한계라고 생각했는데, 입력부터 잘못돼 있었습니다

처음에는 최대 24,000자의 문서 전체를 1.2B 모델에 넣었습니다. 모델이 같은 내용을 반복해서 생성했고, 너무 작은 모델을 선택한 것이 아닌지 의심했습니다. 더 큰 모델로 바꾸기 전에, 긴 입력을 제대로 처리하고 있는지부터 확인했습니다.

문단 경계로 약 1,000자씩 나누자 기록상 반복 생성이 12건에서 2건으로 줄었습니다. 학습 데이터 160건 중 12건에서는 길이 제한 때문에 정답 문장의 끝이 잘렸습니다. 문장의 끝을 알리는 EOS 토큰까지 사라진 상태였습니다. 입력과 정답을 합친 학습 시퀀스의 최대 길이를 8,192에서 20,480토큰으로 늘리자 잘리는 사례가 없어졌습니다. 모델 크기의 한계를 따지기 전에 바로잡아야 할 문제가 있었던 셈입니다.

출처도 원문을 베껴 쓰게 하는 방식에서 문장 번호를 선택하는 방식으로 바꿨습니다. 근거가 원문의 어느 문장인지 확인할 수 있는 비율은 94%에서 100%로 올랐습니다. 다만 학습할 때는 문장 내용을 주고 실제 추론할 때는 번호를 주는 실수도 있었습니다. 입력 방식이 달라 해당 학습 결과를 버리고 다시 맞춰야 했습니다.

그렇다고 **인용한 문장을 찾을 수 있다는 사실만으로 답변이 맞다고 할 수는 없습니다.** 원문에 실제로 있는 문장도 잘못 해석할 수 있기 때문입니다. 처음에는 인용을 의무화해도 원문 일치율이 떨어지지 않았으니 잘못된 답변이 늘지 않았다고 생각했습니다. 하지만 이 지표로는 그런 오류를 잡을 수 없었고, 해당 결론을 철회했습니다.

한국어 어미로 결정 문장을 걸러내는 필터에서도 비슷한 문제가 생겼습니다. “하기로 했다”, “하도록 한다” 같은 형태를 통과시키자 형태소 기반 지표가 올랐습니다. 그러나 사람이 판정한 50건과 비교하니 상관계수는 φ=0.034로 거의 관련이 없었습니다. 사람이 맞다고 본 결과도 상당수 걸러졌습니다. 이 지표가 잘 잡아낸 것은 사실의 정확성보다 특정 어미를 쓰는 문체였습니다.

그래프에 들어오지 않은 사실은 뒤의 검색기가 복구할 수 없습니다. 따라서 더 엄격한 필터라는 이유만으로 채택하지 않았습니다. Gemini가 228개, 소형 모델이 165개를 추출한 비교 역시 전체 정답 목록이 없으므로 추출량의 차이로만 읽어야 합니다. [추출 실험 기록][loops]

### V1. 확정된 결정과 검토 중인 의견을 구분할 수 있을까

V1에서는 추출한 사실에 확정·예정 등의 등급을 붙이고, 답변에서도 이를 구분하도록 학습시켰습니다. 그런데 학습용 답변을 만드는 32B 교사 모델부터 등급을 놓쳤습니다. 당시 네 가지 표현으로 등급 반영 여부를 확인했을 때 반영률은 67%였습니다. 학생 모델을 학습시키기 전에, 교사가 만든 답변에 우리가 원하는 구분이 담겼는지 확인해야 했습니다.

이때 확정도와 중요도를 섞은 데이터 오류도 드러났습니다. `weight = 확정도 × 중요도`로 만든 값을 다시 구간으로 잘라 확정도를 복원하고 있었습니다. 작은 값이 낮은 확정도 때문인지 낮은 중요도 때문인지 구별할 수 없는데도 역산한 것입니다. 원래 판정과 대조하니 940건 중 258건에 잘못된 라벨이 붙어 있었습니다. `[조건부]`로 분류한 229건도 모두 잘못 분류된 사례였습니다.

다음 선택은 모델을 키우는 대신 원래 등급을 직접 보관하고 읽는 것이었습니다. 조건 여부도 확정도의 중간 단계가 아닌 별도 축으로 다뤘습니다. “조건을 만족하면 진행하기로 확정한 결정”과 “진행을 검토 중인 제안”을 구분하기 위해서입니다. [등급 설계][grades]

### V2. 관련 있어 보여도 답이 없는 질문을 가르치기

교사 모델에게 왜 그 등급인지 설명하도록 하자, 같은 네 가지 표현으로 측정한 반영률이 67%에서 93%로 올랐습니다. V2에는 이 설명과 함께, 관련된 정보는 있지만 질문에는 답할 수 없는 사례를 추가했습니다. V1은 274개, V2는 449개의 학습 데이터를 사용했고, 전체 데이터를 여섯 번씩 학습했습니다(6 epoch).

답할 수 없는 사례는 정답 노드를 제거하고, 관련 있어 보이는 주변 사실은 남기는 방식으로 만들었습니다. 모델이 헷갈리기 쉬운 이런 사례를 hard negative라고 합니다. 그러나 **정답 노드를 제거했다고 답할 수 없는 질문이 되는 것은 아니었습니다.** 주변 사실에 답의 단서가 남아 있는 경우가 있었습니다.

평가기에도 문제가 있었습니다. “없어요”가 포함됐다는 이유로 거절로 세면, 한계를 먼저 설명한 뒤 정상적으로 답한 문장까지 거절이 됩니다. 교사가 만든 정상 답변 47건 중 28건을 이런 식으로 잘못 셌습니다. 이후에는 32B 모델이 답변의 의미를 읽고 판정하도록 바꿨습니다. 다만 그 판정이 사람과 얼마나 일치하는지는 아직 검증하지 못했으므로, 새 평가 결과도 그대로 믿을 수는 없었습니다. [V2 데이터와 평가 재검토][audit]

### V3. 아는 만큼 답하라고 했는데, 더 자주 거절했습니다

V3에서는 근거로 확인할 수 있는 내용만이라도 답하도록 지시하고, 학습에 적합하지 않은 답변을 걸러냈습니다. 답할 수 있는데도 거절하는 문제, 즉 과잉거절을 줄이려는 시도였습니다. 처음에는 종합 점수가 0.698에서 0.773으로 오른 것처럼 보였습니다. 하지만 서로 다른 평가셋의 수치였습니다. 같은 281건으로 두 모델을 다시 평가하니 V2 0.763, V3 0.773으로 차이가 작아졌습니다. 이 수치에 사용한 정답 라벨도 이후 수정됐으므로, 최종 성능을 나타내는 값으로 보기는 어렵습니다.

필터의 방향도 점검했습니다. 거절 후보 364건에서 230건을 제외하는 과정에 부분답변 155건이 모두 포함됐습니다. 잘못된 답변을 걸러내려다, 일부만 답하는 사례까지 없애버린 셈입니다. 그 결과 모델이 “애매하면 거절하라”고 배웠을 가능성을 의심했습니다. 다만 필터의 영향만 따로 실험하지 않았으므로 원인으로 단정하지는 않았습니다.

어느 시점의 모델을 선택할지 정하는 점수도 살펴봤습니다. 학습 도중 저장한 모델을 체크포인트라고 하는데, 저희는 Honesty라는 점수로 체크포인트를 골랐습니다. Honesty는 적절한 거절 비율 P와 과잉거절 비율 C를 `0.5 × (P + 1 − C)`로 합칩니다. 두 오류에 같은 무게를 두면 답할 수 있는 질문까지 많이 거절하는 체크포인트가 선택될 수 있습니다.

그 뒤 281개 사례를 다시 판정했을 때 답변 가능·불가 라벨 91건이 뒤집혔습니다. V2 후반 체크포인트를 서비스 적용 후보로 삼자는 판단도 다시 검토했습니다. 테스트 결과를 보고 나서 고른 모델이니, 별도의 데이터에서 다시 확인해야 했습니다. **가능성이 있는 후보로 남기되, 검증이 끝났다고 보지는 않기로 했습니다.** 학습을 더 진행하기 전에 정답 라벨과 모델 선택 기준부터 바로잡아야 했습니다.

### V4. 정답의 근거 하나만 빼보면 어떨까

V4에서는 같은 질문에 정답을 결정하는 사실 하나만 넣었다 뺐다 해봤습니다. 근거가 있으면 답하고, 없으면 답하지 못하도록 입력을 한 쌍으로 만든 것입니다. 비교 기준 모델의 학습 데이터 중 답변 가능·불가 사례 각 32건을 이렇게 만든 32쌍으로 교체했습니다. 두 모델은 같은 난수 시드와 학습 설정으로 342 step을 학습했습니다.

학습 전 점검에서는 데이터 중복도 발견했습니다. 오류를 점검하기 위한 질문 232개 중 108개, 모델을 선택하기 위한 질문 167개 중 42개가 학습·개발 데이터와 겹쳤습니다. 이미 학습한 질문으로 평가하면 점수를 신뢰하기 어려워, 해당 평가 데이터를 버리고 다시 만들었습니다.

새로운 쌍을 학습한 모델은 답이 없을 때 더 잘 거절했지만, 답할 수 있는 질문도 함께 거절했습니다. 과잉거절로 판정된 43건을 전수 검토하자 정당한 거절 6건, 모호한 사례 5건, 명백한 과잉거절 32건이 나왔습니다. 잘못된 판정을 고치거나 모호한 사례를 제외해도, 새로운 쌍을 학습한 모델의 과잉거절 비율은 20.5–23.0%였습니다. 비교 기준 모델의 3.8–4.3%보다 높았습니다. 한 사람이 다시 판정한 결과이므로 확정적인 정답이라고 할 수는 없지만, 판정 오류를 고려해도 결론이 달라지는지 확인할 수 있었습니다.

미리 정한 기준을 통과한 모델이 없어, 최종 확인용으로 따로 남겨둔 150쌍은 평가에 사용하지 않았습니다. 이처럼 모델 선택 과정에서 보지 않도록 분리한 데이터를 실험 기록에서는 봉인 평가셋이라고 부릅니다. 이후 V4b에서는 정답 사실의 유무로 답변 가능 여부를 정할 수 있는 데이터를 쓰기로 계획했습니다. 이 단계는 실험 결과가 아니라 후속 설계로 남아 있습니다. [V1–V4 실험과 정정][loops]

### V5. 100%를 기록한 모델의 답변을 직접 읽어봤습니다

Slack 스레드 650개를 학습용 455개, 개발용·모델 선택용·최종 평가용 각각 65개로 나눴습니다. 같은 스레드가 서로 다른 용도에 섞이지 않도록 출처 단위로 분리했습니다. 교사 모델이 만든 질문·답변 중 826건이 검증을 통과했습니다. 그런데 782건이 핵심(core), 788건이 확정(confirmed)으로 분류돼 있었습니다. 거의 모든 내용이 중요하고 확정적이라고 돼 있으니, 무엇을 더 중요하게 봐야 하는지 학습하기 어려웠습니다.

그래서 같은 문맥에서 두 사실 중 무엇이 더 중요한지 알려주고, 제시 순서도 바꿔가며 학습시켰습니다. 원래 목표는 중요한 내용을 스스로 골라 요약하는 것이었지만, 이번 실험은 **알려준 중요도에 맞춰 답할 수 있는지** 확인하는 데 집중했습니다. 목표를 좁혔다는 사실도 결과를 해석할 때 함께 고려했습니다.

근거와 방해 문서를 함께 읽게 하는 RAFT 방식과, 중요도 지시를 따르게 하는 방식을 비교했습니다. 두 조건은 공통 데이터 676건에 각 방식에 해당하는 데이터 128건을 더해 각각 804건으로 맞췄습니다. seed 42, 2 epoch, 학습률 `2e-4`, 최종 202 step을 사용했습니다. 다만 어떤 체크포인트를 고를지는 처음부터 정하지 못했습니다. 모델 선택용 평가 결과를 본 뒤, 최종 평가 전에 202 step 모델을 쓰기로 정했습니다. 결과를 보기 전에 모든 기준을 정한 실험은 아니었다는 점을 함께 남깁니다.

정답 근거가 없는 입력을 no-oracle이라고 부릅니다. 이런 입력에서 답변을 거절하는지 자동으로 평가한 점수는 초기 모델 44.1%에서 두 학습 모델 모두 100%가 됐습니다. 하지만 평가기는 정확히 `(근거 부족)`이라는 문구를 요구했습니다. 자연어로 제대로 거절한 초기 모델은 오답이었습니다.

34건을 전부 읽자 실제 거절은 초기 모델 33/34, 학습 모델 34/34였습니다. 개선은 55.9%p가 아니라 2.9%p였습니다. 무작위로 뽑은 답변 20건의 내용도 확인했습니다. 정답 자체가 잘못된 2건을 제외하고, 핵심 내용을 정확히 답한 건수는 초기 모델 16/18, RAFT 11/18, 중요도 조건 14/18이었습니다.

작은 표본으로 전체 우열을 확정할 수는 없습니다. 그러나 “챗봇이 크게 좋아졌다”는 해석을 받아들이지 않을 이유는 충분했습니다. 다음 실험에서는 업무 데이터와 함께 일반 대화 데이터를 다시 학습시키기로 했습니다. 원래 잘하던 답변을 잊지 않도록 기존 유형의 데이터를 섞는 방식으로, replay라고 부릅니다.

### V6. 기존보다 좋아졌지만 Gemini에는 미치지 못했습니다

| 설정 | V6 |
|---|---|
| 데이터 | 일반 한국어 20,000 + Slack QA 2,500 + 중요도 2,500 |
| 비율 | 80 / 10 / 10 |
| 학습 | LoRA r16, 2 epoch, lr `2e-4` |
| 반복 | seed 42와 43 |
| 평가 대상 | 6,250 step의 최종 체크포인트로 미리 결정 |

중요도 학습에는 Gemini가 두 사실의 우선순위를 구분한 306쌍을 사용했습니다. 평가용 정답은 모델의 답변을 보기 전에 정했습니다. 판단이 모호한 5개 그룹을 제외하고, 39개 그룹에 담긴 사실 101개를 사용했습니다. 다만 한 사람이 정한 정답이므로 평가자마다 중요도를 다르게 볼 수 있다는 한계는 남습니다.

성공 기준도 미리 정했습니다. 두 사실 중 무엇이 더 중요한지 맞힌 비율(pair accuracy)이 Gemini보다 높아야 했습니다. 우연히 점수가 높아진 것은 아닌지 확인하기 위해, 같은 평가 항목을 짝지어 반복 추출하는 paired bootstrap으로 두 모델의 차이를 계산했습니다. 그 차이의 95% 신뢰구간 하한도 0보다 커야 성공으로 보기로 했습니다.

| 모델 | 중요도 순서 정확도 | JSON 파싱 실패 그룹 |
|---|---:|---:|
| 초기 모델 | 0.442 | 5 |
| Gemini direct | 0.833 | 0 |
| V6 seed42 | 0.744 | 0 |
| V6 seed43 | 0.750 | 0 |

학습 전보다 좋아졌지만, 목표로 삼은 Gemini의 성능에는 미치지 못했습니다. 개선 폭이 크더라도 처음 정한 성공 기준을 바꾸지는 않았습니다. 두 시드 모두 일정·금액처럼 구체적인 정보를 회의의 핵심 결정이나 문제보다 중요하게 보는 오류가 반복됐습니다.

### V7. 데이터는 그대로 두고 학습률을 낮춰봤습니다

V7은 80/10/10 비율을 유지하고 학습률 `1e-4`, `5e-5`를 비교했습니다. seed 42, 2 epoch, 최종 6,250 step을 사용했습니다. `1e-4` 조건의 중요도 순서 정확도가 0.795로 가장 높았습니다.

Gemini와의 차이는 줄었지만 점수는 여전히 낮았습니다. 신뢰구간에 0이 포함돼 차이가 있다고 단정하기 어려워졌지만, 두 모델의 성능이 같다고 확인한 것은 아닙니다. 시험한 설정 중에서는 가장 나았으므로, 후속 답변 실험은 V7에서 시작하기로 했습니다.

### V8. 업무 데이터를 더 넣으면 나아질까

V8은 일반/Slack QA/중요도 비율을 70/15/15로 바꾸고 같은 두 학습률을 비교했습니다. 가장 높은 중요도 순서 정확도는 0.782였습니다. 업무 데이터의 비중을 높인다고 더 좋아지지는 않았습니다.

이 결과를 해석할 때는 같은 39개 그룹으로 여러 설정을 비교했다는 점도 고려해야 합니다. 최종 체크포인트를 미리 정했더라도, 같은 평가 데이터에 맞춰 설정을 고르는 일이 반복됐기 때문입니다. 여기서 고른 모델의 성능은 새로운 데이터로 다시 확인할 필요가 있습니다. [V5–V8 실험 기록][loops]

## V9–V10: 잘 답하는 것만큼, 답하지 않을 때를 아는 것도 중요했습니다

*그림 4. 대화를 이어가는 능력은 좋아졌지만, 근거가 없을 때 답하지 않는 능력이 떨어져 모델을 교체하지 않았습니다. [Mermaid 원본](/assets/images/diagrams/myscdoc-decisions/04-v9-v10.mmd)*

### V9. 답을 외운 걸까, 엉뚱한 근거를 읽은 걸까

V7·V8은 정답 근거가 있을 때는 잘 답했습니다. 문제는 질문과 관계없는 문서를 줘도 답한다는 점이었습니다. 학습 때 본 답을 외워서 말하는 것인지 확인하려고 같은 질문에 세 가지 입력을 붙였습니다. 정답이 있는 원문, 다른 출처의 무관한 문서, 원문의 날짜나 숫자 하나를 바꾼 문서입니다. 마지막처럼 사실을 의도적으로 바꿔 반응을 확인하는 것을 반사실 실험이라고 합니다. 질문 30개에 입력을 세 가지씩 붙여 응답 90개를 비교했습니다.

| 모델 | 원문의 값으로 답함 | 무관한 문서에서 답변 거절 | 바꾼 값으로 답함 |
|---|---:|---:|---:|
| 초기 모델 | 26/30 | 17/30 | 25/30 |
| V7 | 29/30 | 2/30 | 29/30 |
| V8 | 29/30 | 2/30 | 29/30 |

이 평가에서 원래 값을 고집한 사례는 없었습니다. 모델은 바뀐 문맥을 읽고 있었습니다. 문제는 **그 문맥이 질문의 대상에 관한 것인지 판단하지 않고 값을 가져온 것**이었습니다.

V9는 V7의 학습 결과를 기본 모델에 합친 뒤 시작했습니다. 일반 대화·질문 답변·중요도 데이터를 계속 섞으면서, 정답 근거가 없는 사례를 10%(400/4,000) 또는 15%(600/4,000) 넣었습니다. 학습률 `2e-5`로 전체 데이터를 한 번 학습했고(1 epoch), 500 step에서 마쳤습니다.

| 모델 | 원문의 값으로 답함 | 무관한 문서에서 답변 거절 | 바꾼 값으로 답함 |
|---|---:|---:|---:|
| V9 neg10 | 28/30 | 28/30 | 28/30 |
| V9 neg15 | 27/30 | 29/30 | 28/30 |

15% 조건은 무관 근거를 한 건 더 거절했지만, 별도 V5 평가에서는 답할 수 있는데 거절한 사례가 4/84로 neg10의 3/84보다 한 건 많았습니다. 추가로 검증할 후보로는 neg10을 남겼습니다. 적은 표본에서 한 건 차이로 고른 것이므로, 어떤 데이터에서나 10%가 가장 좋다고 해석할 수는 없습니다.

중요도 순서를 맞힌 비율은 V7의 0.795에서 neg10 0.756, neg15 0.769로 낮아졌습니다. 그래서 질문 답변용으로는 V9를, 중요도 분석용으로는 V7을 남겼습니다. 실제 서비스에서 사용하던 Gemini는 교체하지 않았습니다.

### V10. 대화는 더 잘 이어갔지만, 엉뚱한 답변이 다시 늘었습니다

V10은 V9 neg10에서 시작해 일반 대화 19,500, Slack QA 3,500, 같은 스레드에서 두 차례 질문과 답변을 이어가는 데이터 1,000, 중요도 복습 데이터 1,000건을 사용했습니다. 이렇게 앞선 대화를 이어가는 방식을 멀티턴이라고 합니다. 두 조건 모두 seed 42, 학습률 `1e-5`로 1 epoch 학습했습니다. 결과를 보기 전에 최종 3,125 step의 모델로 평가하기로 정했습니다.

차이는 Slack QA에 정답 근거만 넣는 MT와, 정답 근거에 헷갈리기 쉬운 방해 문서를 함께 넣는 MT-RAFT였습니다. RAFT는 관련 문서와 방해 문서가 섞였을 때 근거를 활용하도록 학습하는 접근입니다. 그러나 정답이 있는 묶음에서 방해 문서를 무시하는 능력이, 정답이 전혀 없는 상황의 거절까지 보장하지는 않습니다. [RAFT 논문](https://arxiv.org/html/2403.10131v1)

| 모델 | 연속 대화에서 내용·인용 모두 정답 | 무관한 문서에서 답변 거절 |
|---|---:|---:|
| V9 neg10 | 33/42 | 28/30 |
| V10-MT | 37/42 | 14/30 |
| V10-MT-RAFT | 38/42 | 17/30 |

대화를 이어가는 능력은 좋아졌습니다. 하지만 V9에서 줄였던 오류가 다시 늘었습니다. 다른 기록에 있던 날짜와 금액을 질문 속 다른 대상의 값으로 붙이는 오류였습니다. 답이 근거 어딘가에 실제로 등장한다는 이유만으로 안전한 응답이 되지는 않았습니다.

32B의 A/B 판정도 최종 결정에 쓰지 않았습니다. 응답 순서를 뒤집었을 때 160건 중 판정 불일치가 MT 107건, MT-RAFT 122건이었습니다. 내용이 같아도 순서에 따라 판단이 이렇게 달라진다면, 이 점수로 모델을 고르기는 어려웠습니다.

두 V10 모델은 서비스에 적용하지 않고 V9 neg10을 검증 후보로 유지했습니다. 다음에는 연속 대화 데이터와 함께, 정답 근거가 없어서 답하지 말아야 하는 사례도 학습에 넣어보기로 했습니다. 이 방향은 아직 다음 실험 계획으로 남아 있습니다. [V9–V10 실험 기록][loops]

## 관계를 더 많이 추출하면 더 좋은 그래프가 될까

답변을 잘하려면 먼저 저장된 정보가 정확해야 합니다. 그래서 답변 모델을 학습하는 것과 별도로, 원문에서 정보를 추출하는 방식도 바꿔봤습니다. 이때 온톨로지는 어떤 종류의 대상이 있고 그 사이에 어떤 관계를 허용할지 정한 규칙을 뜻합니다.

먼저 원문에서 후보를 추출하고, 다음 단계에서 기존 그래프와 연결하며 검증하도록 나눴습니다. 엔티티 유형과 관계는 정해진 목록에서만 고르게 했습니다. 추출한 내용마다 실제로 어느 메시지에서 나온 것인지 확인할 수 있도록 메시지 시각도 요구했습니다.

AutoSchemaKG는 엔티티·사건·개념을 추출하고 동적으로 스키마를 유도하는 연구입니다. 이와 비교해 우리의 실험은 도메인에 맞춘 제한된 타입·관계를 얼마나 정확히 지키는지에 초점이 있었습니다. 어떤 개념과 관계를 쓸지 찾아내는 일과, 정해진 관계에 맞춰 누가 한 말인지 정확하게 연결하는 일은 구분할 필요가 있었습니다. [AutoSchemaKG 논문](https://arxiv.org/html/2505.23628v3)

![두 단계 온톨로지 추출의 형식 오류 수정, 원문 대조, 잘못된 기록 제거와 기존 방식 유지](/assets/images/diagrams/myscdoc-decisions/05-ontology.svg)
*그림 5. 트리플 증가를 그래프 품질 개선으로 바로 해석하지 않았습니다. [Mermaid 원본](/assets/images/diagrams/myscdoc-decisions/05-ontology.mmd)*

첫 실행에서는 30건 중 27건이 검증을 통과하지 못했습니다. 모델이 객체를 가리키는 `objectId`와 설명용 문자열인 `literal`을 함께 채우거나, 빈 값 대신 `"null"`이라는 문자열을 반환했습니다. 코드는 이런 오류가 하나만 있어도 해당 스레드의 추출 결과를 모두 버리고 있었습니다. 유효한 객체 ID가 있으면 이를 우선 사용하고, 잘못된 엔티티와 연결된 내용만 제거하도록 바꿨습니다.

수정 후 같은 30개 스레드에서 결과를 비교했습니다.

| 항목 | 기존 추출 | 온톨로지 추출 |
|---|---:|---:|
| 생성된 문서 | 29/30 | 25/30 |
| 구조 오류 | 0 | 5 |
| 트리플 | 257 | 603 |
| 서로 다른 주어(subject) 수 | 143 | 224 |

30건을 모두 원문과 대조하니 새 방식이 나아진 경우는 11건, 좋아진 점과 나빠진 점이 섞인 경우는 5건, 오히려 나빠진 경우는 14건이었습니다. 행사·기업·프로그램의 관계를 더 많이 찾아낸 사례도 있었습니다. 반면 실제 이름 대신 `직원 N` 같은 임시 노드나 Slack ID가 들어갔고, 자기 자신을 가리키는 관계(self-loop)와 중복도 생겼습니다. 글쓴이의 해석을 원 연구기관이 내린 결정처럼 저장하거나, 후원자와 주최자를 뒤바꾸는 오류도 있었습니다.

새로 모델을 호출하지 않고, 같은 결과에서 명백히 잘못된 항목을 걸러내니 트리플이 603개에서 446개로 줄었습니다. 이 숫자는 잘못된 기록 157개를 지웠다는 의미입니다. 원문에 있던 중요한 내용을 더 많이 찾았다는 뜻은 아닙니다. 전체 정답 목록을 만들지 않은 상태에서는, 추출 개수가 늘었다는 이유만으로 재현율이 높아졌다고 말할 수 없습니다.

서비스에서는 기존 추출 방식인 `legacy`를 계속 사용하기로 했습니다. 다음 평가에서는 핵심 사실을 빠뜨리지 않았는지, 관계와 발언 주체를 정확히 연결했는지를 함께 확인해야 합니다. 정해진 JSON 형식을 지켰어도 그 안의 내용까지 맞는 것은 아니었습니다. [온톨로지 A/B 기록][loops]

## AI와 함께 실험하며 바꾼 판단들

실험을 돌아보면 모델을 바꾼 횟수만큼이나 결과를 해석하는 방식도 바뀌었습니다. 처음에는 작은 모델의 한계를 의심했고, 다음에는 필터와 학습 데이터로 문제를 해결하려 했습니다. 하지만 실제 입력과 답변을 확인할 때마다 다음에 해야 할 일이 달라졌습니다.

| 시도·초기 해석 | 받아들이지 않은 이유 | 다음 행동 |
|---|---|---|
| 긴 입력 실패는 모델 크기 문제 | 청킹·정답 문장 잘림 문제를 먼저 확인 | 입력과 학습 파이프라인 수정 |
| 결정 어미 필터로 정확도가 높아짐 | 사람 판단과 거의 무상관 | 정확도 대용 지표로 사용 중단 |
| V3의 점수 상승이 모델 개선 | 평가셋이 달랐고 정답 판정도 바뀜 | 같은 데이터로 평가하고 정답 재검토 |
| V5의 거절 점수 100%는 큰 개선 | 특정 문구를 출력하는지 세고 있었음 | 형식과 내용 따로 평가, 일반 데이터 추가 |
| 업무 데이터를 늘리면 해결 | V8이 V7을 일관되게 넘지 못함 | 무관한 문서에는 답하지 않도록 V9 학습 |
| V10의 연속 대화 성능이 좋아져 교체 가능 | 무관한 문서에도 답하는 오류 증가 | 서비스에 적용하지 않고 기존 후보 유지 |
| 트리플 두 배는 좋은 그래프 | 발언 주체·관계 방향·노드 오류 증가 | 원문 대조와 잘못된 기록 제거 |

AI가 만들어 준 코드와 설명을 검토할 때, 실행됐는지와 말이 되는지만 확인해서는 부족했습니다. 그 설명을 반박할 수 있는 입력을 만들고, 평가기가 그 실패를 잡을 수 있는지 확인해야 했습니다.

문맥의 날짜를 바꿨을 때 새 날짜를 읽는가. 정답 사실을 뺐을 때 거절하는가. 실제 답변을 읽어도 점수와 같은 결론인가. 비교 응답의 순서만 바꿔도 평가가 뒤집히지는 않는가.

이 질문들이 다음 버전의 데이터를 정했습니다. 높은 점수는 다음 실험으로 넘어갈 근거가 될 수 있었지만, 배포를 결정하는 충분조건은 아니었습니다. 더 나중에 학습한 V10 대신 V9를 다음 검증 대상으로 남긴 이유도 여기에 있습니다.

<p>안녕하세요. MYSCube를 만들고 있는 MYSC AX팀입니다.</p>
<p><strong>MYSCube는 MYSC가 자체 개발한 내부 ERP입니다.</strong> 프로젝트, 예산, 지출, 정산, 현금흐름처럼 조직 운영을 지탱하는 데이터를 하나의 흐름으로 연결합니다. 이 ERP를 만들며 가장 먼저 풀어야 했던 문제는 새로운 화면을 만드는 일이 아니었습니다. 이미 구글 시트 안에서 잘 돌아가고 있던 업무를 어떻게 시스템으로 옮길 것인가가 먼저였습니다.</p>
<p>처음에는 문제가 단순해 보였습니다.</p>
<ol>
<li>시트의 값을 읽는다.</li>
<li>Firestore에 저장한다.</li>
<li>MYSCube 화면에서 보여준다.</li>
</ol>
<p>하지만 실제 내부 현금흐름을 관리하는 탭을 열어보니 셀은 단순한 데이터가 아니었습니다. 어떤 셀은 사람이 직접 입력한 원본이었고, 어떤 셀은 다른 탭을 참조한 계산 결과였습니다. 같은 열에서도 일부 값은 자동 계산이었지만 특정 사업에서는 사람이 예외를 반영해 수정하고 있었습니다. 눈에 보이는 숫자 하나 뒤에 업무 규칙, 수정 이력, 암묵적인 승인 과정이 함께 들어 있었습니다.</p>
<p>이 상태에서 값을 그대로 복사하면 데이터는 옮길 수 있습니다. 그러나 왜 그 숫자가 나왔는지, 다음 입력에서 어떻게 다시 계산해야 하는지, 사람이 수정한 값과 시스템이 만든 값을 어떻게 구분할지는 사라집니다.</p>
<p>그래서 저희는 시트를 데이터베이스로 복사하지 않기로 했습니다. 대신 시트가 수행하던 일을 분석하고, 데이터와 계산 규칙, 사람의 판단, 시스템의 저장 권위를 각각 분리하기로 했습니다.</p>
<p>이번 글에서는 MYSCube가 기존 구글 시트를 분석하고 Firestore 기반 시스템에 연결하기까지 어떤 문제를 만났고, 어떤 구조를 선택했는지 이야기해 보겠습니다.</p>
<h2>이관 대상부터 고정하기</h2>
<p>시트 기반 업무를 시스템으로 옮길 때 가장 위험한 말은 “<mark>현재 사용 중인 시트를 기준으로 개발하자</mark>”입니다. 현재 사용 중인 시트는 계속 바뀝니다. 사용자가 열을 추가하거나 수식을 수정할 수 있고, 복사본마다 조금씩 다른 버전이 생길 수도 있습니다.</p>
<p>개발 도중 기준 시트가 바뀌면 두 가지를 구분할 수 없게 됩니다.</p>
<ul>
<li>구현이 잘못되어 결과가 달라진 것인지</li>
<li>원본 시트가 바뀌어서 결과가 달라진 것인지</li>
</ul>
<p>그래서 가장 먼저 한 일은 기능 구현이 아니라 <strong>변경 기준선을 만드는 것</strong>이었습니다.</p>
<p>기준 시점의 탭 이름과 수식 목록, 발견된 오류를 기록했습니다. 당시 기준선은 다음과 같았습니다.</p>

<p>이후 추출한 수식 목록과 오류 목록, 탭별 실행 순서를 JSON과 CSV 산출물로 남겼습니다. 생성된 파일은 일회성 분석 결과가 아니라 다음 구현과 회귀 테스트가 참조하는 버전 관리 산출물로 관리했습니다. 기준 시점 이후 구글 시트가 바뀌면 이 산출물과 다시 비교해 무엇이 달라졌는지 확인했습니다.</p>
<h2>수식 오류만 찾으면 충분할까?</h2>
<p>수식 목록을 만들면서 먼저 <code>#REF!</code>, <code>#N/A</code> 같은 스프레드시트 오류를 수집했습니다. 오류가 직접 포함된 수식과, 앞선 오류를 참조해 결과가 깨진 수식도 구분했습니다.</p>
<p>예를 들어 <code>사용내역</code> 탭의 통장잔액은 이전 행의 잔액을 다음 행이 참조하는 누적 잔액 구조였습니다. 중간 셀 하나에 <code>#REF!</code>가 생기면 이후 행도 연쇄적으로 깨집니다. 이 경우 최초 원인과 전파된 오류를 같은 문제로 세면 실제 수정 지점을 찾기 어렵습니다.</p>
<p>따라서 오류를 다음 두 종류로 나눴습니다.</p>
<ul>
<li><code>literal_formula_error</code>: 해당 수식 자체에 잘못된 참조가 존재</li>
<li><code>propagated_formula_error</code>: 앞선 오류를 참조하면서 결과가 전파됨</li>
</ul>
<p>이 분류를 통해 첫 오류가 발생하기 전 구간은 정상 계산용 고정 테스트 데이터로, 이후 구간은 오류 전파용 고정 테스트 데이터로 따로 다룰 수 있었습니다.</p>
<p>하지만 더 어려운 문제는 오류 코드가 없는 수식이었습니다.</p>
<p><code>사용내역</code> 탭의 한 구간에는 다음과 같은 형태의 수식이 반복되어 있었습니다.</p>
<pre><code>N4:N9 = $K$4 / 11 * 10
</code></pre>
<p>각 행이 자기 행의 통장 금액을 참조해야 할 것처럼 보이지만, 모든 행이 절대참조 <code>$K$4</code>를 사용하고 있었습니다. 엑셀은 이 수식을 정상적으로 계산합니다. <code>#REF!</code>도 발생하지 않습니다. 자동화된 오류 탐지기는 이 수식을 정상으로 판단합니다.</p>
<p>하지만 업무 의미로 보면 의심스러운 패턴입니다. 이 수식을 그대로 코드로 옮기면 원본의 실수까지 MYSCube의 공식 규칙으로 승격하게 됩니다.</p>
<p>여기서 중요한 결론을 얻었습니다.</p>
<blockquote>
<p>문법적으로 계산 가능한 수식과 업무적으로 올바른 규칙은 다르다.</p>
</blockquote>
<p>이후부터는 원본 수식을 세 종류로 보기 시작했습니다.</p>
<table>
<thead>
<tr>
<th>분류</th>
<th>의미</th>
<th>이관 방식</th>
</tr>
</thead>
<tbody><tr>
<td>정상 수식</td>
<td>의도와 결과가 확인된 계산</td>
<td>업무 규칙과 고정 테스트 데이터로 전환</td>
</tr>
<tr>
<td>명시적 오류</td>
<td><code>#REF!</code>, <code>#N/A</code> 등</td>
<td>원인과 전파 구간을 분리해 수정</td>
</tr>
<tr>
<td>의미상 이상 패턴</td>
<td>계산은 되지만 의도가 의심됨</td>
<td>자동 승격하지 않고 사람 검토 대상으로 격리</td>
</tr>
</tbody></table>
<p>이를 저희는 <strong>의미상 이상 징후(semantic anomaly)</strong>라고 불렀습니다. 시트 이관은 수식 번역 작업이 아니라 업무 의미를 복원하는 작업이 되었습니다.</p>
<h2>세 가지 이관 방식을 비교하다</h2>
<p>기준선을 만든 뒤에는 실제 시스템 구조를 결정해야 했습니다. 검토한 방향은 크게 세 가지였습니다.</p>
<h3>1. 구글 시트를 계속 기준 정보원으로 사용한다</h3>
<p>가장 단순한 방법은 MYSCube가 구글 시트의 값을 읽어서 보여주고, 모든 수정도 다시 시트에 기록하는 것입니다.</p>
<p>장점은 명확합니다.</p>
<ul>
<li>기존 운영 방식을 거의 바꾸지 않아도 됩니다.</li>
<li>사용자는 익숙한 시트를 계속 사용할 수 있습니다.</li>
<li>초기 개발 범위가 작습니다.</li>
</ul>
<p>반면 제품이 커질수록 한계도 분명했습니다.</p>
<ul>
<li>열 추가나 순서 변경이 API 계약을 깨뜨릴 수 있습니다.</li>
<li>셀 단위 권한과 도메인 권한을 일치시키기 어렵습니다.</li>
<li>누가 어떤 업무 의미로 값을 바꿨는지 추적하기 어렵습니다.</li>
<li>동시에 수정할 때 어느 값이 최신인지 판단하기 어렵습니다.</li>
<li>월 마감처럼 특정 시점의 상태를 잠그고 보존하기 어렵습니다.</li>
</ul>
<p>시트를 계속 원장으로 두면 MYSCube는 독립적인 시스템이 아니라 시트를 보여주는 또 하나의 화면에 머물 가능성이 컸습니다.</p>
<h3>2. 시트 값을 Firestore에 그대로 복제한다</h3>
<p>두 번째 방법은 시트의 행과 열을 가능한 그대로 Firestore 문서에 저장하는 방식이었습니다.</p>
<p>이 방법은 첫 번째보다 시스템에 가까워 보입니다. 그러나 실제로는 시트의 구조적 문제를 데이터베이스 안으로 옮기는 것에 가깝습니다.</p>
<p>예를 들어 <code>열 N</code>이 무엇을 뜻하는지 코드 여러 곳이 알고 있어야 하고, 원본 탭의 열 순서가 바뀌면 저장 구조도 영향을 받습니다. 수식 결과만 저장하면 계산 근거가 사라지고, 수식 문자열까지 저장하면 Firestore가 사실상 스프레드시트 실행기의 저장소가 됩니다.</p>
<p>무엇보다 가장 중요한 문제가 남습니다.</p>
<blockquote>
<p>시트와 Firestore의 값이 다를 때 어느 쪽이 맞는가?</p>
</blockquote>
<p>명확한 권위가 없는 양방향 동기화는 두 시스템의 장점을 합치기보다 두 시스템의 충돌 가능성을 합칩니다.</p>
<h3>3. 시트의 의미를 도메인 모델로 재구성한다</h3>
<p>저희가 선택한 방식입니다.</p>
<ul>
<li>구글 시트는 사람이 익숙하게 데이터를 확인하고 가져오는 입출력 채널로 사용합니다.</li>
<li>Firestore에는 <code>열 위치</code>가 아닌 프로젝트, 주차, 현금흐름 항목 같은 업무 개념을 저장합니다.</li>
<li>시트 수식은 그대로 실행하지 않고 명시적인 계산 규칙으로 옮깁니다.</li>
<li>자동 계산이 확실하지 않은 값은 확정값이 아니라 검토 후보로 만듭니다.</li>
<li>저장 이후에는 다시 읽어 실제 반영 결과를 검증합니다.</li>
</ul>
<p>이 방식은 초기 구현량이 더 많습니다. 대신 시트가 바뀌어도 도메인 계약을 유지할 수 있고, 이후 주정산과 월결산을 같은 데이터 모델 위에 올릴 수 있습니다.</p>
<h2>17개 탭을 한 번에 옮기지 않은 이유</h2>
<p>17개 탭을 분석했다고 해서 17개 탭을 동시에 제품화하지는 않았습니다.</p>
<p>시트들은 서로 다른 책임을 갖고 있었습니다. 통장내역은 원천 거래에 가깝고, 사용내역은 거래를 정산 규칙에 맞게 분류한 결과였습니다. 현금흐름은 다시 주차별 예측값과 실적값으로 나뉘었습니다. 제출용 탭과 그룹 집계 탭도 있었습니다.</p>
<p>모든 탭을 한 번에 연결하면 데이터 권위와 오류의 원인을 추적하기 어려워집니다. 그래서 전체 탭의 의존 관계를 이해하되, 첫 운영 연동은 <code>현금흐름(사용내역 연동)</code> 계열 탭으로 제한했습니다.</p>
<p>이 탭을 선택한 이유는 세 가지였습니다.</p>
<ol>
<li>주차와 현금흐름 항목이라는 비교적 명확한 업무 식별자가 있었습니다.</li>
<li>구글 시트 값과 MYSCube 값을 같은 위치에서 대조할 수 있었습니다.</li>
<li>이후 주정산 엔진으로 이어지는 경계가 분명했습니다.</li>
</ol>
<p>지원하지 않는 탭을 그럴듯하게 해석하는 대신, 탭 이름과 구조가 기대한 서식과 일치하지 않으면 요청을 거절했습니다. 범용 스프레드시트 해석기를 먼저 만드는 대신 실제 운영 경로 하나를 끝까지 연결하는 쪽을 택했습니다.</p>
<h2>구글 시트와 Firestore 사이에 BFF를 둔 이유</h2>
<p>초기 구조에서는 브라우저가 Firestore를 직접 읽거나 쓰는 경로가 존재했습니다. 빠르게 기능을 만들기에는 편리했지만, 외부 시트까지 연결되자 문제가 복잡해졌습니다.</p>
<p>브라우저가 구글 접근 토큰과 시트 ID, 조직 ID, 작업자 정보를 모두 들고 각 저장소를 직접 호출하면 다음 책임이 프론트엔드에 섞입니다.</p>
<ul>
<li>사용자가 해당 프로젝트를 볼 수 있는지 확인</li>
<li>어떤 구글 계정으로 시트를 읽을지 결정</li>
<li>탭과 셀 구조 검증</li>
<li>시트 값을 표준 항목으로 변환</li>
<li>Firestore 변경 전후 기록</li>
<li>실패 시 재시도와 감사 로그 생성</li>
</ul>
<p>그래서 구글 시트 연동은 Express BFF를 통과하도록 만들었습니다.</p>

<p>브라우저는 시트 링크와 사용자가 선택한 주차 범위를 보냅니다. BFF는 인증된 요청 정보에서 조직과 작업자를 결정합니다. 사용자가 임의로 전달한 권한 정보로 저장 대상을 바꿀 수 없도록 경계를 세웠습니다.</p>
<p>구글 시트 접근에는 서비스 계정을 사용했습니다. 사용자는 MYSCube가 안내하는 시스템 계정에 해당 시트를 공유합니다. 브라우저에서 보내는 구글 접근 토큰은 더 이상 신뢰하지 않습니다.</p>
<p>이 구조에서 중요한 것은 BFF가 단순한 중계기가 아니라는 점입니다. BFF는 외부 시트의 구조와 내부 원장의 구조가 만나는 <strong>오염 방지 계층(anti-corruption layer)</strong> 역할을 합니다.</p>
<h2>화면 배치와 값의 기준 정보원을 분리하다</h2>
<p>구글 시트 미리보기를 구현하면서 한 가지 결정을 더 했습니다.</p>
<p>화면의 행과 열 배치는 구글 시트에서 읽지만, MYSCube가 이미 저장한 현금흐름 값은 Firestore에서 읽습니다.</p>

<p>이 구조 덕분에 사용자는 익숙한 시트 배치 위에서 값을 비교할 수 있지만, MYSCube 화면이 시트의 현재 숫자를 무조건 공식값으로 취급하지는 않습니다.</p>
<p>미리보기 단계에서는 두 값을 나란히 비교합니다. 시트의 셀 위치는 <code>A1</code> 좌표와 표준 항목 ID에 연결되고, 플랫폼 값은 프로젝트 ID, <code>yearMonth</code>, <code>weekNo</code>, <code>mode</code>, <code>lineId</code>의 조합으로 조회됩니다.</p>
<pre><code>type CashflowKey = {
  projectId: string;
  yearMonth: string;
  weekNo: number;
  mode: 'projection' | 'actual';
  lineId: string;
};
</code></pre>
<p><code>C열의 12번째 행</code>처럼 물리적인 위치를 내부 식별자로 사용하지 않은 것이 중요했습니다. 위치는 바뀔 수 있지만 “2026년 6월 2주차의 사업비 지출 실적값”이라는 업무 의미는 유지되어야 하기 때문입니다.</p>
<h2>바로 저장하지 않고 변경 후보를 만든 이유</h2>
<p>시트에서 읽은 값을 Firestore에 즉시 덮어쓰는 구현은 간단합니다. 하지만 운영에서는 위험합니다.</p>
<ul>
<li>이미 관리자가 마감한 주차일 수 있습니다.</li>
<li>사람이 MYSCube에서 더 최신 값을 수정했을 수 있습니다.</li>
<li>시트에 남아 있는 0이 실제 0인지, 아직 입력하지 않은 값인지 불분명할 수 있습니다.</li>
<li>잘못된 수식 결과가 정상 숫자 형태로 들어올 수 있습니다.</li>
</ul>
<p>그래서 <code>미리보기 → 후보 저장 → 반영</code>의 세 단계로 나눴습니다.</p>
<h3>미리보기</h3>
<p>시트 구조를 분석하고 지원 가능한 서식인지 확인합니다. 주차 머리글과 현금흐름 항목을 찾고, Firestore의 현재 값과 비교할 수 있는 형태로 반환합니다. 이 단계에서는 원장을 수정하지 않습니다.</p>
<p>구글 시트 API 호출이 동시에 몰릴 때 같은 시트를 여러 번 읽지 않도록 15초짜리 짧은 캐시와 진행 중 요청 합치기도 적용했습니다. 캐시는 최신성 보장 수단이 아니라 연속된 미리보기 요청의 중복 입출력을 줄이는 용도로만 사용했습니다.</p>
<h3>후보 저장</h3>
<p>시트 값과 Firestore 값이 다른 항목만 변경 후보로 저장합니다. 후보에는 다음 정보가 포함됩니다.</p>
<ul>
<li>변경 전 금액과 변경 후 금액</li>
<li>예측값 또는 실적값 여부</li>
<li>연월과 주차</li>
<li>표준 항목 ID</li>
<li>원본 셀 주소와 라벨</li>
<li>변경을 요청한 사용자</li>
<li>위험 신호</li>
</ul>
<p>관리자가 이미 마감한 주차의 변경에는 <code>closed_week_change</code> 위험 신호를 붙입니다. 위험 후보는 명시적인 선택 없이는 반영 대상에서 제외됩니다.</p>
<h3>반영</h3>
<p>검토가 끝난 후보만 Firestore에 반영합니다. 반영과 함께 금액 변경 기록을 남기고, 다시 Firestore의 시점 데이터를 읽어 기대값과 실제값이 같은지 검증합니다.</p>
<pre><code>if (actual !== expected) {
  throw new Error('cashflow_sheet_apply_verify_failed');
}
</code></pre>
<p>API가 200 응답을 반환했다는 사실만으로 저장 성공을 선언하지 않았습니다. 실제 저장소를 다시 읽었을 때 기대한 항목과 금액이 존재해야 한 주기가 끝난 것으로 봤습니다.</p>
<p><img src="/assets/images/diagrams/building-ledger-01/03-preview-stage-apply-excalidraw.png" alt="시트 값을 미리보고 후보로 저장한 뒤 Firestore에 반영하고 다시 읽어 검증하는 흐름" /></p>
<p><em>그림 2. 변경 후보와 마감 주차 위험을 먼저 검토하고, 반영 후 실제 저장값을 다시 비교합니다.</em></p>
<h2>양방향 동기화에는 기준 해시를 사용하다</h2>
<p>구글 시트를 입력 채널로만 사용하면 구조는 더 단순합니다. 그러나 일부 예측값은 MYSCube에서 수정한 뒤 다시 시트에서 확인해야 했습니다.</p>
<p>문제는 미리보기와 실제 되쓰기 사이에 사용자가 시트를 수정할 수 있다는 점입니다.</p>
<ol>
<li>사용자가 되쓰기 미리보기를 확인합니다.</li>
<li>다른 사용자가 구글 시트 값을 수정합니다.</li>
<li>첫 사용자가 이전 미리보기 기준으로 반영합니다.</li>
<li>최신 수정값이 덮어써집니다.</li>
</ol>
<p>이를 막기 위해 미리보기 시점의 대상 셀들을 정렬하고 SHA-256 해시를 계산했습니다.</p>
<pre><code>const baseline = cells
  .map(({ yearMonth, weekNo, lineId, a1, sheetAmount }) =&gt; ({
    key: `${yearMonth}:${weekNo}:${lineId}`,
    a1,
    sheetAmount,
  }))
  .sort(compareCell);

const baselineHash = sha256(JSON.stringify(baseline));
</code></pre>
<p>반영 요청에서는 캐시를 사용하지 않고 구글 시트를 새로 읽습니다. 현재 기준 해시가 사용자가 미리보기에서 받은 값과 다르면 <code>409 Conflict</code>를 반환합니다.</p>
<pre><code>시트가 검토 이후 변경되었습니다.
현재 시트 값을 다시 검토한 뒤 반영해 주세요.
</code></pre>
<p><img src="/assets/images/diagrams/building-ledger-01/04-baseline-hash-conflict-excalidraw.png" alt="되쓰기 미리보기 이후 시트가 변경되었을 때 기준 해시로 충돌을 감지하는 흐름" /></p>
<p><em>그림 3. 미리보기의 해시와 반영 직전 해시가 다르면 409 Conflict로 덮어쓰기를 중단합니다.</em></p>
<p>되쓰기 범위도 예측값 셀로 제한했습니다. 실적값까지 자동으로 되돌려 쓰는 양방향 동기화는 원본 거래와 확정 실적의 권위를 흐릴 수 있기 때문입니다.</p>
<p>되쓰기 실행 상태는 별도 동기화 작업으로 기록합니다.</p>
<ul>
<li><code>RUNNING</code></li>
<li><code>CONFLICT</code></li>
<li><code>DONE</code></li>
<li><code>FAILED</code></li>
</ul>
<p>각 상태 변화는 발신함 이벤트로도 남깁니다. 사용자는 단순히 “동기화 버튼을 눌렀다”가 아니라 실제로 몇 개 셀이 반영됐고, 충돌했는지, 실패했는지를 확인할 수 있습니다.</p>
<h2>수식보다 어려웠던 사람의 수정값</h2>
<p>스프레드시트 계산을 코드로 옮길 때 자동 계산의 정확도에 집중하기 쉽습니다. 그러나 실제 운영에서 더 중요한 것은 사람이 수정한 값을 보존하는 일이었습니다.</p>
<p>예를 들어 통장 금액을 기준으로 공급가액과 부가세를 역산할 수 있습니다. 수학적으로는 계산 가능하지만 실제 증빙의 공급가액·부가세와 정확히 일치하지 않는 예외가 존재합니다. 취소, 불인정, 복합 거래처럼 한 번의 통장 입출금이 한 줄의 규칙으로 설명되지 않는 경우도 있습니다.</p>
<p>그래서 계산 가능한 값이라고 해서 모두 공식값으로 자동 승격하지 않았습니다.</p>
<ul>
<li>확실한 파생값은 자동 계산합니다.</li>
<li>증빙 확인이 필요한 값은 제안값으로 만듭니다.</li>
<li>사용자가 명시적으로 수정하거나 지운 값은 다시 계산해 덮어쓰지 않습니다.</li>
<li>확정하기 어려운 값에는 HITL(Human-in-the-Loop) 검토 상태를 둡니다.</li>
</ul>
<p>이 원칙은 이후 정산 계산 커널을 TypeScript와 Rust로 검증할 때도 그대로 유지했습니다. 같은 입력에서 같은 결과를 만드는 것만큼, 사람이 내린 명시적인 결정을 보존하는 것이 중요했습니다.</p>
<h2>테스트는 작은 가짜 시트로 끝내지 않았다</h2>
<p>수식 해석기나 셀 연결 보조 함수는 작은 고정 데이터로 테스트할 수 있습니다. 하지만 실제 이관의 성공 기준은 운영 중인 구글 시트였습니다.</p>
<p>그래서 검증 단계를 다음처럼 나눴습니다.</p>
<h3>1. 수식 목록 검사</h3>
<ul>
<li>전체 시트와 수식 개수 확인</li>
<li>직접 오류와 전파된 오류를 분리</li>
<li>알려진 의미상 이상 징후가 격리되는지 확인</li>
</ul>
<h3>2. 기준값 검사</h3>
<ul>
<li>정상 누적 잔액 구간의 기대값 확인</li>
<li>오류가 시작되는 최초 셀 확인</li>
<li>오류 전파 구간을 정상 기대값으로 오인하지 않는지 확인</li>
<li>통장 입력과 직접 입력이 같은 표준 데이터 구조로 수렴하는지 확인</li>
</ul>
<h3>3. BFF 통합 검사</h3>
<ul>
<li>허용되지 않은 역할이 다른 조직의 시트를 적용할 수 없는지 확인</li>
<li>지원하지 않는 탭과 서식을 거절하는지 확인</li>
<li>후보 저장 단계에서 변경된 셀만 후보로 생성하는지 확인</li>
<li>마감 주차 변경을 위험 후보로 분류하는지 확인</li>
<li>반영 후 Firestore에서 다시 읽은 값이 일치하는지 확인</li>
<li>미리보기 이후 시트가 바뀌면 되쓰기가 충돌하는지 확인</li>
</ul>
<h3>4. 실제 구글 시트 기반 전체 흐름 검증</h3>
<p>운영 중인 구글 시트에서 수식 목록을 다시 생성하고, 추출 결과와 기준 산출물을 대조했습니다. “시트를 읽는 과정이 중단되지 않는다”가 아니라 어떤 수식이 어떤 업무 규칙으로 옮겨졌고 어떤 값이 의도적으로 제외됐는지를 확인했습니다.</p>
<h2>구현하면서 바뀐 생각들</h2>
<h3>시트 오류는 셀 오류 코드보다 넓다</h3>
<p>처음에는 <code>#REF!</code>와 <code>#N/A</code>를 모두 찾으면 원본 문제를 파악할 수 있을 것이라 생각했습니다. 실제로는 정상 숫자를 반환하는 잘못된 절대참조가 더 위험했습니다. 시스템은 실패한 수식보다 그럴듯하게 성공한 잘못된 수식을 발견하기 어렵습니다.</p>
<h3>범용 해석기보다 좁은 운영 경계가 먼저다</h3>
<p>17개 탭을 모두 이해하는 범용 엔진을 먼저 만들 수도 있었습니다. 그러나 탭마다 업무 의미와 권위가 달랐습니다. 첫 단계에서는 현금흐름 연동 탭만 지원하고, 예상한 구조가 아니면 명시적으로 거절하는 편이 더 안전했습니다.</p>
<h3>양방향 동기화는 기능이 아니라 충돌 정책이다</h3>
<p>읽기와 쓰기 API를 붙이는 것만으로 양방향 동기화가 완성되지 않습니다. 미리보기 이후 값이 바뀌었을 때 중단할지, 덮어쓸지, 누가 재검토할지를 먼저 정해야 했습니다. 기준 해시는 이 정책을 구현하기 위한 가장 작은 장치였습니다.</p>
<h3>저장 성공은 다시 읽기 전까지 알 수 없다</h3>
<p>Firestore 쓰기가 성공했고 API가 200을 반환해도 사용자가 기대한 조회 모델이 만들어졌다는 보장은 없습니다. 그래서 반영 뒤에는 실제 시점 데이터를 다시 읽어 항목별 기대값을 비교했습니다.</p>
<h2>현재 구조의 한계</h2>
<p>이 구조가 시트 이관 문제를 모두 해결한 것은 아닙니다.</p>
<p>첫째, 현재 시스템에는 React가 Firestore를 직접 사용하는 경로와 BFF를 사용하는 경로가 함께 존재합니다. 핵심 저장 권위를 서버로 이동하는 중간 단계이기 때문에, 업무 영역별 공식 관리 주체를 계속 명확히 해야 합니다.</p>
<p>둘째, 구글 시트 서비스 계정은 예측값 되쓰기를 지원하기 위해 쓰기 권한도 사용할 수 있습니다. 미리보기 경로는 논리적으로 읽기 전용이지만 인증 주체의 권한 자체가 완전히 분리된 것은 아닙니다. 향후에는 읽기 전용 인증 주체와 쓰기 전용 인증 주체를 분리해 최소 권한 원칙을 더 강하게 적용할 수 있습니다.</p>
<p>셋째, 첫 운영 연동은 특정 현금흐름 탭 구조를 대상으로 합니다. 임의의 스프레드시트를 자동으로 이해하는 범용 시스템이 아닙니다. 지원 범위를 넓힐 때는 새로운 탭을 기존 해석기에 억지로 끼우기보다, 업무 의미와 기준 정보원을 먼저 정의해야 합니다.</p>
<p>마지막으로 Firestore가 영구적인 최종 원장이라는 결론도 아닙니다. MYSCube는 장기적으로 서버 권위의 명령 모델과 PostgreSQL 원장으로 단계적으로 전환하고 있습니다. 구글 시트와 Firestore를 동시에 영구적인 권위로 유지하는 끝없는 혼합 구조는 목표가 아닙니다.</p>
<h2>정리</h2>
<p>이번 글에서는 MYSCube가 기존 구글 시트를 시스템에 연결하면서 했던 고민을 살펴보았습니다.</p>
<p>처음에는 시트의 값을 읽어 Firestore에 저장하면 될 것처럼 보였습니다. 하지만 실제로 옮겨야 했던 것은 셀이 아니라 다음 네 가지였습니다.</p>
<ul>
<li>시트 안에 숨어 있던 업무 규칙</li>
<li>데이터와 계산 결과의 출처</li>
<li>사람이 내린 수정과 승인 판단</li>
<li>어느 시스템이 최종 값을 결정하는지에 대한 권위</li>
</ul>
<p>저희가 선택한 방법은 원본을 그대로 복제하는 것이 아니었습니다. 구글 시트의 기준 시점을 기록하고, 수식과 오류를 분류하고, 업무 의미를 표준 모델로 옮겼습니다. 구글 시트는 익숙한 입출력 채널로 남기되, 변경은 미리보기와 검토를 거쳐 적용하고, 충돌과 반영 결과를 다시 검증하도록 만들었습니다.</p>
<p>이 과정을 거치면서 다음 단계의 질문이 생겼습니다.</p>
<p>시트에서 들어온 한 주의 지출을 누가 확정해야 할까요? 같은 요청이 두 번 도착하면 어떻게 해야 할까요? 사용자가 동시에 같은 행을 고쳤을 때 어느 변경을 받아들여야 할까요? 그리고 마감된 주차는 정말 수정할 수 없어야 할까요?</p>
<p>다음 글에서는 이 질문을 해결하기 위해 Express BFF 뒤에 Spring Boot 기반 주정산 API를 두고, 저장을 단순 CRUD가 아닌 버전이 있는 명령과 상태 전이로 다루게 된 과정을 소개하겠습니다.</p>
<h3>JVM은 무엇이고, 왜 뒤에 둘까?</h3>
<p>JVM(Java Virtual Machine, 자바 가상 머신)은 Java와 Kotlin 같은 언어로 작성한 서버 프로그램을 실행하는 환경입니다. MYSCube에서는 구글 시트에 맞춘 요청 변환은 Express BFF가 맡고, 주정산 규칙과 상태 전이, 동시성 제어처럼 일관성이 중요한 처리는 JVM 위의 Spring Boot 서버가 맡습니다. 화면과 외부 서비스에 가까운 계층은 가볍게 유지하면서, 핵심 업무 규칙은 강한 자료형과 트랜잭션 경계를 갖춘 서버에서 지키기 위한 분리입니다.</p>

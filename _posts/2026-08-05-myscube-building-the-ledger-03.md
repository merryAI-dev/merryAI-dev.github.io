<p>안녕하세요. MYSCube를 만들고 있는 MYSC AXR팀입니다.</p>
<p><strong>MYSCube는 MYSC가 자체 개발한 내부 ERP입니다.</strong> 프로젝트의 예산과 지출, 정산, 현금흐름처럼 조직 운영에 필요한 데이터를 하나의 흐름으로 연결하고 있어요.</p>
<p>앞선 글에서는 구글 시트의 데이터를 내부 ERP로 가져오는 과정을 소개했습니다.</p>
<p>하나의 서버는 구글 시트의 행과 열을 읽어 프로젝트·기간·항목이라는 업무 정보로 바꿉니다. 다른 서버는 입금과 출금, 잔액을 다시 계산하고 내부 ERP에 반영할 수 있는 값인지 검증하고요.</p>
<p>이 구조를 운영 흐름에 연결하면서 새로운 질문이 생겼습니다.</p>
<blockquote>
<p>주정산을 완료한 뒤 예상 입금일이 바뀌면 어떻게 해야 할까요?</p>
</blockquote>
<p>담당자가 금요일에 이번 주 현금흐름을 모두 확인하고 주정산을 마쳤다고 해볼게요. 그런데 다음 주 월요일, 거래처의 입금 일정이 바뀌었다는 연락을 받았습니다.</p>
<p>예상 현금흐름을 수정해야 하지만 화면에는 이미 ‘완료’라고 표시되어 있습니다.</p>
<p>완료된 주정산을 다시 열어야 할까요? 숫자를 수정해도 완료 상태를 유지해야 할까요? 아니면 완료된 뒤에는 아무것도 수정하지 못하게 막아야 할까요?</p>
<p>처음에는 버튼과 권한의 문제처럼 보였습니다. 하지만 자세히 들여다볼수록 백엔드가 ‘완료’를 어떻게 정의할 것인지에 관한 문제였어요.</p>
<p>저희는 이 문제를 풀면서 주정산 구조를 몇 차례 다시 다듬었습니다. 오늘은 그 과정을 차례대로 소개해 볼게요.</p>

<h2>Phase 0: 완료 여부만 저장하기</h2>
<p>초기 구조는 단순했습니다.</p>
<pre><code>completed = true
</code></pre>
<p>담당자가 완료 버튼을 누르면 해당 주차를 완료 상태로 바꾸는 방식이에요.</p>
<p>처음에는 이것으로 충분해 보였습니다. 하지만 <code>완료</code>라는 값에 서로 다른 의미가 섞이기 시작했어요.</p>
<ul>
<li>담당자가 이번 주 입력을 마쳤다.</li>
<li>변경사항이 없다는 것을 확인했다.</li>
<li>승인자가 검토했다.</li>
<li>해당 주차의 숫자가 확정됐다.</li>
<li>앞으로 누구도 숫자를 수정할 수 없다.</li>
</ul>
<p>사람은 대화의 맥락을 보고 이 차이를 이해할 수 있습니다. 시스템은 그렇지 못해요. 시스템에는 완료인지 아닌지만 남아 있었기 때문에, 완료 이후 어떤 동작을 허용해야 할지 결정하기 어려웠습니다.</p>
<p>조건도 계속 늘어났습니다.</p>
<pre><code>완료됐지만 예상값은 수정할 수 있다.
완료됐지만 승인 전에는 다시 제출할 수 있다.
완료됐지만 월결산 전에는 숫자가 잠기지 않는다.
완료된 뒤 값이 바뀌면 경고를 표시한다.
</code></pre>
<p>하나의 참·거짓 값에 예외가 계속 붙고 있었습니다.</p>
<p>이때 한 가지를 알게 됐어요.</p>
<blockquote>
<p>주간 업무를 확인했다는 것과 재무 숫자를 확정했다는 것은 다른 일이다.</p>
</blockquote>
<p>그래서 주정산의 완료와 데이터의 잠금을 분리하기 시작했습니다.</p>

<h2>주정산과 월결산을 분리하다</h2>
<p>주정산은 담당자와 승인자가 해당 주의 업무를 확인했다는 기록입니다.</p>
<p>주정산을 마쳤다는 것은 다음 내용을 설명할 수 있어야 한다는 뜻이에요.</p>
<ul>
<li>누가 현금흐름을 확인했는가</li>
<li>언제 확인했는가</li>
<li>변경사항이 있었는가</li>
<li>어떤 판본의 데이터를 확인했는가</li>
<li>누락된 예상값은 없었는가</li>
<li>예외적으로 진행했다면 무엇을 확인했는가</li>
</ul>
<p>하지만 주정산을 마쳤다고 해서 미래의 예상 현금흐름까지 고정되는 것은 아닙니다.</p>
<p>사업의 입금 일정은 바뀔 수 있습니다. 아직 발생하지 않은 지출 계획도 조정될 수 있고요. 주정산 이후의 변경을 모두 막으면 내부 ERP가 실제 업무를 따라가지 못합니다.</p>
<p>숫자를 공식 기록으로 확정하는 일은 월결산이 맡습니다.</p>
<table>
<thead>
<tr><th>구분</th><th>주정산</th><th>월결산</th></tr>
</thead>
<tbody>
<tr><td>목적</td><td>주간 업무 확인</td><td>재무 기록 확정</td></tr>
<tr><td>이후 예상값 수정</td><td>가능</td><td>일반적인 경로에서는 제한</td></tr>
<tr><td>주요 기록</td><td>확인자, 확인 시각, 변경 여부</td><td>승인자, 확정 범위, 데이터 판본</td></tr>
<tr><td>데이터의 성격</td><td>운영 상태</td><td>공식 마감 기록</td></tr>
<tr><td>예외 처리</td><td>확인 근거와 함께 진행</td><td>변경 전후의 값과 사유 기록</td></tr>
</tbody>
</table>
<p>주정산은 “이 시점에 이 데이터를 확인했다”는 기록이고, 월결산은 “이 범위의 숫자를 공식 기록으로 인정한다”는 결정입니다.</p>
<p>두 상태를 나누자 완료 이후 무엇을 허용해야 하는지도 조금씩 명확해졌습니다.</p>

<h2>Phase 1: 완료를 과정으로 바꾸기</h2>
<p>주정산은 이제 세 가지 상태를 가집니다.</p>
<pre><code>업데이트 대기
    ↓
승인 대기
    ↓
완료
</code></pre>
<p>처음에는 <code>업데이트 대기</code> 상태입니다.</p>
<p>담당자가 현금흐름을 확인하고 주정산을 마치면 <code>승인 대기</code>로 이동합니다. 이후 지정된 승인자가 검토하면 <code>완료</code> 상태가 돼요.</p>
<p>이렇게 현재 상태와 다음 상태를 정하고, 허용된 방향으로만 이동하게 만드는 구조를 개발에서는 <strong>상태 머신(State Machine)</strong>이라고 부릅니다.</p>
<p>이름은 어렵지만 교통 신호와 비슷합니다. 신호가 정해진 순서와 조건에 따라 바뀌는 것처럼 정산 상태도 허용된 경로로만 이동합니다.</p>
<pre><code>업데이트 대기
→ 담당자가 완료
→ 승인 대기

승인 대기
→ 지정된 승인자가 승인
→ 완료
</code></pre>
<p>업데이트 대기 상태를 승인자가 곧바로 완료로 바꿀 수는 없습니다. 승인 대기가 아닌 상태를 승인할 수도 없고요.</p>
<p>이미 처리된 승인 요청이 다시 들어왔다면 새로운 완료 기록을 만들지 않고 기존 결과를 돌려줍니다.</p>
<p>중요한 점은 화면이 아니라 서버가 이 순서를 결정한다는 것입니다.</p>
<p>프론트엔드에서 승인 버튼을 숨기는 것만으로는 충분하지 않아요. 다른 화면이나 자동화된 요청이 같은 기능을 호출할 수도 있기 때문입니다.</p>
<p>어떤 경로로 요청하더라도 같은 규칙이 적용되도록, 정산 상태를 변경하는 권한을 재무 규칙을 담당하는 서버에 모았습니다.</p>

<h2>두 백엔드는 무엇이 달랐을까요?</h2>
<p>MYSCube의 현금흐름 기능 뒤에는 서로 다른 역할을 맡은 두 서버가 있습니다.</p>
<p>첫 번째는 화면 가까이에서 구글 시트의 데이터를 정리해 주는 Express 서버입니다.</p>
<p>구글 시트는 <code>C열의 12번째 행</code>처럼 위치로 정보를 표현합니다. 사람은 주변의 제목을 보고 그 의미를 이해하지만 시스템은 그렇지 못해요.</p>
<p>이 서버는 셀 위치를 다음과 같은 업무 정보로 바꿉니다.</p>
<pre><code>2026년 8월 2주차
예상 현금흐름
인건비 지출
1,000,000원
</code></pre>
<p>화면에 필요한 형태로 데이터를 만들어 주는 서버이기 때문에 개발에서는 <strong>BFF(Backend for Frontend)</strong>라고 부릅니다. 이름보다 중요한 것은 구글 시트와 화면 사이의 번역기 역할을 한다는 점이에요.</p>
<p>두 번째는 자바 프로그램을 실행하는 환경 위에서 동작하는 Spring Boot 서버입니다.</p>
<p>Spring Boot는 자바로 서버를 만들 때 사용하는 개발 도구이고, 자바 프로그램을 실행하는 환경을 JVM, 즉 Java Virtual Machine이라고 합니다. 앞선 글에서 ‘JVM 서버’라고 소개했던 서버가 바로 이 서버예요.</p>
<p>이 서버는 구글 시트의 셀 위치를 해석하지 않습니다. 대신 다음과 같은 업무 규칙을 책임집니다.</p>
<ul>
<li>지금 주정산을 완료할 수 있는가</li>
<li>필요한 예상 현금흐름이 모두 입력됐는가</li>
<li>현재 사용자가 승인할 권한이 있는가</li>
<li>사용자가 내용을 확인한 뒤 숫자가 바뀌지 않았는가</li>
<li>같은 완료 요청이 이미 처리되지 않았는가</li>
<li>월결산으로 확정된 기간을 수정하려는 것은 아닌가</li>
</ul>
<p><img src="/assets/images/diagrams/building-ledger-02/bff-jvm-role-separation.png" alt="구글 시트를 Express 서버가 업무 정보로 바꾸고 Spring Boot 서버가 계산과 저장 규칙을 검증하는 구조" /></p>
<p><em>그림 1. Express 서버는 시트의 언어를 업무의 언어로 바꾸고, Spring Boot 서버는 그 업무를 실행해도 되는지 판단합니다.</em></p>
<p>두 서버의 역할을 한 문장으로 정리하면 이렇습니다.</p>
<blockquote>
<p>Express 서버는 시트의 언어를 업무의 언어로 바꾸고, Spring Boot 서버는 그 업무를 실행해도 되는지 결정합니다.</p>
</blockquote>

<h2>시트의 표현을 내부 시스템까지 가져오지 않기</h2>
<p>구글 시트에서 특정 숫자가 ‘입금 합계가 놓인 셀’에 있다고 해볼게요.</p>
<p>내부 ERP가 이 셀의 위치를 그대로 업무 식별자로 사용하면 시트의 열 하나만 이동해도 시스템이 깨집니다. 개발자가 아닌 사용자가 시트의 구조를 조금 수정한 일이 서버 장애로 이어질 수도 있어요.</p>
<p>그래서 Express 서버는 물리적인 셀 위치를 내부 서버에 그대로 전달하지 않습니다.</p>
<pre><code>입금 합계가 놓인 셀
       ↓
2026년 12월 5주차
예상값
입금 합계
0원
</code></pre>
<p>외부 시스템의 표현 방식이 내부 업무 모델 전체로 퍼지지 않도록 중간에서 변환하는 구조를 <strong>오염 방지 계층(Anti-Corruption Layer)</strong>이라고 합니다.</p>
<p>구글 시트의 배치가 바뀌면 Express 서버의 해석 방식을 수정합니다. 하지만 정산 상태와 승인 규칙을 관리하는 Spring Boot 서버까지 셀 위치를 알 필요는 없습니다.</p>
<p>반대로 승인 절차가 달라지더라도 구글 시트를 읽는 코드까지 수정할 필요는 없고요.</p>
<p>서버를 두 개로 나눈 이유는 사용하는 기술이 달라서가 아니었습니다. <mark>서로 다른 이유로 변경되는 코드를 분리하기 위해서였습니다.</mark></p>

<h2>Phase 2: 상태를 직접 수정하지 않고 명령을 보낸다</h2>
<p>일반적인 데이터 수정 기능이라면 다음처럼 요청할 수 있습니다.</p>
<pre><code>이 주정산의 상태를 완료로 바꿔주세요.
</code></pre>
<p>하지만 이런 요청은 사용자가 원하는 결과를 서버가 그대로 저장하게 합니다.</p>
<p>현재 상태에서 완료로 이동해도 되는지, 사용자가 어떤 데이터를 확인했는지, 누락된 항목은 없었는지 알기 어렵습니다.</p>
<p>그래서 MYSCube는 상태 값을 직접 수정하는 대신 사용자가 하려는 일을 요청하도록 바꿨습니다.</p>
<pre><code>2026년 8월 2주차의 현금흐름을 확인했고
변경사항을 모두 반영했으니
주정산 완료 절차를 시작해주세요.
</code></pre>
<p>실제 완료 요청에는 다음과 같은 정보가 들어갑니다.</p>
<pre><code>완료하려는 연월과 주차
변경사항이 있었는지 여부
사용자가 확인한 검증 결과
같은 요청을 구분하는 작업 번호
</code></pre>
<p>요청을 받은 서버는 여기에 현재 정산 상태와 데이터 판본을 직접 읽어 검증합니다. 사용자가 다음 상태를 직접 지정하지 않는 것이 중요합니다.</p>
<p>사용자는 완료 작업을 요청하고, 서버가 현재 상태와 권한, 데이터 판본과 검증 결과를 확인해 다음 상태를 결정합니다.</p>
<p>이처럼 결과 데이터를 직접 수정하는 대신 사용자의 의도를 전달하는 방식을 <strong>명령 중심 모델(Command Model)</strong>이라고 합니다.</p>
<p>상태 머신은 어디로 이동할 수 있는지를 제한합니다. 명령은 왜 상태를 이동하려는지를 표현하고요.</p>
<p>두 구조를 함께 사용하면서 주정산 완료는 단순한 데이터 수정이 아니라, 검증 가능한 업무 행위가 됐습니다.</p>

<h2>명령 하나는 어디까지 함께 성공해야 할까요?</h2>
<p>주정산 완료는 상태 필드 하나를 바꾸는 작업이 아닙니다.</p>
<p>서버에서는 대략 다음 순서로 처리합니다.</p>
<ol>
<li>같은 작업 번호가 이미 처리됐는지 확인합니다.</li>
<li>월결산으로 잠긴 기간인지 확인합니다.</li>
<li>현재 정산 상태와 데이터 판본을 읽습니다.</li>
<li>이후 16주의 예상 현금흐름을 검증합니다.</li>
<li>완료 시점의 데이터를 별도로 보관합니다.</li>
<li>주정산 상태를 승인 대기로 변경합니다.</li>
<li>처리자와 검증 결과를 변경 이력에 추가합니다.</li>
</ol>
<p>5번까지 성공한 뒤 6번이 실패하면 어떻게 될까요?</p>
<p>완료 시점의 데이터는 남았지만 화면에는 여전히 업데이트 대기로 표시됩니다. 반대로 상태만 승인 대기로 바뀌고 검증 결과가 저장되지 않으면 승인자는 무엇을 확인해야 하는지 알 수 없습니다.</p>
<p>그래서 이 과정은 하나의 트랜잭션 안에서 실행합니다.</p>
<p>트랜잭션은 여러 저장 작업을 하나의 작업처럼 묶는 장치입니다. 중간 단계 중 하나라도 실패하면 앞에서 처리한 내용도 함께 취소합니다.</p>
<pre><code>runInTransaction(() -&gt; {
    checkDuplicateRequest();
    requireMonthOpen();
    validateCurrentRevision();
    validateFutureCashflow();

    saveCompletionRecord();
    transitionToPendingApproval();
    appendChangeHistory();
});
</code></pre>
<p>실제 코드는 더 많은 조건을 다루지만 원칙은 단순합니다.</p>
<blockquote>
<p>상태, 검증 결과, 완료 시점의 데이터와 변경 이력은 함께 성공하거나 함께 실패해야 합니다.</p>
</blockquote>
<p>주정산에서는 일부 성공도 실패이기 때문입니다.</p>

<h2>서버 내부의 업무 규칙과 저장 방식을 분리하다</h2>
<p>Spring Boot 서버 안에서도 모든 코드를 한곳에 넣지는 않았습니다.</p>
<pre><code>HTTP 요청을 받는 부분
        ↓
주정산 명령을 실행하는 부분
        ↓
저장 방식과 연결하는 공통 약속
        ↓
Firestore 또는 관계형 데이터베이스
</code></pre>
<p>HTTP 요청을 받는 부분은 주소와 요청 형식, 인증된 사용자 정보를 이해합니다.</p>
<p>그다음 단계는 현재 정산 상태와 승인 권한, 16주 검증 같은 업무 규칙을 실행합니다. 이 코드는 데이터가 Firestore의 어떤 문서에 저장되는지 직접 알 필요가 없습니다.</p>
<p>마지막 단계가 실제 저장 방식을 담당합니다.</p>
<pre><code>WeeklyExpensePersistence
    ├── Firestore 저장 구현
    └── 관계형 데이터베이스 저장 구현
</code></pre>
<p>업무 코드가 필요로 하는 저장 기능을 먼저 약속하고, 실제 데이터베이스에 맞게 그 약속을 구현한 구조입니다.</p>
<p>개발에서는 안쪽의 업무 규칙과 바깥쪽의 저장 기술을 연결하는 방식을 <strong>Ports and Adapters</strong>, 또는 <strong>Hexagonal Architecture</strong>라고 부릅니다.</p>
<p>여기서 Port는 업무 코드가 필요로 하는 기능의 약속입니다. Adapter는 그 약속을 Firestore나 관계형 데이터베이스에 맞게 실제로 구현한 코드예요.</p>
<p>이 구조를 선택한 목적은 데이터베이스를 마음대로 교체하기 위해서만은 아니었습니다.</p>
<p>기존 Firestore 저장 방식과 새로운 관계형 데이터베이스가 함께 존재하는 기간에도 주정산 규칙을 두 번 구현하지 않기 위해서였습니다.</p>

<h2>기존 구조를 한 번에 교체하지 않았어요</h2>
<p>MYSCube의 기존 기능 중에는 화면이나 Express 서버가 Firestore를 직접 사용하는 경로도 있었습니다.</p>
<p>이를 한 번에 모두 Spring Boot 서버로 옮기면 변경 범위가 너무 커집니다. 주정산, 현금흐름, 월결산을 동시에 바꾸다가 문제가 생기면 어느 경계에서 잘못됐는지 찾기도 어려워요.</p>
<p>그래서 새로운 정산 명령부터 Spring Boot 서버에 권한을 두고, 기존 경로는 검증이 끝난 기능부터 하나씩 닫았습니다.</p>
<pre><code>기존 구조
화면 또는 Express 서버 → Firestore

전환 중
화면 → Express 서버 → Spring Boot 서버 → Firestore

목표 구조
화면 → Express 서버 → Spring Boot 서버 → 공식 저장소
</code></pre>
<p>기존 시스템을 한 번에 없애지 않고 새로운 구조로 조금씩 대체하는 방식을 <strong>교살자 패턴(Strangler Fig Pattern)</strong>이라고 합니다.</p>
<p>큰 나무 주변에서 새로운 나무가 자라 기존 나무를 서서히 대체하는 모습에서 나온 이름이에요.</p>
<p>MYSCube에서도 기존 주차 마감 기능을 계속 확장하지 않았습니다. 새로운 월결산 경계를 만든 뒤 검증이 끝난 기존 마감 경로부터 사용하지 않도록 전환했습니다.</p>
<p>전환 기간에는 두 구조를 함께 관리해야 한다는 비용이 있습니다. 대신 전체 시스템을 한 번에 다시 만드는 위험을 줄이고, 기능별로 실제 운영 검증을 거칠 수 있습니다.</p>

<h2>한 주를 완료하는데 왜 256개의 값을 확인할까요?</h2>
<p>주정산 완료 시 Spring Boot 서버는 현재 한 주만 확인하지 않습니다.</p>
<p>현재 주차부터 이후 15개 재무 주차까지, 총 16주를 확인합니다. 각 주에는 예상 현금흐름을 구성하는 16개 항목이 있어요.</p>
<pre><code>16개 현금흐름 항목 × 16개 주차 = 256개 값
</code></pre>
<p>왜 이렇게 넓은 범위를 볼까요?</p>
<p>현금흐름 관리의 목적은 이번 주의 금액을 기록하는 것만이 아닙니다. 앞으로 입금이 언제 들어오고, 어느 시점에 지출이 발생하며, 가까운 미래에 잔액이 부족해지지는 않는지 확인하는 일이기도 해요.</p>
<p>현재 주만 채운 상태에서 주정산을 완료할 수 있다면 다음 달의 예상 현금흐름이 모두 비어 있어도 시스템은 정상이라고 판단하게 됩니다.</p>
<p>그래서 주정산 완료 조건을 다음과 같이 정했습니다.</p>
<blockquote>
<p>현재 주차를 포함한 16주 동안 예상 현금흐름 256개 값이 모두 입력되어 있어야 한다.</p>
</blockquote>
<p>여기서 빈칸과 0원도 구분합니다.</p>
<p>0원은 담당자가 확인한 결과 금액이 없다는 뜻입니다. 반면 빈칸은 아직 입력하지 않았다는 뜻일 수 있어요. 계산할 때는 둘 다 0처럼 보일 수 있지만, 업무 상태는 다릅니다.</p>
<p>12월 마지막 주에 주정산을 하더라도 검증은 12월에서 멈추지 않습니다. 다음 해의 주차까지 이어서 16주를 확인합니다.</p>
<p>검증에 실패하면 단순히 “입력값이 올바르지 않습니다”라고 표시하지 않습니다. 어느 기간의 어떤 항목이 비어 있는지, 전체 확인 범위가 어디까지인지 함께 보여줍니다.</p>

<h2>경고를 확인하는 사이 숫자가 바뀐다면요?</h2>
<p>모든 값이 준비될 때까지 기다릴 수 없는 경우도 있습니다.</p>
<p>아직 확정되지 않은 입금 일정이 있지만 현재 확인된 정보를 기준으로 주정산을 진행해야 할 수 있어요. 모든 예외를 막으면 사용자는 시스템 밖에서 별도의 기록을 만들기 시작합니다.</p>
<p>그래서 누락된 값이 있으면 어떤 기간의 어떤 항목이 비어 있는지 보여주고, 내용을 확인한 뒤 예외적으로 진행할 수 있게 했습니다.</p>
<p>다만 ‘확인했습니다’라는 버튼만 두지는 않았어요.</p>
<p>다음과 같은 상황이 생길 수 있기 때문입니다.</p>
<pre><code>1. 사용자가 누락된 항목 12개를 확인한다.
2. 다른 사용자가 구글 시트의 값을 수정한다.
3. 실제 누락 항목이 7개로 바뀐다.
4. 첫 사용자가 이전 화면을 기준으로 진행한다.
</code></pre>
<p>첫 사용자가 확인한 문제와 실제 저장 시점의 문제가 달라졌습니다.</p>
<p>이를 막기 위해 서버는 사용자가 확인한 누락 항목과 기간을 일정한 순서로 정리한 뒤, 내용이 같은지 확인할 수 있는 짧은 지문을 만듭니다.</p>
<p>데이터가 조금이라도 달라지면 이 지문도 달라져요.</p>
<p>개발에서는 이렇게 데이터의 내용으로부터 만든 식별값을 <strong>해시(Hash)</strong>라고 합니다.</p>
<p>사용자가 예외 진행을 요청하면 서버는 현재 데이터를 다시 검증합니다.</p>
<ul>
<li>사용자가 확인한 내용 지문</li>
<li>현재 데이터로 다시 만든 내용 지문</li>
<li>사용자가 확인한 누락 항목 수</li>
<li>현재의 누락 항목 수</li>
</ul>
<p>이 값들이 모두 같을 때만 요청을 처리합니다. 검토 이후 데이터가 달라졌다면 최신 내용을 다시 확인하게 합니다.</p>
<p>데이터를 오랫동안 잠그지 않고 저장 직전에 사용자가 본 판본이 여전히 최신인지 확인하는 방식을 <strong>낙관적 동시성 제어(Optimistic Concurrency Control)</strong>라고 합니다.</p>
<p>쉽게 말하면 이런 약속입니다.</p>
<blockquote>
<p>다른 사람이 수정하지 않았을 것이라고 우선 가정하되, 실제 저장 직전에는 반드시 다시 확인한다.</p>
</blockquote>

<h2>트랜잭션만으로는 충분하지 않았어요</h2>
<p>트랜잭션을 적용하면 서버 내부의 부분 저장을 막을 수 있습니다. 하지만 사용자가 화면을 열어둔 동안 다른 사용자가 데이터를 수정하거나, 오래된 요청이 뒤늦게 도착하는 문제까지 해결하지는 못합니다.</p>
<p>MYSCube는 서로 다른 실패를 막기 위해 몇 가지 장치를 함께 사용합니다.</p>
<table>
<thead>
<tr><th>장치</th><th>막으려는 문제</th></tr>
</thead>
<tbody>
<tr><td>트랜잭션</td><td>하나의 명령이 절반만 저장되는 문제</td></tr>
<tr><td>데이터 판본</td><td>오래된 화면에서 최신 데이터를 덮어쓰는 문제</td></tr>
<tr><td>작업 번호</td><td>버튼 재클릭과 네트워크 재시도로 중복 처리되는 문제</td></tr>
<tr><td>편집 순번</td><td>만료된 편집 화면의 요청이 뒤늦게 저장되는 문제</td></tr>
</tbody>
</table>
<p>편집을 시작한 사용자에게 일정 시간 동안 유효한 편집 권한과 순번을 발급한다고 해볼게요.</p>
<p>첫 번째 사용자가 순번 10으로 편집하고 있던 중 연결이 끊겼습니다. 이후 새로운 편집 세션이 시작되어 순번 11을 받았습니다.</p>
<p>이때 순번 10의 저장 요청이 뒤늦게 도착하더라도 서버는 이를 거절합니다. 지금 유효한 편집 순번은 11이기 때문입니다.</p>
<p>이 순번을 개발에서는 <strong>펜싱 토큰(Fencing Token)</strong>이라고 합니다.</p>
<p>자물쇠를 가지고 있었는지만 확인하는 것이 아니라, 지금도 가장 최신 자물쇠를 가지고 있는지 확인하는 방식이에요.</p>
<p>트랜잭션, 판본, 작업 번호와 편집 순번은 비슷해 보이지만 서로 대체할 수 없습니다.</p>
<p>트랜잭션이 있어도 같은 요청이 두 번 들어올 수 있습니다. 중복 방지가 있어도 오래된 화면의 데이터가 최신 값을 덮어쓸 수 있고요.</p>
<p>어떤 실패를 막으려는지 구분한 뒤 각각의 경계를 두었습니다.</p>

<h2>완료 버튼을 두 번 누르면 어떻게 될까요?</h2>
<p>네트워크 요청은 항상 한 번만 전달되지 않습니다.</p>
<p>사용자가 완료 버튼을 두 번 누를 수도 있고, 서버의 처리는 끝났지만 응답이 돌아오는 중에 연결이 끊길 수도 있어요.</p>
<p>완료 요청마다 고유한 작업 번호를 붙인 이유입니다.</p>
<pre><code>첫 번째 요청
작업 번호: weekly-close-2026-08-w2-001

응답 유실 후 재요청
작업 번호: weekly-close-2026-08-w2-001
</code></pre>
<p>Spring Boot 서버는 같은 작업 번호를 이미 처리했다면 새로운 완료 기록을 만들지 않고 기존 결과를 돌려줍니다.</p>
<p>같은 요청을 여러 번 실행해도 결과가 한 번 실행한 것과 같게 만드는 성질을 <strong>멱등성(Idempotency)</strong>이라고 합니다.</p>
<p>어려운 이름이지만 해결하려는 문제는 단순합니다.</p>
<blockquote>
<p>사용자가 버튼을 다시 눌러도 같은 정산이 두 번 처리되지 않게 한다.</p>
</blockquote>
<p>그렇다면 화면 가까이에 있는 Express 서버가 Spring Boot 서버의 응답을 받지 못한 경우는 어떻게 해야 할까요?</p>
<pre><code>Express 서버 → Spring Boot 서버
주정산을 완료해주세요.

Spring Boot 서버
저장 완료

Spring Boot 서버 → Express 서버
응답 전송 중 연결 끊김
</code></pre>
<p>Express 서버는 응답을 받지 못했습니다. 하지만 Spring Boot 서버에는 이미 완료 기록이 저장됐습니다.</p>
<p>이때 요청을 실패로 표시하면 화면과 실제 상태가 달라집니다. 무조건 다시 처리하면 기록이 중복될 수 있고요.</p>
<p>그래서 Express 서버는 시간 초과를 곧바로 실패로 확정하지 않습니다.</p>
<p>같은 작업 번호로 다시 요청하거나 Spring Boot 서버의 공식 상태를 조회합니다. Spring Boot 서버는 이미 처리된 요청이라면 기존 결과를 반환합니다.</p>
<p>분산된 서버가 함께 일할 때는 네트워크 응답보다 저장된 상태가 더 신뢰할 수 있습니다.</p>

<h2>공식 상태는 한 서버만 변경한다</h2>
<p>Express 서버와 Spring Boot 서버가 모두 주정산 상태를 변경할 수 있다면 어느 쪽의 기록이 공식 상태인지 알기 어렵습니다.</p>
<p>따라서 Express 서버는 명령을 전달하고 장애 상황을 복구하지만, 정산 상태를 직접 만들어내지는 않습니다. 공식적인 상태 전이는 Spring Boot 서버만 수행합니다.</p>
<p>이런 원칙을 <strong>단일 쓰기 권한(Single Writer Principle)</strong>이라고 합니다.</p>
<pre><code>Express 서버
“이 주정산을 완료해 주세요.”

Spring Boot 서버
“현재 상태와 권한, 판본을 확인한 결과
승인 대기로 전환할 수 있습니다.”
</code></pre>
<p>상태를 변경하는 곳이 하나이기 때문에 장애가 발생해도 어디에서 결과를 확인해야 하는지가 명확합니다.</p>
<p>같은 계산과 상태 전이 규칙을 두 서버에 중복해서 구현하지 않아도 되고요.</p>

<h2>상태가 늘어나자 조회 방식도 바뀌었어요</h2>
<p>주정산 상태를 구체적으로 관리하자 대시보드의 조회 문제가 보이기 시작했습니다.</p>
<p>대시보드에서는 여러 사업의 현재 정산 상태를 한 번에 보여줘야 합니다. 처음에는 사업마다 상태 조회 요청을 하나씩 보냈습니다.</p>
<pre><code>사업 1개 → 요청 1번
사업 100개 → 요청 100번
</code></pre>
<p>기능은 동작하지만 사업이 늘어날수록 요청도 같은 속도로 늘어납니다. 이런 문제를 개발에서는 <strong>N+1 요청 문제</strong>라고 합니다.</p>
<p>그래서 상태를 바꾸는 기능은 한 사업씩 안전하게 처리하되, 조회는 여러 사업의 상태를 한 번에 요청할 수 있도록 분리했습니다.</p>
<pre><code>사업 100개
→ 상태 일괄 조회 1번
→ 사업별 결과 100개
</code></pre>
<p>한 사업의 상태를 불러오지 못하더라도 전체 대시보드가 실패하지 않도록 사업별 오류도 나누었습니다.</p>
<p>상태를 변경하는 작업과 여러 상태를 읽는 작업은 요구사항이 달랐습니다.</p>
<ul>
<li>상태 변경은 한 사업의 데이터를 정확하게 처리해야 합니다.</li>
<li>상태 조회는 여러 사업의 결과를 빠르게 모아야 합니다.</li>
</ul>
<p>개발에서는 상태를 변경하는 책임과 조회하는 책임을 분리하는 설계를 <strong>CQRS(Command Query Responsibility Segregation)</strong>라고 부릅니다.</p>
<p>다만 MYSCube를 완전한 CQRS 시스템이라고 부르지는 않습니다.</p>
<p>상태 변경과 조회를 위해 별도의 데이터베이스를 운영하거나, 변경 이벤트로 조회 전용 데이터를 만드는 구조까지 도입하지 않았기 때문입니다. 현재 필요한 범위에서 API와 읽기 방식만 분리했습니다.</p>
<p>패턴을 끝까지 구현하는 것보다 실제 문제에 필요한 만큼만 사용하는 쪽을 선택했습니다.</p>

<h2>Phase 3: 승인할 숫자를 따로 보관하기</h2>
<p>마지막으로 주정산과 월결산의 경계를 나눴습니다.</p>
<p>주정산이 완료되면 서버는 당시의 예상값과 실적값, 확인 전후의 데이터 판본과 검증 결과를 보관합니다.</p>
<p>이 기록을 보면 담당자와 승인자가 어떤 데이터를 확인했는지 알 수 있어요. 하지만 주정산 완료가 곧 데이터 잠금을 의미하지는 않습니다.</p>
<p>숫자를 공식 기록으로 확정하는 경계는 월결산입니다.</p>
<p>월결산에는 요청자와 승인자 사이에 시간이 생깁니다.</p>
<p>담당자가 월결산을 요청한 뒤 승인자가 검토하기 전까지 구글 시트나 내부 ERP의 숫자가 수정될 수 있어요. 승인하는 순간 데이터를 다시 읽으면 두 사람이 서로 다른 숫자를 보고 결산하게 됩니다.</p>
<p>그래서 월결산을 요청하는 순간, 승인 대상이 되는 숫자를 별도의 고정본으로 보관합니다.</p>
<pre><code>계속 수정되는 현금흐름
        ↓ 월결산 요청
승인할 숫자를 고정본으로 보관
        ↓ 승인자 검토
공식적인 월 마감 기록으로 확정
</code></pre>
<p>승인자는 현재 구글 시트를 다시 읽지 않습니다. 요청 시점에 만들어진 고정본을 검토합니다.</p>
<p>그사이에 원본 데이터가 바뀌었다면 기존 결산 요청에 몰래 반영하지 않습니다. 변경된 숫자로 새로운 결산을 요청해야 해요.</p>
<p>개발에서는 특정 시점의 데이터를 고정해서 보관한 기록을 <strong>불변 스냅샷(Immutable Snapshot)</strong>이라고 부릅니다.</p>
<p>사진을 저장한다는 뜻이 아니라, 승인할 데이터의 사본을 만든 뒤 나중에 그 내용을 바꿀 수 없게 한다는 뜻입니다. 본문에서는 이를 ‘결산 요청 시점의 고정본’이라고 부르겠습니다.</p>
<p>고정본에는 금액만 들어 있지 않습니다.</p>
<ul>
<li>결산 대상 기간</li>
<li>예상값과 실적값</li>
<li>데이터 판본</li>
<li>요청자와 요청 시각</li>
<li>전체 내용이 같은지 확인하는 지문</li>
</ul>
<p>내용 지문을 다시 비교하면 요청자가 올린 고정본이 승인 전에 달라지지 않았는지 확인할 수 있습니다.</p>

<h2>고정본이 하나의 문서에 들어가지 않았어요</h2>
<p>월결산은 한 달만 따로 확정하지 않습니다.</p>
<p>이번 달의 시작 잔액은 이전 달의 마감 잔액에서 만들어집니다. 과거 한 달의 숫자가 바뀌면 이후 기간의 잔액도 함께 달라질 수 있어요.</p>
<p>따라서 기준 시작 시점부터 선택한 월까지를 하나의 누적 범위로 확정합니다.</p>
<p>그런데 누적 기간의 예상값과 실적값, 판본과 검증 결과를 하나의 Firestore 문서에 모두 담으면 다른 문제가 생깁니다.</p>
<p>Firestore 문서 하나에는 약 1MB의 크기 제한이 있습니다. 사업 기간이 길어질수록 하나의 문서로는 전체 결산 데이터를 보관하기 어려워요.</p>
<p>그래서 월결산 고정본을 두 부분으로 나눴습니다.</p>
<pre><code>월결산 머리 기록
├── 어느 달까지 마감됐는지
├── 현재 결산 판본
└── 전체 내용의 대표 지문

월별 데이터 조각
├── 2026년 1월 고정본
├── 2026년 2월 고정본
└── 2026년 3월 고정본
</code></pre>
<p>물리적으로는 여러 문서에 나뉘지만 사용자에게는 하나의 월결산으로 보입니다.</p>
<p>일부 월만 저장되고 마감이 완료되는 일도 허용하지 않습니다. 모든 월별 데이터 조각과 대표 기록이 함께 저장돼야 월결산이 완료됩니다.</p>
<p>저장소의 기술적인 크기 제한이 사용자의 업무 모델까지 드러나지 않도록 한 것입니다.</p>

<h2>마감 이후에는 기존 기록을 덮어쓰지 않아요</h2>
<p>월결산이 끝난 뒤에도 꼭 수정해야 하는 값이 생길 수 있습니다.</p>
<p>이때 기존 결산 기록을 바로 덮어쓰면 무엇이 바뀌었는지 알 수 없습니다.</p>
<p>그래서 이전 기록은 그대로 두고 새로운 변경 사실을 이어서 남깁니다.</p>
<pre><code>기존 금액: 1,000,000원
변경 금액: 1,200,000원
변경 사유: 입금 일정 정정
변경한 사람: 담당자 A
변경 시각: 2026년 8월 5일
변경 전후의 데이터 판본
</code></pre>
<p>기존 기록을 수정하지 않고 변경 내용을 계속 추가하는 방식을 개발에서는 <strong>추가 전용 감사 기록(Append-only Audit Log)</strong>이라고 합니다.</p>
<p>다만 MYSCube를 이벤트 소싱 시스템이라고 부르지는 않습니다.</p>
<p>모든 현재 상태를 과거의 변경 기록으로부터 매번 다시 만드는 구조는 아니기 때문입니다. 현재 상태는 별도로 저장하고, 설명이 필요한 재무 변경에 대해서만 과거 기록을 보존합니다.</p>
<p>설계에 사용한 일부 개념만 보고 전체 시스템을 더 큰 패턴으로 부르지 않는 것도 중요했습니다.</p>

<h2>구현하며 배운 것들</h2>
<h3>1. 완료와 잠금은 같은 상태가 아니었어요</h3>
<p>주정산은 사람이 업무를 확인했다는 기록입니다. 월결산은 데이터를 공식 기록으로 확정하는 경계이고요.</p>
<p>둘을 하나로 묶으면 현장의 변화를 막거나, 반대로 확정된 숫자를 너무 쉽게 바꾸게 됩니다.</p>

<h3>2. 백엔드를 나누는 것보다 권한을 나누는 일이 중요했어요</h3>
<p>Express와 Spring Boot라는 두 기술을 사용한 것이 핵심은 아니었습니다.</p>
<p>외부 데이터를 해석하는 책임과 정산 상태를 결정하는 책임을 나누고, 공식 상태를 변경하는 권한을 한 서버에 모은 것이 중요했습니다.</p>

<h3>3. 트랜잭션과 중복 방지, 판본 검사는 서로 다른 문제였어요</h3>
<p>트랜잭션은 하나의 명령이 절반만 저장되는 것을 막습니다.</p>
<p>작업 번호는 같은 요청이 두 번 처리되는 것을 막고, 데이터 판본과 내용 지문은 사용자가 확인하는 사이 숫자가 바뀌는 것을 막습니다. 편집 순번은 만료된 화면의 늦은 저장을 차단하고요.</p>
<p>비슷해 보이는 장치들이지만 각각 다른 실패를 다룹니다.</p>

<h3>4. 설계 패턴은 문제보다 먼저 오지 않았어요</h3>
<p>상태 머신이나 오염 방지 계층, Ports and Adapters, 멱등성을 먼저 정해두고 시스템을 만든 것은 아닙니다.</p>
<p>시트의 위치가 업무 모델까지 퍼지는 문제가 생겨 번역 경계를 만들었습니다. 두 서버가 같은 상태를 판단할 수 있어 쓰기 권한을 한곳에 모았습니다. 완료 여부만으로 업무를 설명할 수 없어 상태와 명령을 나눴고요.</p>
<p>패턴은 설계의 출발점이라기보다 반복해서 나타난 문제에 이름을 붙인 결과에 가까웠습니다.</p>

<h3>5. 어려운 용어보다 실패 상황이 먼저였어요</h3>
<p>‘낙관적 동시성 제어가 필요하다’고 시작했다면 실제로 무엇을 막으려는지 이해하기 어려웠을 것입니다.</p>
<p>하지만 사용자가 경고를 확인하는 사이 다른 사람이 숫자를 수정하는 상황부터 보면, 왜 저장 전에 데이터 판본을 다시 확인해야 하는지 자연스럽게 이해할 수 있습니다.</p>
<p>기술을 설명할 때도 패턴의 이름보다 그 패턴이 없을 때 어떤 문제가 생기는지를 먼저 보여주는 것이 중요했습니다.</p>

<h2>마무리</h2>
<p>처음에는 완료된 주차를 잠그면 문제가 해결될 것이라고 생각했습니다.</p>
<p>하지만 실제 사업의 현금흐름은 주정산이 끝났다고 멈추지 않았습니다. 예상 입금일이 달라지고, 누락된 지출이 발견되고, 다음 달 계획이 수정됐어요.</p>
<p>필요했던 것은 숫자가 절대 바뀌지 않는 시스템이 아니었습니다.</p>
<p>어떤 숫자를 확인했는지, 확인 이후 무엇이 바뀌었는지, 누가 승인했는지, 어느 시점부터 공식 기록이 되었는지를 설명할 수 있는 시스템이 필요했습니다.</p>
<p>그래서 주정산은 운영상의 확인으로, 월결산은 데이터 확정의 경계로 나눴습니다.</p>
<p>구글 시트를 읽는 Express 서버는 외부 데이터를 내부 업무 언어로 바꿉니다. Spring Boot 서버는 상태 전이와 승인, 판본과 저장 규칙을 책임집니다. 서버 내부에서는 업무 규칙과 데이터베이스 구현을 분리하고, 기존 저장 경로는 검증이 끝난 기능부터 단계적으로 교체하고 있습니다.</p>
<p>재미있는 점은 백엔드를 둘로 나누면서 시스템이 더 복잡해진 것이 아니라, 오히려 누가 무엇을 책임지는지가 더 선명해졌다는 것입니다.</p>
<p>기술은 늘어났지만 판단의 기준은 줄어들었습니다.</p>

안녕하세요. MYSC의 자체 개발 ERP인 MYSCube를 만들고 있는 MYSC AXR팀입니다.

> “구글 시트에 있는 값을 내부 시스템으로 가져오는 일인데, 왜 이렇게 오래 걸리지?”

개발을 시작할 때 저희도 비슷한 질문을 했습니다. 이미 시트에 숫자가 있고, 시스템에는 그 숫자를 담을 화면과 데이터베이스가 있습니다. 그렇다면 각 셀을 읽어 알맞은 칸에 저장하면 끝나는 일처럼 보였어요.

처음부터 특별히 어려운 기술이 필요해 보이지도 않았습니다. 구글 시트를 읽는 기능도, 데이터베이스에 값을 저장하는 기능도 이미 널리 쓰이고 있으니까요.

하지만 실제로 옮기려던 것은 셀에 보이는 숫자만이 아니었습니다.

어떤 숫자는 사람이 직접 입력한 값이었고, 어떤 숫자는 여러 항목을 더해 만든 결과였습니다. 빈칸과 0원은 화면에서는 비슷해 보여도 의미가 달랐어요. 같은 달의 값도 누가 언제 수정했는지에 따라 다시 확인해야 했고, 월결산이 승인된 뒤에는 일반적인 경로에서 더 이상 바뀌어서는 안 됐습니다.

시트에는 이런 규칙이 수식, 셀 위치, 색상, 담당자의 경험 속에 함께 들어 있었습니다. 숫자를 복사하는 것은 어렵지 않았지만, <mark>그 숫자를 공식 기록으로 인정해도 되는지 판단하는 일</mark>은 전혀 다른 문제였어요.

예를 들어 시트에는 100만 원이 적혀 있고 내부 ERP에는 90만 원이 저장돼 있다면 무엇이 맞을까요? 무조건 최근에 수정된 값을 선택할 수도 없습니다. 한쪽은 사람이 입력한 예상 금액이고 다른 한쪽은 승인된 실제 금액일 수 있기 때문이에요.

이때 필요한 것은 단순한 동기화 기능이 아니라, 어떤 조건에서 어느 값을 공식값으로 볼지 정하는 정책입니다.

그래서 개발이 길어진 이유는 기술이 특별히 새로워서가 아니었습니다. 오랫동안 사람과 시트가 함께 처리하던 판단을, 코드가 반복해서 실행할 수 있는 규칙으로 바꾸어야 했기 때문입니다.

## 월결산 담당자는 숫자를 한 번만 보지 않아요

먼저 사용자가 실제로 무엇을 하는지부터 살펴볼게요.

월결산 담당자는 시트에서 이번 달의 입금과 출금 내역을 확인합니다. 예상했던 금액과 실제로 발생한 금액을 비교하고, 빠진 항목이 없는지 살펴본 뒤 월결산을 승인해요. 숫자가 맞지 않으면 원본 내역으로 돌아가 수정하고 다시 합계를 확인합니다.

한 번 읽어서 저장하고 끝나는 작업이 아니에요. 원본과 계산 결과를 오가며 값의 근거를 확인하고, 마지막에는 “이제 이 숫자를 공식 기록으로 인정한다”는 결정을 내리는 과정에 가깝습니다.

문제는 기존 시트에서는 이 과정의 일부를 수식이, 일부를 담당자가 맡고 있었다는 점입니다. 시스템으로 옮기면서 담당자의 화면만 새로 만들면 수식이 하던 판단이 사라지고, 수식만 그대로 옮기면 사람이 확인하고 승인하던 맥락이 사라져요.

그래서 문제를 다시 정의했습니다.

> “시트의 값을 어떻게 가져올까?”가 아니라 “시트에서 이루어지던 계산과 판단을 시스템의 어느 부분이 책임질까?”로요.

이 질문으로 바꾸자 단순한 데이터 연동처럼 보였던 일이 백엔드의 책임과 데이터의 소유권을 정하는 문제로 보이기 시작했습니다.

## 시트의 언어와 월결산의 언어를 나누다

앞선 글에서는 이 문제를 다루기 위해 두 개의 백엔드를 둔 이유를 소개했습니다.

첫 번째 서버는 구글 시트의 행과 열을 읽어 프로젝트·기간·항목이라는 업무 정보로 바꿉니다. 브라우저 화면에 필요한 데이터를 가까이에서 만들어 주기 때문에 화면을 위한 백엔드(Backend for Frontend, 이하 BFF)라고 불러요.

두 번째 서버는 금액을 다시 계산하고 공식 기록을 저장합니다. Spring Boot로 만들었고, 자바 프로그램을 실행하는 기반인 자바 가상 머신(Java Virtual Machine, 이하 JVM) 위에서 동작합니다.

구글 시트의 모양은 자주 바뀌지만 월결산의 계산과 승인 규칙은 더 엄격하게 관리해야 했어요. 그래서 BFF는 시트와 화면의 변화를 받아들이고, Spring Boot 서버는 조직이 공식적으로 인정할 숫자를 결정하도록 역할을 나눴습니다.

![구글 시트의 셀과 수식을 화면 가까운 서버가 업무 정보로 번역하고, 애플리케이션과 도메인이 검증한 뒤 MYSCube 공식 저장소에 기록하는 흐름](/assets/images/diagrams/building-ledger-04/01-sheet-to-cube.png)
*그림 1. 시트의 표현은 경계에서 번역하고, 공식 기록에 관한 판단은 업무 규칙 안에서 내립니다.*

그런데 아키텍처 그림에 서버를 두 개 그렸다고 책임까지 자동으로 나뉘지는 않았습니다. 실제 코드에는 월결산 수식 검증과 변경 여부 확인이 양쪽에 남아 있었어요. Spring Boot 서버 안에서도 어떤 규칙은 외부 요청을 받는 코드에, 어떤 규칙은 저장 코드에, 어떤 규칙은 큰 서비스 클래스에 섞여 있었습니다.

## 그런데 검증을 두 번 하면 더 안전하지 않을까

시트의 월결산 값을 MYSCube에 반영하는 흐름은 처음에 다음과 같았습니다.

1. BFF가 구글 시트와 MYSCube의 값을 비교합니다.
2. BFF가 수식과 데이터 변경 여부를 미리 검사합니다.
3. 이상이 없으면 Spring Boot 서버에 저장을 요청합니다.
4. Spring Boot 서버가 다시 값을 검사한 뒤 공식 기록으로 저장합니다.

표면적으로는 안전해 보입니다. 중요한 숫자를 두 번 검사하니 한 번만 검사하는 것보다 견고해 보이기도 해요.

하지만 두 검사는 같은 순간에 실행되지 않습니다. BFF가 검사를 마친 직후 누군가 시트를 수정할 수 있고, 공식 기록 서버가 실제 저장을 시작할 때는 이미 다른 상태가 되어 있을 수 있어요. 반대로 BFF가 조금 오래된 정보를 기준으로 요청을 거절했지만, 공식 상태에서는 정상인 경우도 생길 수 있습니다.

이 문제는 검사를 많이 한다고 해결되지 않았습니다. 오히려 **서로 다른 두 곳이 같은 업무 판단을 내리는 구조**가 됐어요.

보안에서는 서로 다른 방어 수단을 여러 겹 두는 것을 심층 방어(Defense in Depth)라고 합니다. 그러나 같은 업무 규칙을 두 서버에 복사하고 각각 승인과 거절을 결정하게 만드는 것은 심층 방어와 달라요. 규칙이 수정될 때 한쪽만 바뀌면 두 서버가 서로 다른 답을 내리기 때문입니다.

저희에게 필요했던 것은 검사를 두 번 하는 구조가 아니라, **판단은 한 번만 하되 그 결과를 여러 단계에서 확인하는 구조**였습니다.

## 결정: 저장하는 순간의 판단을 공식 판단으로 삼기

월결산에서 가장 중요한 질문은 “요청을 보낼 때 값이 맞았는가?”가 아니라 “공식 기록으로 저장되는 순간에도 값이 맞는가?”였습니다.

그래서 월결산 수식 검증과 변경 여부 확인을 공식 기록 서버의 저장 명령 안으로 옮겼습니다. 서버는 다음 작업을 하나의 흐름으로 처리해요.

- 요청자가 기준으로 삼은 데이터 버전을 확인합니다.
- 월결산에 필요한 고정값이 빠짐없이 들어왔는지 검사합니다.
- 금액과 수식이 현재 업무 규칙에 맞는지 다시 계산합니다.
- 앞선 조건이 모두 맞을 때만 공식 기록을 변경합니다.

여기서 데이터 버전은 사용자가 내용을 확인한 뒤 저장 버튼을 누르는 사이 다른 사람이 같은 데이터를 먼저 바꾸지 않았는지 확인하기 위한 번호입니다. 요청의 번호와 서버의 현재 번호가 다르면, 오래된 화면으로 새 값을 덮어쓰지 않고 다시 확인하도록 안내해요.

이 방식을 낙관적 동시성 제어(Optimistic Concurrency Control)라고 합니다. 대부분의 시간에는 충돌이 없다고 보고 작업을 허용하되, 실제로 저장할 때 버전이 달라졌다면 그 순간 충돌을 감지하는 방식이에요.

중요한 점은 이 검사가 실제 저장과 떨어져 있지 않다는 것입니다. 검사를 먼저 끝내고 나중에 저장하면 그 짧은 사이에도 상태가 달라질 수 있어요. 그래서 확인과 변경을 같은 트랜잭션 경계 안에 두었습니다. 검사에 사용한 상태와 저장할 때의 상태가 어긋나지 않도록 한 것이죠.

하나의 시스템만 공식 상태를 변경하도록 만드는 원칙을 단일 작성자(Single Writer)라고 합니다. 특정 기술을 선호한다는 뜻이 아니라, <mark>같은 사실에 대해 두 곳이 서로 다른 결론을 내리지 않게 만드는 운영 규칙</mark>에 가깝습니다.

## 그런데 서버를 나눈 것만으로는 부족했어요

결정권을 공식 기록 서버로 모은 뒤에는 서버 내부를 다시 살펴봐야 했습니다.

처음에는 외부 요청을 받는 객체가 “한 달치 데이터는 160개여야 한다”는 규칙을 검사하고 있었어요. MYSCube의 월별 현금흐름은 16개 항목, 두 가지 구분, 최대 5주를 기준으로 관리하기 때문에 한 달의 입력 단위가 160개가 됩니다.

이 숫자는 단순한 전송 형식이 아니에요. 159개만 들어왔다면 요청 본문의 길이가 짧은 것이 아니라, 이번 달 공식 기록에서 확인해야 할 항목 하나가 사라졌다는 뜻입니다.

이 규칙은 외부 요청을 받을 때만 필요하지 않습니다. 파일에서 불러오든, 내부 작업이 만들든, 관리자가 복구를 실행하든 동일하게 지켜야 하는 월결산 자체의 규칙이에요.

그런데 규칙이 API 요청 객체에 있으면 저장 코드가 API 객체를 불러와 검사하게 됩니다. 바깥쪽의 전달 형식을 다루는 코드가 안쪽의 업무 규칙을 소유하고, 저장 계층이 다시 API 계층에 의존하게 돼요. 폴더를 `domain`, `application`, `storage`로 나누어도 실제 의존 방향은 반대일 수 있습니다.

## 160개라는 규칙은 어디에 있어야 할까

선택지는 세 가지였습니다.

| 선택지 | 장점 | 문제 |
| --- | --- | --- |
| 요청 객체에서 검사 | 구현이 가장 단순함 | API를 거치지 않는 흐름에서는 규칙이 사라짐 |
| 각 서비스에서 반복 검사 | 흐름별 대응이 쉬움 | 규칙을 바꿀 때 여러 곳을 함께 수정해야 함 |
| 월결산 자체가 검사 | 들어오는 경로와 무관하게 같은 규칙 적용 | 기존 호출부를 도메인 객체 중심으로 옮겨야 함 |

저희는 세 번째를 선택했습니다. `CashflowMonthCellSet`이라는 도메인 객체가 한 달치 현금흐름의 완전성을 책임하게 만들었어요.

실제 코드를 게시용으로 줄이면 다음과 같습니다.

```java
public final class CashflowMonthCellSet {
    public record Cell(
        String mode,
        int weekNo,
        String line,
        String state,
        BigDecimal amount
    ) {}

    public static List<Cell> requireComplete(List<Cell> cells) {
        if (cells == null || cells.size() != 160) {
            throw new IllegalArgumentException(
                "한 달의 현금흐름은 160개 항목이 모두 필요합니다."
            );
        }

        for (Cell cell : cells) {
            requireSupportedWeek(cell.weekNo());
            requireSupportedLine(cell.line());
            requireValidStateAndAmount(cell.state(), cell.amount());
        }

        requireNoDuplicates(cells);
        return List.copyOf(cells);
    }
}
```

이 객체는 다음 내용을 알고 있습니다.

- 한 달을 구성하는 값이 160개인지
- 같은 항목이 중복으로 들어오지 않았는지
- 값이 비어 있는 상태, 실제 숫자 0인 상태, 금액이 있는 상태가 구분되는지
- 금액이 원 단위의 정수인지
- 항목과 기간을 식별하는 값이 올바른지

반대로 HTTP 주소나 Firestore 문서 이름, 데이터베이스 테이블은 알지 못합니다. 업무 규칙을 실행하는 데 필요하지 않기 때문이에요.

작은 이동처럼 보이지만 효과는 컸습니다. 이제 같은 월결산이 어디에서 들어오든 동일한 규칙을 통과합니다. 요청 형식이 바뀌거나 저장 기술이 달라져도 “완전한 한 달”의 의미는 바뀌지 않아요.

## 요청, 업무 흐름, 규칙, 저장을 나누기

‘계층을 분리했다’는 말은 자칫 폴더 정리처럼 들릴 수 있습니다. 저희가 구분하려 한 것은 파일의 위치보다 **변경되는 이유**였어요.

*그림 2. 업무 규칙은 저장 기술을 향해 흐르지 않고, 저장 기술이 업무에서 정의한 경계에 맞춥니다.*

### API 계층: 외부의 말을 내부의 말로 번역한다

API 계층은 브라우저나 BFF가 보낸 요청을 받습니다. 필수 항목이 있는지 확인하고, 문자열로 들어온 날짜와 상태를 내부 객체로 바꾸며, 처리 결과를 응답으로 돌려줘요.

여기에는 “요청 형식이 올바른가?”라는 질문은 둘 수 있지만, “이 월결산을 승인해도 되는가?”라는 업무 판단은 두지 않습니다.

### 애플리케이션 계층: 한 번의 업무 흐름을 지휘한다

애플리케이션 계층은 사용자가 요청한 한 번의 업무를 끝까지 조율합니다. 월결산 반영이라면 권한과 중복 요청을 확인하고, 도메인에 검증을 맡긴 뒤 저장과 감사 기록을 하나의 흐름으로 묶어요.

각 금액을 직접 계산하기보다 필요한 객체를 불러 순서와 경계를 관리하는 역할입니다.

### 도메인 계층: 반드시 지켜야 할 업무 규칙을 표현한다

도메인 계층에는 현금흐름 셀 묶음, 결산 상태, 승인자 정책, 마감 기한처럼 저장 방식과 무관한 규칙을 둡니다.

승인할 수 있는 사람이 누구인지 판단하는 규칙은 화면도, Firestore 저장 코드도 아닌 도메인이 알아야 해요. 그래야 승인 화면이나 저장소가 바뀌어도 같은 규칙이 유지됩니다.

### 포트와 어댑터: 업무가 저장 기술을 직접 알지 않게 한다

애플리케이션이 월결산을 읽으려면 저장소가 필요합니다. 그렇다고 Firestore나 관계형 데이터베이스의 사용법까지 알게 하면, 저장 기술을 바꿀 때 업무 흐름도 함께 흔들려요.

그래서 안쪽에서는 필요한 기능의 형태만 정의하고, 바깥쪽 코드가 실제 저장 기술로 이를 구현하게 했습니다. 안쪽이 필요한 기능을 먼저 정의하고 바깥쪽이 맞추는 방식을 의존성 역전(Dependency Inversion)이라고 해요.

```java
// 애플리케이션이 필요한 읽기 기능을 먼저 정의합니다.
public interface CashflowReadPort {
    CashflowMonthCloseState findMonthClose(
        String organizationId,
        String projectId,
        String yearMonth
    );
}

@Service
public class CashflowReadService {
    private final CashflowReadPort readPort;

    public CashflowMonthCloseState monthClose(
        String organizationId,
        String projectId,
        String yearMonth
    ) {
        return readPort.findMonthClose(
            organizationId, projectId, yearMonth
        );
    }
}
```

현재 읽기 서비스는 얇은 위임에 가깝습니다. 지금 필요하지 않은 추상화를 더 넣지는 않았어요. 이후 조회 권한, 캐시 정책, 여러 저장소의 조합이 필요해질 때 그 책임을 받을 경계만 먼저 세웠습니다.

## “저장 성공” 응답만 믿지 않은 이유

공식 판단을 한 서버로 모았다고 해서 BFF가 아무것도 확인하지 않는 것은 아닙니다.

서버가 저장 성공을 응답하면 BFF는 공식 월결산 상태를 다시 읽습니다. 그리고 다음 내용을 대조해요.

- 같은 프로젝트의 결과인지
- 저장 요청에 사용한 버전이 반영됐는지
- 반영하려던 기간이 모두 포함됐는지
- 각 고정값이 요청한 결과와 정확히 같은지

이 과정은 BFF에서 업무 규칙을 다시 판단하는 것과 다릅니다. 계산을 반복하는 것이 아니라, **요청과 공식 저장 결과가 전송 과정에서 어긋나지 않았는지 확인하는 일**이에요.

![월결산 저장 요청 뒤 공식 저장 결과를 다시 조회해 요청한 항목과 버전을 대조하는 흐름](/assets/images/diagrams/building-ledger-04/03-write-readback.png)
*그림 3. 성공 응답을 받은 뒤에도 공식값을 다시 읽어 요청한 결과와 일치하는지 확인합니다.*

은행 이체를 요청한 뒤 “요청을 접수했습니다”라는 화면만 보고 잔액이 실제로 바뀌었다고 단정하지 않는 것과 비슷합니다. 최종 잔액을 다시 조회해야 이체 결과를 확신할 수 있으니까요.

이런 확인을 저장 후 재조회(Read After Write)라고 합니다. 재조회 결과가 다르면 MYSCube는 성공으로 포장하지 않고 다시 확인하거나 조정이 필요한 상태로 남깁니다. 결산 시스템에서 잘못된 성공 메시지는 명시적인 실패보다 더 위험하다고 판단했어요.

## 같은 문제가 월결산 승인에서도 나타났어요

이전에는 공식 월결산 상태를 읽은 뒤 BFF가 관리하던 별도의 요청 기록을 다시 합쳐 화면 상태를 만들었습니다. 두 자료가 같은 방향을 가리킬 때는 문제가 없었지만, 갱신 순서가 달라지면 공식 서버에서는 승인된 월이 화면에서는 승인 전처럼 보일 수 있었어요.

원인은 화면 표시가 아니라 권한의 중복이었습니다. 어떤 월이 승인됐는지 두 저장소가 함께 결정하고 있었기 때문이에요.

현재는 월결산 승인도 공식 서버의 상태 전이를 통해 처리하고, 화면은 그 결과를 그대로 읽도록 정리했습니다. BFF는 선택한 월과 사용자 의도를 정확히 전달하지만, 승인 상태를 덮어써서 새로운 사실을 만들지 않습니다.

| 구분 | BFF가 맡는 일 | 공식 기록 서버가 맡는 일 |
| --- | --- | --- |
| 구글 시트 | 행·열 읽기, 업무 단위로 변환 | 전달받은 값의 업무 규칙 검증 |
| 월결산 반영 | 변경 내용 표시, 요청 전달 | 버전 확인, 계산, 공식 저장 |
| 승인 | 선택한 월과 사용자 의도 전달 | 승인 가능 여부 판단, 상태 전이 |
| 결과 확인 | 공식값 재조회와 요청 결과 대조 | 공식 상태와 변경 이력 제공 |

## 고려했지만 선택하지 않은 것들

### BFF에서 모든 일을 끝내기

구글 시트를 가장 잘 이해하는 서버는 BFF입니다. 그러니 읽기, 계산, 검증, 저장을 모두 BFF에서 처리하는 방법이 가장 빠르게 보였어요.

하지만 시트의 열 위치와 월결산 규칙이 한 코드에 들어가면 둘 중 하나만 바뀌어도 전체 흐름을 다시 확인해야 합니다. 화면을 위한 서버가 공식 회계 기록까지 결정하면 다른 화면이나 내부 작업이 같은 규칙을 사용하기도 어려워져요. 초기 구현은 단순하지만 변경 비용이 계속 BFF에 쌓이는 선택이라 판단했습니다.

### 두 서버가 서로 같은 규칙으로 검사하기

두 서버에 같은 검사를 두면 한쪽의 실수를 다른 쪽이 막아줄 것처럼 보입니다. 실제로는 배포 시점과 사용하는 데이터의 시점이 달라, 규칙이 조금만 어긋나도 정상 요청을 거절하거나 잘못된 요청을 통과시킬 수 있었어요.

그래서 BFF에는 요청을 만들기 위한 형식 검사와 저장 결과를 확인하는 검증만 남겼습니다. 월결산을 승인하거나 거절하는 업무 판단은 공식 기록 서버 한곳에서 내립니다.

### 전체 구조를 한 번에 다시 만들기

가장 깨끗한 그림을 먼저 그리고 모든 코드를 한꺼번에 옮기는 방법도 고려할 수 있습니다. 하지만 월결산은 실제 업무가 매달 반복되는 운영 시스템이에요. 넓은 범위를 동시에 바꾸면 문제가 생겼을 때 어느 변경이 원인인지 찾기 어려워집니다.

저희는 월결산 수식 검증, 변경 여부 확인, 승인 상태처럼 실제로 두 개의 판단이 충돌한 지점부터 하나씩 옮겼습니다. 새 구조를 위한 빈 인터페이스를 미리 늘리기보다, 다음 책임을 옮길 때 필요한 경계를 그때 만들었어요.

## 이 결정에 따라온 비용

공식 판단을 한곳으로 모으면서 책임은 선명해졌지만 공짜는 아니었습니다.

- BFF와 공식 기록 서버 사이에 항목 식별자, 값의 상태, 데이터 버전에 관한 계약이 생겼습니다.
- 저장 뒤 공식값을 다시 읽기 때문에 요청이 한 번 더 발생합니다.
- 기존 코드가 새 도메인 객체를 사용하도록 점진적으로 옮겨야 합니다.
- 장애를 볼 때 BFF의 변환 과정과 공식 서버의 판단 과정을 함께 추적해야 합니다.

트레이드오프가 없는 설계는 대개 아직 비용을 찾지 못한 설계라고 생각합니다. 저희는 호출 한 번과 마이그레이션 비용을 더 내더라도, 월결산의 공식 판단이 갈라지는 위험을 줄이는 쪽을 선택했어요.

## 아직 완성된 클린 아키텍처는 아니에요

여기까지만 보면 도메인, 애플리케이션, 포트와 어댑터가 깔끔하게 정리된 것처럼 보일 수 있습니다. 하지만 현재 MYSCube를 완성된 클린 아키텍처라고 평가하는 것은 정확하지 않아요. 방향은 좋아졌지만 아직 전환 중인 구조에 가깝습니다.

일부 주정산 명령 서비스는 여러 업무 흐름을 한 클래스에서 처리해 크기가 큽니다. 저장 인터페이스도 아직 API에서 사용하는 자료형을 참조하는 부분이 남아 있어요. 일부 도메인 객체에는 데이터베이스 저장을 위한 표시가 함께 있어, 순수한 업무 모델과 저장 모델이 완전히 분리되지 않은 곳도 있습니다.

BFF에도 과제가 남아 있습니다. 구글 시트 변환과 화면 흐름을 담당하는 파일이 커졌고, 공식 저장 결과를 확인하기 위해 자바와 자바스크립트 양쪽이 일부 계약을 함께 이해합니다. 결과 대조는 경계 검증에 필요하지만, 그 코드가 다시 업무 판단으로 자라지 않도록 계약 테스트로 관리해야 해요.

이 문제들을 한 번의 대규모 재작성으로 해결할 계획은 없습니다. 기능을 수정할 때마다 다음 기준으로 경계를 조금씩 바로잡고 있습니다.

- 새로운 업무 규칙은 API 객체나 저장 코드가 아니라 도메인에 둡니다.
- 애플리케이션은 저장 구현 대신 필요한 기능의 인터페이스에 의존합니다.
- 큰 서비스는 실제로 분리할 업무 단위가 확인될 때 나눕니다.
- 기존 흐름을 옮길 때는 같은 입력에 같은 결과가 나오는 계약 테스트를 먼저 둡니다.

아키텍처 개선의 목표는 그림을 아름답게 만드는 것이 아니라, 다음 변경이 어디에 들어가야 하는지 팀이 예측할 수 있게 만드는 데 있다고 생각합니다.

## 구조를 바꾸고 무엇이 달라졌을까

가장 먼저 달라진 것은 수정할 곳을 찾는 방식입니다. 월결산을 구성하는 항목 수나 금액 상태가 바뀌면 도메인 규칙을 먼저 봅니다. 승인 조건이 바뀌면 승인 정책을 보고, 구글 시트의 열이 이동하면 BFF의 변환 코드만 확인해요.

테스트의 성격도 달라졌습니다. 160개 고정값의 완전성은 구글 시트나 데이터베이스를 띄우지 않고 월결산 객체만으로 확인할 수 있습니다. 반대로 BFF와 공식 서버 사이에서는 내부 계산을 중복 테스트하기보다, 요청한 값이 공식 저장 결과와 일치하는지를 확인해요.

다만 처리 속도가 몇 퍼센트 빨라졌다는 식의 성과를 말하기는 어렵습니다. 이번 작업의 주된 효과는 성능보다 변경의 예측 가능성과 공식 기록의 일관성에 있어요. 장애가 발생했을 때 어느 시스템의 값을 기준으로 복구해야 하는지도 이전보다 명확해졌습니다.

## 아직 못 푼 문제

현재 가장 큰 과제는 오래된 주정산 흐름입니다. 여러 업무 명령이 큰 서비스 클래스와 저장 인터페이스에 모여 있고, 일부 저장 코드는 여전히 외부 요청에서 사용하는 자료형을 알고 있어요.

그렇다고 파일 크기만 기준으로 기계적으로 쪼갤 수는 없습니다. 잘못 나누면 하나의 업무를 이해하기 위해 더 많은 파일을 오가게 되고 이름만 다른 서비스가 늘어납니다. 다음 변경이 발생했을 때 함께 바뀌는 규칙을 관찰하면서, 실제 업무 단위가 확인된 부분부터 분리하려고 해요.

BFF의 구글 시트 변환 코드도 커지고 있습니다. 시트 형식을 받아내는 완충지대라는 역할상 어느 정도 복잡성은 피하기 어렵지만, 화면 흐름과 셀 변환, 결과 대조까지 한곳에 계속 쌓이게 둘 수는 없습니다.

아직 답은 없습니다. 다만 이제는 복잡성이 생겼을 때 어디로 보내야 하는지 판단할 기준이 생겼습니다.

## 마치며

처음 MYSCube를 만들 때의 질문은 “구글 시트의 값을 어떻게 시스템으로 옮길까?”였습니다. 지금의 질문은 조금 달라졌어요.

> “이 값이 공식 기록이 되기까지, 어느 계층이 무엇을 판단해야 하는가?”

구글 시트의 값을 읽는 일은 여전히 BFF가 잘합니다. 월결산을 계산하고 승인하며 공식 기록으로 남기는 일은 Spring Boot 서버가 맡아요. 서버 안에서는 API가 외부의 요청을 번역하고, 애플리케이션이 업무 흐름을 지휘하며, 도메인이 규칙을 판단하고, 저장 어댑터가 그 결과를 보관합니다.

아직 모든 의존 관계가 이 원칙대로 정리된 것은 아닙니다. 하지만 새 기능을 더할 때마다 판단이 다시 바깥으로 새어나가지 않는지 확인할 기준은 생겼어요.

결국 이번 변화의 핵심은 백엔드가 하나 더 생긴 것이 아니었습니다. **시스템 안에서 공식적인 결정을 내리는 자리를 하나로 줄이고, 나머지 구성 요소가 그 결정을 돕고 검증하도록 역할을 다시 세운 것**이었습니다.
